## Describing a Machine, Not a Procedure

Here is a Verilog file with three lines in it, and a question about those lines that decides whether the rest of this guide will make sense to you.

```verilog
assign sum   = a ^ b;
assign carry = a & b;
assign parity = ^{a, b, carry};
```

The question: what happens if you swap the first and the last line?

The answer is *nothing*. Not "nothing much", not "nothing unless you are careful" — literally nothing. There is no before and after here. Those three lines are not three steps. They are three pieces of wire-and-gate that all exist at the same time, permanently, from the moment the circuit is powered until it is powered off. `parity` is not computed "after" `carry` in the sense that a program computes one variable after another; it is computed *continuously*, and the electrical settling that makes `carry` correct also makes `parity` correct a moment later, because the signal physically travels.

That is the single mental shift. Everything else in this chapter is detail. You are not writing down a sequence of things to do. **You are writing down a structure that exists all at once.**

Programming languages describe *how a machine that already exists should be driven*. An HDL describes *a machine that does not exist yet*. The output of your compiler is not a binary; conceptually it is a netlist — a list of gates and the wires between them. Nothing "runs". The circuit simply *is*, and applying voltages to its inputs makes its outputs settle.

Verilog is a little strange because it is really two languages fused into one file format. The first is a **description language**: `assign`, operators, module instances, `always` blocks — the part that becomes gates. The second is a **simulation control language**: `initial`, `$display`, `#5`, file I/O, `$random` — the part that drives the description in a simulator and prints results to your terminal. They look alike; they are not alike. The first becomes hardware. The second is a test harness that could never be built out of transistors and is never meant to be. Keeping them mentally separate is the difference between a design that works and a design that only simulates.

**The tool chain has three distinct phases, and readers conflate them constantly.**

1. **Parse and preprocess.** Macros expand, `` `include ``d files are pulled in, tokens are checked. Failures here are syntax errors.
2. **Elaboration.** The module hierarchy is built: parameters resolve to numbers, instances are created, vector widths are fixed, `generate` blocks unroll, ports bind. Everything about the design's *shape* freezes here. Icarus reports failures as `N error(s) during elaboration.`
3. **Simulation.** An event scheduler runs, time advances, `initial` and `always` processes execute.

There is a fourth phase — **synthesis** — that maps the elaborated description onto real gates or FPGA lookup tables. Icarus does not do it. This matters more than it sounds.

> **Icarus reality.** **Icarus Verilog does not synthesise. It only simulates.** Nothing you write in this guide will be checked by a synthesis tool, which means nothing will stop you writing a `$display` in the middle of a datapath, or comparing against `x` with `===` in what you think is real logic, or using a `real` where a 24-bit vector belongs. All of it simulates beautifully. You have to police the synthesisable subset yourself. Every time this chapter says "not synthesisable", read it as a rule you are personally responsible for, because no tool in this flow will enforce it.

The elaboration/simulation split is worth one concrete example, because it explains a rule you will otherwise trip over. A `parameter` is resolved during elaboration, so a parameter can size a vector: `reg [W-1:0] mantissa;` is fine. A `reg` holds a value that only exists during simulation, so a `reg` can never size anything. Widths are frozen before the first event is scheduled.

A design also lives at three levels of abstraction at once, and a single module may mix all three.

| Level | Constructs | Looks like |
|---|---|---|
| Structural / gate | module instances, gate primitives `and` `or` `xor` `not` | `xor g1 (s, a, b);` |
| Dataflow / RTL | `assign`, operators, concatenation | `assign {cout, sum} = a + b + cin;` |
| Behavioural | `always`, `initial`, `if`, `case`, `for`, `function` | `always @(*) if (a > b) y = a; else y = b;` |

Chapter 1's gate diagrams map onto the structural level; you will build a ripple-carry adder that way later in this chapter, precisely because there the topology *is* the lesson. The floating point adder itself will be almost entirely dataflow and behavioural RTL, because writing a 24-bit adder as gate instances is a punishment rather than a lesson. A good framing to keep: *structural Verilog describes a plan you already have; dataflow Verilog asks the tool to produce one.*

**One paragraph of history, because the version number on your command line is a fossil.** Verilog was created at Gateway Design Automation by Prabhu Goel, Phil Moorby and Chi-Lai Huang in 1983–84 ([Wikipedia, "Verilog"](https://en.wikipedia.org/wiki/Verilog)) and standardised as IEEE 1364 in 1995, revised in 2001 — the big one, which gave us ANSI port lists, `generate`, signed arithmetic, `localparam`, `+:`/`-:` and `` `default_nettype `` — and again in 2005. Then it stopped: 1364-2005 was **merged into SystemVerilog** in 2009, and its standards record now reads, verbatim, "Superseded Standard" ([IEEE Std 1364-2005 record page](https://standards.ieee.org/ieee/1364/3641/)). What people call "Verilog" is now the Verilog-compatible subset of IEEE 1800 — but Icarus still names its language levels after the old standards, which is why the flag you will type is `-g2012`.

> **Icarus reality.** The installed toolchain reports `Icarus Verilog version 13.0 (stable) (v13_0)`. Its `-ghelp` lists exactly six generations: `1995 2001 2005 2005-sv 2009 2012`. The online documentation describes a development branch that also offers `-g2017` and `-g2023`; the released 13.0 binary does not. Everything in this guide is written against `-g2012`, which is the highest this build accepts. The default, if you pass nothing, is `-g2005` — and that default is too old for several constructs we want.

## Your First Module, Compiled and Run

Enough framing. Open an editor and make a directory. Everything in this chapter lives in `src/ch02/`, and everything in it has been compiled and run exactly as printed.

The first thing you will build is the half adder from chapter 1's "Half adder and full adder" — sum is XOR, carry is AND. Here is the whole file, `half_adder.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Chapter 1's half adder, written down.
// sum   = a XOR b
// carry = a AND b
module half_adder
  (input  wire a,
   input  wire b,
   output wire sum,
   output wire carry);

  assign sum   = a ^ b;
  assign carry = a & b;

endmodule

`default_nettype wire
```

Six things are happening, and you should be able to name all of them before moving on.

The two lines starting with a backtick are **compiler directives**, not statements — they are handled by the preprocessor before parsing. `` `timescale 1ns/1ps `` says that a bare `#1` delay means one nanosecond and that all delays are rounded to picoseconds. `` `default_nettype none `` disables Verilog's oldest and worst misfeature, silent creation of undeclared wires; we will earn that line the hard way in "Modules, Ports, and Instantiation", and from here on **every listing in this guide carries it**.

`module half_adder ( ... );` opens the only unit of design Verilog has. There are no free functions, no globals, no namespaces. Modules do not nest textually; you build hierarchy by *instantiating* one module inside another. The `endmodule` at the bottom needs no semicolon.

Inside the parentheses is an **ANSI-style port list**: direction, type, name, all in one place. `input wire a` says a is an input and is a net. The final `` `default_nettype wire `` restores the default so that the file is safe to `` `include `` into something else, because these directives are global across the whole compile, not scoped to the file.

And then the two `assign` statements, which are the entire circuit: two gates, permanently connected, both live at all times.

Now something to drive it. A Verilog design does not have a `main`; you write a **testbench**, a module with no ports whose job is to apply stimulus and check answers. Here is `tb_half_adder.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

module tb_half_adder;

  reg  a, b;
  wire sum, carry;
  integer errors = 0;

  half_adder dut (.a(a), .b(b), .sum(sum), .carry(carry));

  task check;
    input exp_sum;
    input exp_carry;
    begin
      if (sum !== exp_sum || carry !== exp_carry) begin
        errors = errors + 1;
        $display("FAIL a=%b b=%b : got sum=%b carry=%b, expected sum=%b carry=%b",
                 a, b, sum, carry, exp_sum, exp_carry);
      end else begin
        $display("ok   a=%b b=%b -> sum=%b carry=%b", a, b, sum, carry);
      end
    end
  endtask

  initial begin
    a = 1'b0; b = 1'b0; #1 check(1'b0, 1'b0);
    a = 1'b0; b = 1'b1; #1 check(1'b1, 1'b0);
    a = 1'b1; b = 1'b0; #1 check(1'b1, 1'b0);
    a = 1'b1; b = 1'b1; #1 check(1'b0, 1'b1);

    if (errors == 0) $display("PASS tb_half_adder");
    else             $fatal(1, "FAIL tb_half_adder: %0d error(s)", errors);
    $finish;
  end

endmodule

`default_nettype wire
```

Compile and run it with the two commands you are going to type several thousand times:

```sh
iverilog -g2012 -Wall -o /tmp/sim half_adder.v tb_half_adder.v
vvp /tmp/sim
```

`iverilog` compiles; `vvp` runs the compiled program. `-g2012` picks the language generation. `-Wall` turns on Icarus's warning classes, and you should never omit it. `-o` names the output — without it you get `a.out`. The order of source files does not matter for finding modules (elaboration binds instances by name), but it *does* matter for macros and `` `default_nettype ``, which take effect in file order.

The real output:

```
ok   a=0 b=0 -> sum=0 carry=0
ok   a=0 b=1 -> sum=1 carry=0
ok   a=1 b=0 -> sum=1 carry=0
ok   a=1 b=1 -> sum=0 carry=1
PASS tb_half_adder
tb_half_adder.v:34: $finish called at 4000 (1ps)
```

That is a working hardware description, simulated, verified, in about forty lines.

Four things in the testbench deserve immediate attention, because you will repeat them constantly.

`half_adder dut (.a(a), .b(b), ...)` is an **instantiation**: it creates one copy of `half_adder`, names that copy `dut`, and connects its ports to signals in the testbench. The dotted form is **named connection** — port name inside the dots, local signal in the parentheses. There is a positional form too. Do not use it; "Modules, Ports, and Instantiation" shows you why with a real mis-wire.

`task check; input exp_sum; ... endtask` is a **task**: a named block of statements you can call by name, with its arguments declared inside its own body rather than in a parameter list. It exists here purely to avoid writing the same comparison four times. The full rules for `task` — and for its value-returning sibling `function` — are in "`function` and `task`" near the end of this chapter; for now, read it as a subroutine.

The stimulus lives in an `initial` block, which runs once, starting at time zero, and is pure simulation-control language — you could not build it out of transistors and there is no attempt to. `#1` advances simulated time by one nanosecond so the combinational logic has a moment to settle before we look at it. `reg` for the driven signals and `wire` for the observed ones is a rule we will make precise shortly.

And the check uses `!==`, not `!=` — why, in "The four equality operators" below — and ends in `$fatal` rather than a friendly message.

> **Trap.** A testbench that prints values for a human to eyeball is not a testbench, it is a demo. Worse, `$error` — Verilog's own error-reporting task — prints a loud `ERROR:` line and then *continues, leaving the process exit code at zero*. A continuous-integration job would call that a pass. Every self-checking testbench in this guide therefore counts its failures and ends with `$fatal(1, ...)`, which terminates immediately with exit code 1. Verified behaviour: `$info`, `$warning` and `$error` all print and continue; only `$fatal` changes the exit code.

> **Icarus reality.** From here on, every command in this guide is exactly `iverilog -g2012 -Wall -o <output> <files>` followed by `vvp <output>`. Put the output somewhere outside your source tree — this guide uses `/tmp` — because a compiled `vvp` program is a build artifact and does not belong next to your Verilog.

## Modules, Ports, and Instantiation

A half adder with fixed one-bit ports is not much of a building block. Real designs are parameterised: you want *an* adder, and you decide its width where you use it. Here is `adder_ansi.v`, which will show up again in three later sections:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Parameterised unsigned adder, ANSI-2001 port list.
// The {cout, sum} concatenation on the left is the whole trick: the target is
// W+1 bits wide, so the addition is evaluated at W+1 bits and the carry-out
// survives.
module adder_ansi #(parameter W = 8)
  (input  wire [W-1:0] a,
   input  wire [W-1:0] b,
   input  wire         cin,
   output wire [W-1:0] sum,
   output wire         cout);

  assign {cout, sum} = a + b + cin;

endmodule

`default_nettype wire
```

That one line, `assign {cout, sum} = a + b + cin;`, is the most useful thing in this chapter. Chapter 1's "Unsigned binary" section warned you that adding two n-bit numbers needs n+1 bits somewhere; the braces are where the extra bit lives. We will take that line apart properly in "Width and Signedness", where you will find out exactly how much damage the alternative spelling does.

**Parameters** are elaboration-time constants. `#(parameter W = 8)` declares one with a default; a caller overrides it per instance. Two flavours matter:

- `parameter` — overridable from outside.
- `localparam` — **not** overridable. Use it for anything derived, so a caller cannot break an internal invariant:

```verilog
module fp #(parameter EXP_W = 8, parameter MAN_W = 23) ( ... );
  localparam WIDTH = 1 + EXP_W + MAN_W;   // derived: must not be overridden
  localparam BIAS  = (1 << (EXP_W-1)) - 1;
```

That pattern is exactly what the floating point adder will use. Because parameters resolve at elaboration, they can size vectors, bound `for` loops, and drive `generate`.

**The port list has two syntaxes, and you should be able to read both.** The ANSI style above is Verilog-2001 and is what you will write. The older non-ANSI style is what you will find in existing code. The header of `adder_1995.v` — the same adder, same body — is the whole difference:

```verilog
module adder_1995 (a, b, cin, sum, cout);

  parameter W = 8;

  input  wire [W-1:0] a;
  input  wire [W-1:0] b;
  input  wire         cin;
  output wire [W-1:0] sum;
  output wire         cout;
```

The header lists bare names; directions and types come afterwards in the body, and parameters are declared in the body too. Each name appears at least twice and often three times. That redundancy is the entire argument for the newer syntax, and it is enough of an argument. Read non-ANSI, write ANSI.

Direction is mandatory: `input`, `output`, or `inout`. What *defaults* is the type — a port with a direction and no type is a `wire`, subject to `` `default_nettype ``. The rule for which type an output should be is short and worth memorising now, even though the reasoning waits for "Wires, Variables, and the Lie in the Name `reg`": **an output is a `wire` if it is driven by `assign` or by an instance, and a `reg` if it is driven from inside an `always` or `initial` block.** An `input` is always a net and can never be a `reg`. An `inout` must be a net, driven with a three-state expression like `assign pad = oe ? d : 1'bz;`.

**Instantiation** creates a copy. The instance name is mandatory for modules (it is optional for the built-in gate primitives, but name those too). Both connection styles are legal:

```verilog
adder_ansi          u_named (.a(a), .b(b), .cin(cin), .sum(s), .cout(c));  // named
adder_ansi          u_posn  (a, b, cin, s, c);                             // positional
adder_ansi #(.W(4)) u_small (.a(a[3:0]), .b(b[3:0]), .cin(cin), .sum(s4), .cout(c4));
```

Parameter overrides follow the same pattern: `#(.W(4))` is the named form, `#(4)` the positional one. `tb_port_styles.v` runs all three of these against 64 random vectors and confirms they agree, which they do.

Now the argument against positional connection, made with a real mis-wire rather than an assertion. `bad_positional.v` instantiates the same adder twice, once correctly and once with `b` and `cin` swapped:

```verilog
  adder_ansi u_good (.a(a), .b(b), .cin(cin), .sum(s_good), .cout(c_good));
  adder_ansi u_bad  (a, cin, b, s_bad, c_bad);   // b <-> cin swapped
```

Build and run it, and this is what it prints:

```
bad_positional.v:19: warning: Port 2 (b) of module adder_ansi expects 8 bit(s), given 1.
bad_positional.v:19:        : Padding 7 high bits of the port.
bad_positional.v:19: warning: Port 3 (cin) of module adder_ansi expects 1 bit(s), given 8.
bad_positional.v:19:        : Pruning 7 high bits of the expression.
intended  a=200 b=100 cin=1 -> cout=1 sum=45
mis-wired a=200 b=100 cin=1 -> cout=0 sum=201
PASS bad_positional: trap reproduced, mis-wire gives 201 not 301
bad_positional.v:38: $finish called at 1000 (1ps)
```

The design produced 201 where it should have produced 301, and the compiler's only complaint was two *warnings* about widths. Now notice why even those appeared: `b` is eight bits and `cin` is one, so the swap produced a width mismatch. Swap two ports of the *same* width — two 24-bit mantissas, say — and Icarus says nothing whatsoever. There is no diagnostic, there is no crash, there is a wrong number.

> **Trap.** Positional port connection is checkable by nothing. Named connection is the only form where the compiler knows what you meant, and it costs you a few keystrokes once per instance. Use it always. The same argument applies to parameter overrides: write `#(.W(4))`, not `#(4)`.

Two more mechanisms, both of which you should be able to read and one of which you should never write.

**Hierarchical names.** From anywhere, you can reach into an instance with a dotted path: `tb_port_styles.u_1995.W`, `u_named.a`. The testbench above prints one:

```
hierarchical: tb_port_styles.u_1995.W = 8, scope %m = tb_port_styles
```

`%m` in a `$display` format string prints the current scope and takes no argument. Hierarchical references are excellent for probing in a testbench and are **not synthesisable** — there is no wire in silicon corresponding to "reach into that module and read its parameter".

**`defparam`.** An old way to override a parameter from a distance — `defparam u_sub.P = 99;`. It still works, and — verified — draws no warning even under `-Wall`. It is deprecated in IEEE 1364-2005 Annex C because the override lives *away* from the instance it modifies. Read it if you find it; never write it.

### The implicit wire, and the line that stops it

Here is Verilog's oldest wart, and the reason every file in this guide opens with `` `default_nettype none ``. An undeclared identifier used where a net is expected is silently created as a **one-bit wire**. `bad_implicit.v` — note that this is the one file in the chapter that deliberately omits the directive:

```verilog
  reg  [3:0] a, b;
  wire [3:0] good;

  // ...

  assign godo = a & b;      // typo: meant `good'
```

Real output:

```
bad_implicit.v:15: warning: implicit definition of wire 'godo'.
good = zzzz   ($bits = 4)
godo = 0   ($bits = 1)
```

`good`, the signal you actually declared and presumably use elsewhere, is undriven — floating, all `z`. The four-bit result of `a & b` went into a one-bit wire you never wrote down. In a mantissa datapath this is how twenty-three bits vanish.

The folklore about this bug is broader than the truth, and the truth is worth knowing precisely. Implicit nets are created only where the language says they may be: on the **left-hand side of a continuous assignment**, and in **port connections**. A typo on the *right*-hand side is a hard error — Icarus says `error: Unable to bind wire/reg/memory 'tnp'`. So the silent case is narrower than people claim. It is also exactly the case that silently narrows a signal.

The defence is mechanical. `bad_nettype_none.v` is the same code with the directive restored, and it does not compile:

```
bad_nettype_none.v:13: error: Net godo is not defined in this context.
1 error(s) during elaboration.
```

A typo is now an error at elaboration, before a single event is scheduled. Put `` `default_nettype none `` at the top of every file. Put `` `default_nettype wire `` at the bottom, because the directive is *global to the compile*, not scoped to the file — it stays in effect across file boundaries on one `iverilog` command line, and leaving `none` set can break somebody else's code compiled after yours.

> **Icarus reality.** Under `` `default_nettype none ``, a bare ANSI port declaration like `input a` — no `wire` keyword — is still accepted by Icarus. Other tools reject it. So the directive does not force you to write `input wire a` here, but write it anyway; portability is free at the point of typing and expensive later.

## Wires, Variables, and the Lie in the Name `reg`

Ask a simulator what value a wire has before anything drives it, and it will not say zero. Ask it what value two disagreeing drivers produce, and it will not pick one. Verilog's answer in both cases is a value that has no voltage: it refuses to guess.

Every bit of every net and every variable holds one of **four** values.

| Value | Meaning in simulation | Physical reading |
|---|---|---|
| `0` | logic zero | driven low |
| `1` | logic one | driven high |
| `x` | **unknown** | the simulator does not know: uninitialised storage, a driver conflict, or a value that depends on a race |
| `z` | **high impedance** | no driver at all; the net floats |

`x` is the single most misunderstood thing in the language. It is **not** "any value" and it is **not** a voltage. Real silicon has no `x`; a real wire is always at some potential. `x` is a *modelling* value that means "I refuse to guess, and if you propagate me you will find out where your design is under-specified." Treat every unexpected `x` as a bug report, not as noise. Uninitialised `reg`s start at `x`; undriven nets sit at `z`.

`tb_mux2.v` shows what `x` really means better than any definition. The module under test is chapter 1's multiplexer, spelled as one conditional operator:

```verilog
module mux2 #(parameter W = 8)
  (input  wire [W-1:0] d0,
   input  wire [W-1:0] d1,
   input  wire         sel,
   output wire [W-1:0] y);

  assign y = sel ? d1 : d0;

endmodule
```

Drive `sel` to `x` and watch:

```
ok   d0=aa d1=55 sel=0 -> y=aa
ok   d0=aa d1=55 sel=1 -> y=55
ok   d0=aa d1=55 sel=x -> y=xx
ok   d0=aa d1=aa sel=x -> y=aa
ok   d0=a5 d1=aa sel=x -> y=ax
```

The third line is what everybody expects. The fourth and fifth are the interesting ones. With an unknown selector and two arms that *agree*, the answer is known — it does not matter which way the mux goes. With arms that agree in the top nibble and differ in the bottom, only the bottom nibble goes unknown. `x` is not contagious; it is precise about exactly how much is unknown.

### Nets and variables are different kinds of thing

A **net** models a wire. It has *drivers*, and its value is the resolution of all of them, recomputed continuously. You cannot assign a net procedurally; you connect things to it.

- `wire` — the one you will use. More than one driver, and disagreement resolves to `x`.
- `supply0` / `supply1` — constant ground and supply rails.

`tri`, `wand`, `wor` and `uwire` also exist, for three-state and open-drain buses. The FP adder has one driver per net, so recognise the names and move on.

A **variable** models storage *in the simulator*. It holds its value until something assigns it again. Variables are assigned only inside procedural blocks (`always`, `initial`) or as function and task outputs.

- `reg` — four-state, any width. The workhorse.
- `integer` — four-state, **32-bit signed**. Verified: `$bits(integer)` is 32.
- `time` — 64-bit unsigned. Verified: `$bits(time)` is 64.
- `real` — a C `double`, two-state, no `x`/`z`, not synthesisable. Testbenches only.

`tb_drivers.v` makes the resolution rules concrete:

```
-- two drivers on one net
  a=1 b=0 -> wire=x  wand=0  wor=1  (nda = a&b = 0)
  a=1 b=1 -> wire=1  wand=1  wor=1  (nda = a&b = 1)
  a=0 b=0 -> wire=0  wand=0  wor=0  (nda = a&b = 0)
-- supply nets are constants
  {vdd,gnd,vdd,gnd} = 1010
```

Two `assign` statements to the same `wire` are two drivers. Where they agree the net takes that value; where they disagree it goes to `x`. In real hardware that is a short circuit between an output driving high and an output driving low, and it burns.

> **Trap.** Icarus does **not** warn about multiple drivers on a net. The `x` is your only signal. When an `x` appears somewhere you did not expect, the two suspects are always the same: a second driver on a net, or a `reg` nobody has written yet.

### `reg` does not mean register

Say it out loud, because the name has misled two generations of engineers. `reg` means *"a variable that holds its value between procedural assignments."* It is a storage cell in the simulator's memory. It says nothing about flip-flops.

Here is a module whose output is declared `reg` and which contains not one bit of storage — `comb_max.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// `output reg' does not mean a register. This module has no clock, no
// storage, and no flip-flops: it is a comparator feeding a multiplexer.
// The keyword only says "y is assigned from inside a procedural block".
module comb_max
  (input  wire [7:0] a,
   input  wire [7:0] b,
   output reg  [7:0] y);

  always @(*) begin
    if (a > b) y = a;
    else       y = b;
  end

endmodule

`default_nettype wire
```

Run `tb_comb_max.v` over 516 cases and the output tracks the inputs the whole way:

```
a=100 b=200 -> y=200   (no clock anywhere in the design)
PASS tb_comb_max (516 cases)
```

`always @(*)` means "re-evaluate this block whenever anything it reads changes", and an assignment inside such a block is a **procedural assignment**; the full treatment is in "A First Look at Procedural Blocks" below. There is no clock in that design. There is no edge. The hardware is a magnitude comparator (chapter 1, "The magnitude comparator") feeding a multiplexer, and `reg` appears only because Verilog requires the target of a procedural assignment to be a variable. Storage comes from a *clocked* `always` block, which is chapter 3's subject. The keyword and the concept have nothing to do with each other.

SystemVerilog introduced `logic` precisely to end this confusion; it is the modern spelling of `reg`, and Icarus accepts it at `-g2005-sv` and above. This guide stays with `wire`/`reg` because chapter 1's references and most existing Verilog use them, and mixing spellings mid-book helps nobody. Know that `logic` exists and means the same thing.

### Vectors, part-selects, and the barrel shifter

`reg [7:0] v;` declares an eight-bit vector where bit 7 is the most significant. Always declare `[N-1:0]`. The ascending form `reg [0:31]` is legal and reverses the *bit numbering*, not the value — verified:

```
-- an ascending declaration reverses the NUMBERING, not the value
  reg [0:31] a; a[0:7] = de  a[24:31] = ef
```

for the same `32'hDEAD_BEEF` that gives `v[31:28] = d` and `v[15:8] = be` in the normal declaration. Mixing the two conventions in one design is a reliable way to produce reversed-bit bugs. Pick descending and never deviate.

Selecting from a vector comes in three forms, and the third is the one that matters for this guide.

A **bit-select** is `v[3]`. A **constant part-select** is `v[15:8]`, and its range direction must match the declaration's. Both are what you would guess.

The third is the **indexed part-select**, added in Verilog-2001: `v[base +: width]` takes `width` bits starting at `base` and counting *up* in bit number; `v[base -: width]` takes `width` bits ending at `base` and counting *down*. Here is `byte_select.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Indexed part-select with a variable base. The WIDTH is constant (8), only
// the BASE varies, which is exactly why this is legal and why it maps to a
// multiplexer. `word[idx*8 : idx*8+7]' would be illegal: both bounds vary.
module byte_select
  (input  wire [31:0] word,
   input  wire [1:0]  idx,
   output wire [7:0]  lo_up,     // 8 bits starting at idx*8, counting up
   output wire [7:0]  hi_down);  // 8 bits ending at 31-idx*8, counting down

  assign lo_up   = word[idx*8      +: 8];
  assign hi_down = word[31 - idx*8 -: 8];

endmodule

`default_nettype wire
```

with `word = 32'hDEAD_BEEF`:

```
idx=0 : word[idx*8 +: 8] = ef   word[31-idx*8 -: 8] = de
idx=1 : word[idx*8 +: 8] = be   word[31-idx*8 -: 8] = ad
idx=2 : word[idx*8 +: 8] = ad   word[31-idx*8 -: 8] = be
idx=3 : word[idx*8 +: 8] = de   word[31-idx*8 -: 8] = ef
```

**The width must be a constant; only the base may vary.** That restriction is the entire point of the syntax. `v[k*8+7 : k*8]` is illegal because both bounds are variable and the compiler cannot fix a width at elaboration. `v[k*8 +: 8]` is legal because the width is nailed down and only the offset moves — and a fixed-width window at a variable offset is *exactly* a multiplexer, which is why it maps to hardware at all.

> **Seed for chapter 9.** That is a barrel shifter in one line. Chapter 1's "The barrel shifter" described a logarithmic network of muxes that shifts by any amount in constant depth; `v[base +: width]` is how you write one without drawing it. The FP adder needs two: one to right-shift the smaller significand by the exponent difference, and one to left-shift the result by the leading-zero count. Both sit on the critical path, and the alignment shifter must not discard the bits it pushes off the end — see "Reduction Operators and the Sticky Bit" below.

Out-of-range selects are not errors. They return `x`, with a warning under `-Wall`:

```
tb_partsel.v:38: warning: Part select [35:32] is selecting after the vector v[31:0].
tb_partsel.v:38:        : Replacing the out of bound bits with 'bx.
...
  v[35:32]  = x
  v[40 +: 4]= x
```

### Arrays are not vectors

A **vector** is one multi-bit value; it does arithmetic, it can be part-selected, it can be a port. An **array** is many separate values:

```verilog
reg [7:0] mem [0:255];    // 256 independent 8-bit words
```

The memorable phrasing is **width on the left of the name, depth on the right**. `mem` as a whole is not an expression — you cannot add it, print it, or pass it through a port in classic Verilog. Only `mem[i]` is a value, and Verilog-2001 lets you part-select one: `mem[1][3:0]`. The FP adder needs no memories, so that mnemonic plus one verified fact is all this chapter owes the subject — an unwritten word reads as `x`, not as zero, which is the four-state rule showing up again.

### `signed`, and where it comes from

`reg` and `wire` are **unsigned** by default. `integer` is signed. You can declare either explicitly:

```verilog
reg  signed [7:0] s;
wire signed [7:0] ws;
```

Signedness changes which of `>>` and `>>>` sign-extends, how `<`, `/` and `%` behave, and — the one that surprises everyone — how a value extends when it is widened. Here is that last rule, verified in `tb_signedness.v`:

```
-- extension is decided by the SOURCE's signedness, not the target's
  00001001	unsigned 4'b1001 -> [7:0]
  11111001	signed   4'b1001 -> signed [7:0]
  11111001	signed   4'b1001 -> UNSIGNED [7:0]
```

Read the third line twice. A signed four-bit source assigned to an *unsigned* eight-bit target still sign-extends. The destination has no vote. Extension is a property of the expression being extended. The full treatment is in "Width and Signedness" below, because signedness interacts with expression width and the interaction is where the damage happens.

Two smaller items worth knowing before you meet them. Classic Verilog has **no string type**: a string literal is just 8-bit character codes packed into a vector and left-padded with zeros, so printing a short string from a wide variable with `%s` gives you leading spaces. And `real` is an IEEE double, useful only in testbenches; assigning a `real` to an `integer` **rounds**, while `$rtoi` truncates. Which brings us to a fact worth banking for the end of the book.

> **Seed for chapter 12.** Icarus 13.0 at `-g2012` supports `shortreal` along with `$shortrealtobits` and `$bitstoshortreal` — a direct, exact route between a host 32-bit float and its IEEE 754 bit pattern. Verified: `$shortrealtobits(1.5)` gives `3fc00000`, and `$bitstoshortreal(32'h40490fdb)` gives `3.141593`. That is how the final testbench of chapter 12 will build its golden model: compute the expected sum in host floating point, convert to bits, compare against the DUT bit for bit.

## Writing Numbers Down

How many bits is `8'hFF`? If you said eight hex digits you are in good company and you are wrong; it is eight *bits*. That confusion is worth clearing up before it costs you a mantissa.

A Verilog literal has the form `<size>'<signed><base><value>`, and every part earns its place:

- **`<size>`** — the width **in bits**, written in plain decimal with no base prefix.
- **`'`** — the tick, mandatory.
- **`<signed>`** — an optional `s` or `S`, which makes the literal a signed value.
- **`<base>`** — `b` binary, `o` octal, `d` decimal, `h` hex; case-insensitive.
- **`<value>`** — digits legal for the base, plus `_` separators anywhere but the first character, plus `x`, `z` and `?` in any base except decimal.

`tb_literals.v` walks through the whole surface. The four spellings of one nibble:

```
-- bases, all four spellings of the same nibble
  1010  4'hA
  0111  4'o7
  1001  4'd9
  1010  4'b1010
-- underscores are cosmetic
  10100101  8'b1010_0101
```

Underscores do nothing but help you read, which is exactly why you should use them liberally. The single most valuable place is a floating point constant:

```
  32'b0_10000000_00000000000000000000000 = 40000000 (that is 2.0)
```

Sign, exponent, significand, separated exactly where IEEE 754 separates them. Adopt this style for every FP constant in the rest of the book; it turns an unreadable hex blob into something you can check by eye against chapter 1's "The contrast that matters: IEEE 754 is sign-magnitude".

**Left extension follows the leftmost digit you wrote**, and this is a real rule rather than a quirk:

```
-- left extension copies the LEFTMOST SPECIFIED digit's kind
  0010  4'b10   (0 extends with 0)
  xxx1  4'bx1   (x extends with x)
  zzz1  4'bz1   (z extends with z)
```

So `8'bx` is not one unknown bit and seven zeros. It is eight unknown bits. Likewise one `x` digit in hex sets four bits unknown, and in octal three — the `x` applies to the whole digit position.

**Unsized literals are 32 bits.** `'h1F` has a base but no size; it is 32 bits wide. A bare decimal like `42` is also 32 bits, and additionally **signed**, which is why `-1` behaves the way you expect in integer contexts and why the width rules in "Width and Signedness" below have a 32 lurking in them.

```
-- unsized literals are 32 bits
  'h1F = 31, $bits('h1F) = 32
```

**Signed literals** use `'sd`, `'sh`, `'sb`. The `s` makes *that operand* signed; it does not sign-extend the digits you wrote. `4'sb1001` is the signed value −7, not 9:

```
-- signed literals
  -7  4'sb1001 read as a signed value
  5 / -5  'sd5 and -'sd5
```

And here is a pair that looks like a typo and is not:

```
-- unary minus happens AFTER the operand grows to the context width
  11111001  w8 = -4'd7   (widened to 8 bits, then negated)
  1111  q  = -4'd1   (stays 4 bits: an unsigned bit pattern)
```

`-4'd7` assigned to an eight-bit target gives `11111001`, because the four-bit literal is widened to the context width *first* and negated afterwards. The same expression in a four-bit context stays four bits. If that feels arbitrary, it is the width algorithm poking through, and it is the subject of "Width and Signedness" below.

**Fill literals.** SystemVerilog added `'0`, `'1`, `'x` and `'z`, which fill the target width with that value whatever the width is. All four work in Icarus at `-g2012`:

```
-- fill literals (SystemVerilog; need -g2005-sv or later)
  000000000000  f = '0
  111111111111  f = '1
  xxxxxxxxxxxx  f = 'x
  zzzzzzzzzzzz  f = 'z
```

These are genuinely useful for FP work — `exp = '1;` is a readable way to build the all-ones exponent of an infinity or NaN — but they carry a hazard. In a **self-determined** context, `'1` collapses to one bit: `$bits('1)` is 1, verified. So `{'1, x}` is not "all ones then x". Use fill literals only as a whole right-hand side or a port connection, where the width is imposed from outside.

> **Icarus reality.** At `-g2005` the fill literals produce `warning: Using SystemVerilog 'N bit vector. Use at least -g2005-sv to remove this warning.` rather than an error. They are one of the reasons this guide compiles with `-g2012` everywhere.

**A literal too big for its declared size is truncated from the left**, silently as far as behaviour is concerned but not silently as far as diagnostics go:

```
tb_literals.v:79: warning: Numeric constant truncated to 4 bits.
...
  1111  4'd31
```

Note that this warning appears with or without `-Wall`. Remember that, because "The silent truncation" below shows you a much more dangerous truncation that produces no message at all.

Four style rules to adopt now and keep:

- **Size your literals.** `8'd0`, not `0` — except where a bare small integer really is a count: loop bounds, replication counts, parameter defaults.
- **Never write a decimal literal for a bit pattern.** Use `'b` or `'h`.
- **Use `_` in anything over eight bits**, grouped along field boundaries where the value has fields.
- **Reach for `'0` and `'1`** for width-agnostic constants, and remember they need `-g2012` and that they collapse when self-determined.

## The Operators

Two expressions, one keystroke apart:

```verilog
a && b
a &  b
```

With `a = 8'b0000_0010` and `b = 8'b0000_0100`, the first is 1 and the second is 0. Both are "and". Neither is a typo. If you cannot yet say why, this section is for you.

Verilog's operator set is close to C's, with reduction operators bolted on at the top and a handful of hardware-specific additions. Here is the precedence table, highest first.

| Prec | Operators | Assoc | Notes |
|---|---|---|---|
| 1 | `+ - ! ~ & ~& \| ~\| ^ ~^ ^~` (all **unary**) | right | unary arithmetic, logical NOT, bitwise NOT, **reduction** |
| 2 | `**` | left | power (Verilog-2001) |
| 3 | `* / %` | left | |
| 4 | `+ -` (binary) | left | |
| 5 | `<< >> <<< >>>` | left | shifts |
| 6 | `< <= > >=` | left | relational |
| 7 | `== != === !== ==? !=?` | left | `==?`/`!=?` are SystemVerilog wildcard equality |
| 8 | `&` (binary) | left | |
| 9 | `^ ~^ ^~` (binary) | left | |
| 10 | `\|` (binary) | left | |
| 11 | `&&` | left | |
| 12 | `\|\|` | left | |
| 13 | `?:` | right | |
| — | `{}` `{{}}` | — | concatenation and replication are primaries; they impose no precedence |

The one line of practical advice that comes out of that table: **parenthesise anything that mixes `&`, `|` or `^` with `==`.** Bitwise binds *below* equality, inherited straight from C, which is why `if (a & MASK == 0)` parses as `a & (MASK == 0)` and is the classic bug.

### Logical versus bitwise

The distinction that opened this section, stated properly:

- **Logical** `&& || !` reduce each operand to a single truth value — non-zero is true — and return **one bit**.
- **Bitwise** `& | ^ ~ ~^` operate **per bit** and return a vector as wide as the expression.

Verified with the same two operands:

```
-- logical vs bitwise: a = 8'b0000_0010, b = 8'b0000_0100
  1  a && b
  00000000  a &  b
  1  a || b
  00000110  a |  b
  0  !a
  11111101  ~a
```

`a & b` is zero because the two operands share no set bit. `a && b` is one because both are non-zero. Use `&&`, `||` and `!` in conditions; use `&`, `|`, `^` and `~` in datapaths. Mixing them up produces code that works on one-bit signals and fails silently the moment a signal gets wider.

### The four equality operators

Verilog has two families of equality, and confusing them will cost you a day.

| Operator | Name | `x`/`z` handling | Result | Synthesisable |
|---|---|---|---|---|
| `==` | logical equality | any `x`/`z` in either operand makes the result `x` | 0/1/x | yes |
| `!=` | logical inequality | same | 0/1/x | yes |
| `===` | case equality | compares `x` and `z` **literally** | 0/1 only | **no** |
| `!==` | case inequality | same | 0/1 only | **no** |

Verified with `a = 8'b1010_101x`, `b = 8'b1010_1010`:

```
-- equality: a = 8'b1010_101x, b = 8'b1010_1010
  x  a ==  b
  0  a === b
  1  a !== b
  1  8'bx === 8'bx
  x  8'bx ==  8'bx
  1  if (a == b) took the ELSE branch
```

The last line is where designs go quietly wrong. `a == b` evaluated to `x`, and `if (x)` is **false** — an unknown condition takes the `else` branch. Nothing crashes. Nothing warns. Your design just picks a path, and it is not necessarily the one you would have picked.

Why is `===` not synthesisable? Because there is no gate that can distinguish "unknown" from "one". `x` is a property of the model, not of silicon; a synthesis tool would have to invent a signal that does not exist. So `===` and `!==` belong in testbench self-checks — `if (dut_out !== expected) $fatal(1, ...)` — and nowhere else. That is exactly how every testbench in this chapter is written.

SystemVerilog adds **wildcard equality**, `==?` and `!=?`, where `x`, `z` and `?` in the **right** operand are don't-cares and the left operand is matched exactly. Verified working in Icarus at `-g2012`:

```
-- wildcard equality: wildcards allowed only on the RIGHT
  1  4'b1010 ==? 4'b10zz
  0  4'b1010 ==? 4'b11zz
  0  4'b1010 !=? 4'b10zz
```

Because the wildcards are one-sided, this is the safe way to do a masked compare — and it will matter when we get to `casex` below.

### Arithmetic, shifts, and the conditional operator

`+ - * / % **` all operate on the **whole vector**, not bit by bit. Overflow wraps silently, truncated to the expression width — the subject of "Width and Signedness" below. Division by a variable is usually not synthesisable to anything you want; division by a constant power of two becomes a shift. The FP adder needs no divider.

Shifts come in four flavours, and only one has a subtlety:

| Operator | Name | Fill |
|---|---|---|
| `<<` | logical left | zeros |
| `>>` | logical right | zeros |
| `<<<` | arithmetic left | zeros — identical in effect to `<<` |
| `>>>` | arithmetic right | **the sign bit, but only if the left operand is signed** |

Verified with `sa = -8` declared signed and `uhi = 8'b1000_0000` declared unsigned:

```
-- shifts, sa = -8 signed, uhi = 8'b1000_0000 unsigned
  01111100	sa >> 1
  11111100	sa >>> 1
  01000000	uhi >>> 1
  11000000	$signed(uhi) >>> 1
```

> **Trap.** `>>>` on an **unsigned** operand is not an error, is not a warning, and is not an arithmetic shift. It quietly behaves as `>>`. Whether you get sign extension depends on the *declaration* of the operand, never on the operator you typed. `uhi >>> 1` and `$signed(uhi) >>> 1` are the same operator on the same bits and give different answers.

Two more rules about shifts that will matter enormously in "Width and Signedness" below: the **right** operand of a shift is always **self-determined** and always treated as **unsigned** — so a negative shift count is a very large positive one — and the **left** operand is **context-determined**.

The conditional operator `cond ? a : b` is a 2:1 multiplexer, and nesting it builds a priority mux chain. Its selector is self-determined and reduced to a truth value; the two arms are context-determined together with the result. The `x` behaviour, which you saw in `tb_mux2.v` above, is the bitwise merge rather than blanket unknown.

### Concatenation and replication

`{a, b, c}` joins vectors left to right, most significant first, and its width is the sum of the operand widths. `{n{expr}}` repeats an expression `n` times, with `n` a constant.

```
-- concatenation and replication
  10100101  {4'hA, 4'h5}
  00100010  {2{4'b0010}}
  101010  {3{2'b10}}
```

`{{4{s}}, x}` is the idiomatic sign extension chapter 1 promised you in "Two's complement" — replicate the sign bit four times, then the value.

Two properties of `{}` are load-bearing and easy to forget. First, **every concatenation operand is self-determined**, which has consequences severe enough that "Width and Signedness" below opens with them; a direct corollary is that an unsized literal cannot appear inside braces at all, because it has no definite width. Second, a concatenation is a legal **left-hand side**:

```verilog
assign {cout, sum} = a + b + cin;
```

which is the single most useful line in this chapter and the reason `adder_ansi` is only one statement long.

That is five of the six operator families. The sixth — the **reduction** operators, which collapse a whole vector down to a single bit — gets a section of its own, because one of them turns out to be a piece of the floating point adder.

## Reduction Operators and the Sticky Bit

This is the one place in the chapter where the floating point payload arrives early. If the rounding rule in the callout below does not land on first reading, take the reduction OR and the module that follows it and move on — chapter 7 is where IEEE 754 is defined and chapter 8 is where the rounding gets taught properly. Do read to the end of the section anyway: its last two pages are about `localparam` widths and elaboration-time checks, which are core Verilog and are referred back to later, not floating point.

A reduction operator takes **one** operand and returns **one** bit, by applying the operator across every bit of the vector. There are six: `&a`, `~&a`, `|a`, `~|a`, `^a`, `~^a`.

```
-- reduction operators on a = 10110010
  0  &a   (all ones?)
  1  |a   (any one?)
  0  ^a   (odd parity?)
  1  ~&a
  0  ~|a  (is a zero?)
  1  ~^a
-- zero detect on a = 00000000
  0  |a  on all-zeros
  1  ~|a on all-zeros
```

Read them as questions rather than as operators and they become obvious. `&a` asks *are all the bits one?* `|a` asks *is any bit one?* — which makes `~|a` the standard **zero detect**. `^a` is **parity**: one if an odd number of bits are set.

`x` propagates through reductions *selectively*, and the selectivity is exactly what you would want:

```
-- x propagates through reductions selectively
  1  |a  with one x, but a 1 elsewhere
  0  &a  with one x, but a 0 elsewhere
  x  ^a  with one x  (parity cannot resolve)
  x  |a  when the x is the only candidate
```

An OR that already found a one does not care what the unknown bit is. An OR whose only candidate is unknown must answer unknown. Parity can never resolve, because flipping one bit flips the answer.

Now the reason reduction operators get a section of their own in a book about floating point.

> **Seed for chapter 8.** A reduction OR is how you compute a sticky bit — but only over the *right* range, and getting that range wrong is the classic way to build a floating point unit that cannot round. When you right-shift a significand to align it with a larger exponent, the bits that fall off the end are not garbage to be discarded — chapter 1's "The barrel shifter" warned you about this. Three quantities have to survive the shift, and they are **not** interchangeable. Counting down from the first bit shifted out: the **guard** bit `G` is that first position, the **round** bit `R` is the second, and the **sticky** bit `S` is the reduction OR of *everything strictly below the round bit*. Guard and round are not part of sticky.
>
> They are kept apart because round-to-nearest-even has to separate three cases. `G = 0` is below a tie: round down. `G = 1` with `R | S = 1` is above a tie: round up. `G = 1, R = 0, S = 0` is an **exact tie**, and the tie is broken by the least significant bit of the *kept* significand — round up only when that bit is 1, so the stored result ends even. Fold all three into a single "something was lost" flag and the last two cases become the same bit, which is exactly why a rounder built on one flag cannot be written at all.
>
> A right-shift of five discards `sticky_src[4:0]`, and that is where the split falls. `sticky_src` is a 24-bit `reg`; the transcript prints it in hex and then prints its low byte again in binary, because the whole point is which *bit* sits where:
>
> ```
> -- guard, round and sticky for a right-shift of 5
>    sticky_src = 24'h000010   bits [7:0] = 8'b00010000
>   1  sticky_src[4]     guard
>   0  sticky_src[3]     round
>   0  |sticky_src[2:0]  sticky
>    sticky_src = 24'h000011   bits [7:0] = 8'b00010001
>   1  sticky_src[4]     guard
>   0  sticky_src[3]     round
>   1  |sticky_src[2:0]  sticky
> ```
>
> Read the binary field right to left, counting from bit 0. In both values the guard bit at position 4 is the `1`, and the round bit at position 3 is the `0` immediately to its right. The two mantissas differ only in bit 0, and both lose a 1 to the shift. The first is an exact tie; the second is above one. Only a sticky bit that excludes guard and round can tell them apart.

That structure is small enough to build right now. One piece of syntax first, because the module uses it three times: a **net declaration assignment** puts a net's declaration and its single driver on one line, so `wire nda = a & b;` is exactly `wire nda; assign nda = a & b;`. It is allowed once per net, and in a wide datapath keeping the declaration beside the expression that drives it is a real readability win.

`align_sticky.v` is that alignment shifter, with guard, round and sticky brought out as three separate ports:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Alignment right-shift with guard, round and sticky — the shape chapter 8 needs.
//
// The mantissa goes in the TOP W bits of a (2W+2)-bit vector and is shifted
// right. Whatever leaves the top W bits lands in the fields below it instead
// of vanishing:
//
//   shifted[2W+1 : W+2]  aligned   the significand we keep
//   shifted[W+1]         guard     the FIRST bit shifted out
//   shifted[W]           round     the SECOND bit shifted out
//   shifted[W-1 : 0]     every bit shifted out BELOW the round bit
//
// `sticky' is the reduction OR of that last field ONLY. Guard and round are
// deliberately NOT folded into it, because round-to-nearest-even has to tell
// an exact tie (g=1, r=0, s=0 — break it on the LSB of `aligned') from a value
// just above a tie (g=1, r|s=1 — round up) from a value below a tie (g=0 —
// round down). A single "something was lost" flag cannot make that
// distinction, and a rounder built on one is wrong.
//
// Shift amounts at or beyond W+2 saturate to W+2. That is not a shortcut:
// once the whole mantissa has passed below the round position, shifting
// further leaves `aligned', `guard' and `round' all zero and `sticky' at
// |mant, so nothing can change again.
//
// PRECONDITION: SHW must be wide enough to express W+2, i.e. 2**SHW > W+2.
//
// This is a DESIGN-INTENT check, not a correctness patch. The arithmetic below
// is right for every parameter pair, including the ones the check rejects: a
// too-narrow `shamt' cannot reach the saturation threshold in the first place,
// so the saturating arm is simply unreachable and the plain shift is already
// correct. What a too-narrow SHW does mean is that NO value of `shamt' can
// command the full W+2 alignment shift -- so whatever computes the exponent
// difference upstream is too narrow too, and will wrap before it ever gets
// here. The generate-if below turns that into an ELABORATION error, which is
// the cheapest place to find it.
module align_sticky #(parameter W = 24, parameter SHW = 5)
  (input  wire [W-1:0]   mant,
   input  wire [SHW-1:0] shamt,
   output wire [W-1:0]   aligned,
   output wire           guard,
   output wire           round,
   output wire           sticky);

  localparam [31:0] SH_MAX = W + 2;

  // Write the width of the 1 down too: an unsized `1' is 32 bits, so `1 << SHW'
  // wraps to 0 at SHW >= 32 and would fire this check on a perfectly good
  // parameter pair. SHW >= 32 is excluded first so the shift is never that wide.
  if (SHW < 32 && (32'd1 << SHW) <= SH_MAX)
    $fatal(1, "align_sticky: SHW is too narrow to express W+2; need 2**SHW > W+2");

  // SH_MAX is a full 32-bit localparam, so `shamt > SH_MAX' is compared at 32
  // bits and the saturation constant cannot be truncated by the comparison.
  // THAT is what makes the saturation correct; narrow SH_MAX to [SHW-1:0] and
  // at W=32, SHW=5 it becomes 32'd34 & 5'h1F = 5'd2 and every shift saturates
  // to 2. The one narrowing left, SH_MAX[SHW-1:0], is written down on purpose
  // and is a no-op: that arm is reachable only when 2**SHW-1 > W+2, and then
  // SH_MAX already fits in SHW bits.
  wire [SHW-1:0]   sh      = (shamt > SH_MAX) ? SH_MAX[SHW-1:0] : shamt;
  wire [2*W+1:0]   ext     = {mant, {(W+2){1'b0}}};
  wire [2*W+1:0]   shifted = ext >> sh;

  assign aligned = shifted[2*W+1 -: W];
  assign guard   = shifted[W+1];
  assign round   = shifted[W];
  assign sticky  = |shifted[W-1:0];

endmodule

`default_nettype wire
```

`tb_align_sticky.v` checks every representable shift amount against eight mantissas at `W=24` and four more at `W=32`, comparing all four outputs against a reference computed by index arithmetic rather than by shifting. It passes, and these printed cases are the whole argument for the three-way split:

```
-- alignment right-shift: guard, round and sticky kept separate
  mant=000010 >> 0 -> aligned=000010 g=0 r=0 s=0   n=0: nothing shifted out
  mant=000010 >> 5 -> aligned=000000 g=1 r=0 s=0   exact tie     -> break on the LSB of aligned
  mant=000018 >> 5 -> aligned=000000 g=1 r=1 s=0   above the tie -> round up
  mant=000011 >> 5 -> aligned=000000 g=1 r=0 s=1   above the tie -> round up
  mant=00000f >> 5 -> aligned=000000 g=0 r=1 s=1   below the tie -> round down
-- the second parameter pair, W=32 SHW=6
  mant=000000ff >> 8 -> aligned=00000000 g=1 r=1 s=1
PASS tb_align_sticky (8 mantissas x 32 shifts at W=24, 4 x 64 at W=32)
```

Read the four `>> 5` rows together. All four produce `aligned=000000`, and all four lost at least one `1` to the shift — so a module that reported only "did anything fall off" would emit the identical answer for every one of them. They nevertheless demand three different rounding decisions, and the guard, round and sticky bits are what separate them. This is the reason the module has three one-bit outputs instead of one.

Note also what the module does *not* do: it never shifts `mant` directly. It shifts a wider vector with `mant` in the top `W` bits, so the departing bits land somewhere they can still be examined. The vector is `2W+2` bits rather than `2W` because the guard and round positions have to sit *below* the kept significand and *above* the sticky field, and at the maximum useful shift of `W+2` the whole mantissa has to fit underneath both of them.

That `W+2` is a precondition, not a detail, and two different things in the module attend to it. They are worth telling apart, because only one of them is about getting the right answer.

The one that is about correctness is a width, written down on purpose. `SH_MAX` is declared `localparam [31:0]`, so `shamt > SH_MAX` is compared at 32 bits and the saturation constant cannot be truncated by the comparison. Declare it `localparam [SHW-1:0]` instead and at `W=32, SHW=5` it becomes `32'd34 & 5'h1F`, which is `5'd2`: every shift of three or more silently saturates to two, so a significand that needed moving twenty places moves two. Same logic, same ports, one narrower declaration, and the module is broken. That is the lesson of "Width and Signedness: The Rules That Will Break Your Adder" arriving early.

The `if` is the other thing, and it enforces a **design contract** rather than a correctness property. Be clear about which, because a check defended by the wrong reason is a check somebody deletes later. `shamt` is only `SHW` bits wide, so if `2**SHW` is not greater than `W+2`, no value that port can hold will ever command the full alignment shift. The module still computes correct outputs for every shift amount such a port *can* express: the saturating arm simply becomes unreachable, and the plain shift is already right. What the parameter pair tells you is something about the rest of the design — an instance that can never fully align a significand is being fed by exponent-difference logic that is too narrow, and that bug lives upstream where this module cannot see it. `bad_align_shw.v` instantiates the module at `W=32, SHW=5`, a plausible-looking padded significand for which `2**5 = 32` is *not* greater than `W+2 = 34`. It does not compile:

```
FATAL: align_sticky.v:52: align_sticky: SHW is too narrow to express W+2; need 2**SHW > W+2
       During elaboration  Scope: genblk1
1 error(s) during elaboration.
```

That is worth pausing on, because it lands in the phase that matters. A module-level `if` with a constant condition is a **generate** construct, so it is resolved during *elaboration*, alongside parameter resolution and vector sizing — not at run time. An `initial` block containing the same test would compile clean and only complain once `vvp` was running. Writing the precondition as a generate-if turns "this instance can never do the whole job" into a build failure, which is the earliest phase that can catch it.

## Width and Signedness: The Rules That Will Break Your Adder

Here are two lines. `a` and `b` are four-bit registers holding `4'hF` and `4'h1`. `r8` is eight bits.

```verilog
r8 = a + b;
r8 = {a + b};
```

The first gives 16. The second gives 0. The subexpression is identical, the target is identical, and the only difference is a pair of braces. This section explains why, and it is the most important section in the chapter, because the same mechanism is what silently destroys a mantissa.

### The two-pass width algorithm

Verilog sizes an expression in two passes.

**Pass 1, bottom-up: compute the expression's own width.** For most binary operators the width is `max(width(left), width(right))`. For an assignment, the target's width joins that maximum. For a shift it is the left operand's width. For a concatenation it is the sum of the operand widths.

**Pass 2, top-down: push that width back down into every operand that is allowed to grow**, extending each one according to its *own* signedness.

The operands allowed to grow are called **context-determined**. The ones that are not are **self-determined**: they are evaluated at their own natural width, in isolation, and only then does their result participate.

| Context-determined (grow to the expression width) | Self-determined (fixed at their own width) |
|---|---|
| operands of `+ - * / % & \| ^ ~^` | every operand of `{}` and `{n{}}` |
| the operand of **unary** `+ - ~` | the operand of **unary** `!` |
| both arms of `?:` | the selector of `?:` |
| the **left** operand of `<< >> <<< >>>` | the **right** operand of a shift |
| both operands of `== != === !== < <= > >=`, **relative to each other** | the 1-bit result of a comparison |
| the right-hand side of an assignment, joined with the left-hand side's width | operands of `&&`, `\|\|`, and all reduction operators |

That table is the whole rule. Everything below is it happening to you.

`tb_widths.v` runs each case and checks the predicted answer. Its real output:

```
a = f, b = 1, so a + b needs 5 bits
  00010000   r8 = a + b
  00000000   r4 = a + b   (truncated)
  00000000   r8 = {a + b}
  00000000   r8 = {1'b0, a + b}
  00000000   r8 = {2{a + b}}
  00010000   r8 = {4'b0,a}+{4'b0,b}
  00010000   r8 = a ? (a+b) : 8'hFF
  11101111   r8 = ~(a + b)
  00000001   r8 = {7'b0, !(a + b)}
```

Take these one at a time.

**`r8 = a + b`** works because the assignment target joins the maximum: the expression is eight bits wide, both operands are widened to eight bits, and the add is performed at eight bits. The carry has room.

**`r4 = a + b`** loses the carry, because the expression is only four bits wide. Nothing is wrong with the addition; there is simply nowhere for the fifth bit to go.

**`r8 = {a + b}`** is the one that hurts. Concatenation operands are self-determined, so `a + b` is evaluated at *four* bits — the target's eight bits never reach it. The result is `4'b0000`, which is then placed in the concatenation, which is then assigned to `r8`. The braces changed the arithmetic.

**`r8 = {1'b0, a + b}`** does not help. Adding a zero bit in front makes the concatenation five bits wide, but it does not make `a + b` five bits wide; each operand is still sized on its own.

**`r8 = {4'b0, a} + {4'b0, b}`** is the fix. Widen each operand *explicitly*, before the operator sees them. Now the add is genuinely eight bits.

**`r8 = a ? (a+b) : 8'hFF`** works, because the arms of a conditional operator *are* context-determined. The `8'hFF` in the other arm pulled the expression to eight bits, and the addition came along.

**`r8 = ~(a + b)`** gives `11101111`, and that value is the proof that unary `~` is context-determined. The addition grew to eight bits, produced `00010000`, and *then* was inverted. Had the operand stayed at its own four bits, `~4'b0000` would be `4'b1111` and the answer would read `00001111`.

**`r8 = {7'b0, !(a + b)}`** is the exception in the same family. Unary `!` is self-determined and always returns one bit, so `a + b` was evaluated at four bits, came out zero, and `!0` gave 1. The two unary operators one keystroke apart sit in opposite columns of the table.

Shifts show the asymmetry directly:

```
  0001  r16 = 16'h0001 << (a + b)        (a+b evaluated at 4 bits = 0)
  0000  r16 = 16'h0001 << ({1'b0,a}+{1'b0,b})  (shift count really is 16)
```

The shift count is self-determined, so `a + b` is computed at four bits, yields zero, and the shift does nothing. Widen it and the count is genuinely 16, which shifts the one straight out of a sixteen-bit vector.

And comparisons size against **each other**, which produces a result that is genuinely startling the first time:

```
  1   ((a + b) == 5'd16)   -- the 5-bit literal widened the add
  1   ((a + b) == 4'd0)    -- the 4-bit literal did not
```

The *literal on the right* decided whether the addition on the left overflowed. Change `5'd16` to `4'd0` and the same expression compares equal to a different number. There is no way to look at `a + b` in isolation and know how wide it is.

### The folklore about `1 << 40`, corrected

You will read in a lot of places that `1 << 40` is always zero in Verilog because `1` is a 32-bit literal. That is not the rule, and believing it will teach you the wrong model. Verified, all four cases:

```
  0000010000000000  big = 1 << 40            (64-bit context: correct)
  00000000          n32 = 1 << 40            (32-bit context: lost)
  0000000000000000  big = {1'b1 << 40}       (self-determined: lost)
  0000000000000000  big = {32'd1 << 40}      (self-determined: lost)
```

Assigned to a 64-bit target, `1 << 40` gives the right answer, because the left operand of a shift is context-determined and the assignment widened it to 64 bits before shifting. Assigned to a 32-bit target it is lost. Put it inside braces and it is lost regardless of the target, because concatenation operands are self-determined.

Learn the real rule — context-determined versus self-determined — and all four cases follow. Learn the folk rule and you will be wrong half the time in each direction.

### The silent truncation, and why you cannot trust the compiler here

Everything above follows from a rule you can now apply. This next part is worse, because there is no diagnostic at all.

```
  1111        r4 = 8'hFF               (silent: no diagnostic at all)
```

Assigning a wide value to a narrow target drops the high bits, and under `-Wall` Icarus emits **nothing**. Compare that with the too-wide *literal* from "Writing Numbers Down" above, which produced `warning: Numeric constant truncated to 4 bits` even without `-Wall`. Only constants written directly as literals get that warning; a truncating assignment gets silence.

> **Trap.** `-Wall` does **not** warn on truncating assignment. It also does not warn on signed/unsigned contamination, on self-determined truncation inside a concatenation, or on multiple drivers on a net. Those four are the most damaging width and type errors in the language, and the compiler will tell you about none of them. Distrust the absence of warnings. The only defence is to write the width of every intermediate signal down on purpose and check it against the arithmetic you intended.

Here is the shape of the bug in the place it will actually bite you. `mant_add.v` does it correctly:

```verilog
module mant_add #(parameter W = 24)
  (input  wire [W-1:0] a,
   input  wire [W-1:0] b,
   output wire [W-1:0] sum,
   output wire         carry);

  assign {carry, sum} = a + b;

endmodule
```

and `bad_mant_add.v` does it the way that looks more natural and is wrong:

```verilog
  assign sum   = a + b;
  assign carry = (a + b) >> W;
```

The first line truncates: `sum` is 24 bits, so the addition is evaluated at 24 bits and the carry is gone before the second line can see it. The second line is worse. `carry` is *one bit*, so `(a + b) >> W` is evaluated in a **one-bit** context: the addition is performed at one bit, and shifting a one-bit value right by 24 gives zero, always. That output is not merely wrong on some inputs. It is a constant.

Both modules on the same stimulus:

```
a=ffffff b=000001
  correct : carry=1 sum=000000   (25-bit value 1000000)
  broken  : carry=0 sum=000000   (25-bit value 0000000)
PASS tb_mant_add (mant_add correct on 501 cases; bad_mant_add carry stuck at 0)
```

Five hundred random pairs, and `bad_mant_add` never once reported a carry. Not a warning was printed at compile time.

The procedural spelling of the same bug is, if anything, more instructive, because Icarus notices something is odd without noticing what. `bad_carry_always.v`:

```verilog
  always @(*) sum   = a + b;
  always @(*) carry = (a + b) >> 8;
```

```
bad_carry_always.v:18: warning: @* found no sensitivities so it will never trigger.
a=200 b=100 -> sum=44 carry=x
```

Icarus constant-folded `(a + b) >> 8` at one bit down to a constant, discovered the block therefore reads nothing, and warned that the `always` can never fire. `carry` stays `x` for the entire simulation. That warning is worth learning to recognise: **"@\* found no sensitivities" almost always means an expression collapsed because of a width you did not intend.**

**The fix is always the same.** Make the result wide enough first, then select from it. Either concatenate the target — `{cout, sum} = a + b + cin` — or compute into a deliberately wide intermediate and take the bit you want:

```verilog
wire [8:0] wide = a + b;      // 9 bits: the carry has somewhere to live
wire       cout = wide[8];
```

> **Seed for chapter 9.** This is the bug that will cost you the most time in the floating point adder, and it will not announce itself. A 24-bit significand addition that overflows into 25 bits, a guard/round/sticky path that needs three bits below the LSB, a normalisation shift that needs one bit above the MSB — every one of them is a place where a target one bit too narrow produces plausible results on easy inputs and wrong results on exactly the cases that matter. Write the width of every signal in the datapath down before you write the arithmetic.

### Signedness contaminates

The second half of this section is a single law, and it is worth stating in italics because everything else follows from it.

> *An expression is treated as **signed** only if **every** operand is signed. One unsigned operand makes the entire expression unsigned, and every operand is then reinterpreted as an unsigned bit pattern.*

Reinterpreted, not converted. The bits do not move; their meaning changes. `tb_signedness.v` shows what that costs, with `sa` a signed 8-bit register holding −8:

```
-- division and remainder, sa = -8, sb = 3, ua2 = 2 (unsigned)
  -2	sa / sb
  124	sa / ua2
  -4	sa / $signed(ua2)
  -2	sa % sb
  2	8 % -3
```

`sa / sb` is −8 divided by 3, truncated toward zero, giving −2. Correct. `sa / ua2` is −8 divided by 2, and gives **124**, because one unsigned operand made the whole expression unsigned, so `sa`'s bit pattern `11111000` was read as 248, and 248 / 2 = 124. Cast the offending operand and you get −4 as intended.

The multiplication pair is the version to memorise, because the two spellings are one keystroke apart:

```
-- multiplication, s4 = -2 (4-bit signed)
  -4	s4 * 2
  28	s4 * 4'd2
  -4	s4 * $signed(4'd2)
```

`s4 * 2` gives −4, because a bare `2` is a *signed* 32-bit literal. `s4 * 4'd2` gives **28**, because `4'd2` is unsigned, which makes the expression unsigned, which makes `s4`'s bits `1110` read as 14, and 14 × 2 = 28. Adding the size to a literal changed the sign of the result.

Comparisons are contaminated the same way:

```
-- comparison
  0	(-8'sd1 < 8'd0)              one unsigned operand, so -1 reads as 255
  1	($signed(8'hFF) < $signed(8'h00))
```

"Is −1 less than 0" answers *no*. That is not a bug in Icarus; it is the law being applied.

And concatenation results are **always unsigned**, whatever went into them:

```
-- concatenation results are always unsigned
  00001110	r8u = {s4}
  11111110	r8u = s4
  0/1	({s4} < 0) = 0 but (s4 < 0) = 1
```

Which gives you a useful idiom in both directions: `{x}` strips signedness cheaply, and `{1'b0, x}` is the standard "widen by one and force unsigned".

The surgical fixes are `$signed(expr)` and `$unsigned(expr)`. They are system functions, they *are* synthesisable, and they change only the signedness attribute — not the width, not the bits. Verified: `$signed(8'hFF)` is −1 and `$unsigned(-8'sd1)` is 255.

> **Trap.** Chapter 1's "Two's complement" section warned you that the tool would zero-extend exactly where you meant it to replicate the sign, and here is the mechanism. `reg [7:0]` is unsigned by default; a single unsigned operand anywhere in the expression makes the whole thing unsigned; extension then follows the source expression's signedness, which is now unsigned. The two cures are the same two chapter 1 named: an explicit `$signed()` cast, or replicating the sign bit by hand as `{{4{x[3]}}, x}`.

The policy that follows, and that this guide will hold to: **keep the FP mantissa and exponent datapaths unsigned end to end.** Handle the sign as a separate explicit bit, exactly as IEEE 754 stores it. Where you genuinely need a signed quantity — the exponent difference is the obvious one — declare it `signed`, give it deliberate extra width, and cast anything unsigned that meets it. Mixed signedness inside an arithmetic datapath is not a style problem; it is a correctness problem with no compiler support.

## Wiring Things Together with `assign`

You have been using `assign` since the first listing. Now the definition, which is shorter than you expect: **whenever any operand on the right-hand side changes, the left-hand side is recomputed and updated.** Permanently. Always.

A continuous assignment is not a statement and has no position in time. Ten `assign`s in a module are ten pieces of combinational logic that all exist at once; reorder the lines and nothing changes, which is where this chapter started. The left-hand side must be a **net**, or a concatenation or part-select of nets. The right-hand side may be any expression, including a function call, and it is context-determined against the left-hand side's width — which is the source of every width bug in "Width and Signedness: The Rules That Will Break Your Adder".

The **net declaration assignment**, introduced alongside `align_sticky.v` above, is the shorthand for the common case:

```verilog
wire nda = a & b;      // exactly equivalent to: wire nda; assign nda = a & b;
```

Allowed once per net — which is precisely why it can only ever express a single driver.

### Structural composition, and when it earns its place

Sometimes the topology *is* the design, and then you want to name the parts. Verilog has gate primitives built in — no library, no import. `and nand or nor xor xnor` take one output and any number of inputs; `buf` and `not` take one input and any number of outputs; `bufif0`/`bufif1`/`notif0`/`notif1` are the three-state drivers. **The output is always the first port.** Instance names are optional for primitives; name them anyway.

Here is chapter 1's full adder, spelled as gates rather than as arithmetic — `full_adder.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Chapter 1's full adder, written structurally out of gate primitives.
// Gate primitives take the OUTPUT as their first port.
//   sum  = a XOR b XOR cin
//   cout = a.b + (a XOR b).cin
module full_adder
  (input  wire a,
   input  wire b,
   input  wire cin,
   output wire sum,
   output wire cout);

  wire ab, ab_cin, a_and_b;

  xor g_ab   (ab,      a,  b);
  xor g_sum  (sum,     ab, cin);
  and g_maj1 (a_and_b, a,  b);
  and g_maj2 (ab_cin,  ab, cin);
  or  g_cout (cout,    a_and_b, ab_cin);

endmodule

`default_nettype wire
```

Compare it against the equations from chapter 1's "Half adder and full adder": `S = A ⊕ B ⊕ Cin` and `Cout = A·B + (A ⊕ B)·Cin`. Five gate instances, one per term. And now chapter 1's "Ripple-carry, and why it is not enough", made physical — `ripple4.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Chapter 1's ripple-carry adder: four full adders, carry chained.
// The topology IS the point here, which is why this one is structural.
// `c' holds the internal carries; c[0] is the incoming carry and c[4] is
// the carry-out.
module ripple4
  (input  wire [3:0] a,
   input  wire [3:0] b,
   input  wire       cin,
   output wire [3:0] sum,
   output wire       cout);

  wire [4:0] c;

  assign c[0] = cin;
  assign cout = c[4];

  full_adder fa0 (.a(a[0]), .b(b[0]), .cin(c[0]), .sum(sum[0]), .cout(c[1]));
  full_adder fa1 (.a(a[1]), .b(b[1]), .cin(c[1]), .sum(sum[1]), .cout(c[2]));
  full_adder fa2 (.a(a[2]), .b(b[2]), .cin(c[2]), .sum(sum[2]), .cout(c[3]));
  full_adder fa3 (.a(a[3]), .b(b[3]), .cin(c[3]), .sum(sum[3]), .cout(c[4]));

endmodule

`default_nettype wire
```

The carry chain is right there in the source: `c[1]` out of `fa0` and into `fa1`. You can *see* the O(n) dependency chapter 1 said was unaffordable in a significand adder. `tb_ripple4.v` checks it against `adder_ansi` over all 512 input combinations and they agree exactly:

```
PASS tb_ripple4 (512 exhaustive cases, structural == dataflow)
```

Two descriptions, one circuit — but not one *cost*. The structural version makes the carry chain visible; the dataflow version hands the problem to the tool, which is free to build a carry-lookahead or a parallel-prefix adder instead. That is the trade, and it is why the FP adder will be dataflow: you want the tool's adder, not yours.

> **Trap.** Structural style is right when you are describing a topology you have already designed, and wrong for anything arithmetic. A 24-bit adder written as gate instances is not a lesson, it is a punishment — and it forbids the synthesiser from choosing a better structure.

Two remaining facts about nets, both already visible in `tb_drivers.v`. **Two `assign`s to the same wire are two drivers**, which resolve to `x` where they disagree and go unwarned by Icarus. And `wand`/`wor` replace the resolution function rather than producing `x`, which is how open-drain buses are modelled. A `reg` driven from two different `always` blocks is the same class of bug *without* the `x` — it becomes a race with a non-deterministic winner, and that is chapter 3's territory.

Drive strengths, the switch-level primitives, `pullup`/`pulldown` and user-defined primitives all exist and all simulate in Icarus. They model buses and standard cells; you will not write one.

## A First Look at Procedural Blocks

Some hardware is awkward to write as one expression. A priority chain, a case decode, a leading-zero count — you want `if` and `case` and `for`. Verilog gives you them inside **procedural blocks**, and this section takes you exactly far enough to *read* such code. The rules that govern writing it correctly are chapter 3's, and this section will hand them over explicitly rather than half-teach them.

There are two kinds of block.

`initial begin ... end` runs **once**, starting at time zero. It is testbench machinery — not synthesisable, apart from FPGA memory initialisation — and every stimulus block in this chapter is one.

`always <event-control> begin ... end` is an **infinite process**: it runs to the end, then immediately waits for its event control to fire again. Both kinds are concurrent with each other and with every `assign`, and multiple `initial` blocks all start at time zero together.

> **Trap.** `always` is one of the worst names in the language. It does not mean "loop" and it does not mean "continuously". It means *this process restarts whenever its event control fires*. It describes a piece of hardware that reacts.

For this chapter you need exactly one form: `always @(*)`, the implicit sensitivity list from Verilog-2001, which means "re-evaluate whenever anything read inside this block changes". That is the definition of combinational logic, and `comb_max.v` above is the canonical shape. The other form, `always @(posedge clk)`, builds flip-flops and belongs to chapter 3.

Anything assigned inside a procedural block must be a variable — `reg`, `integer`, `real` or `time`. Assigning a `wire` procedurally is an error: `'w' is not a valid l-value for a procedural assignment`. That is the whole origin of the `wire`/`reg` port rule from earlier.

> **Icarus reality.** An `always` block with no event control and no delay is a zero-delay infinite loop, and Icarus refuses it at compile time rather than hanging: `error: always process does not have any delay. : A runtime infinite loop will occur.` It also warns when `@(*)` finds nothing to be sensitive to — `warning: @* found no sensitivities so it will never trigger` — which, as "Width and Signedness" showed, usually means an expression constant-folded because of a width you did not intend.

### `begin`/`end`, and a bug you have seen before

`if`, `else`, `for` and each `case` item take exactly **one** statement. Two statements need `begin`/`end`. And Verilog has no significant whitespace whatsoever — indentation is a lie the compiler never reads. `bad_begin_end.v`:

```verilog
    a = 1'b0;

    if (a)
      b = 1'b1;
      c = 1'b1;    // NOT part of the if
```

```
a=0 b=x c=1
```

`c` was assigned although the condition was false, and `b` was never touched. This is the Verilog analogue of the goto-fail bug, and the defence is mechanical: **always write `begin`/`end`, even around a single statement.** Named blocks — `begin : bitloop ... end` — additionally create a scope, allow local declarations, and give generate instances stable hierarchical names you can find in a waveform viewer.

### `if`, `case`, `casez`, and never `casex`

`if`/`else` chains describe a **priority** structure; `case` describes a **parallel** one. That distinction shows up in area and timing, and it matters for the FP adder, whose special-case handling (NaN beats infinity beats zero beats normal) is naturally a priority chain.

`case` matching is exact and four-state, like `===`: an `x` in the selector matches only an `x` in an item. Always write a `default` — without one, an unmatched selector leaves the variable unassigned, which in a combinational block infers the latch chapter 1's "Taming Time With a Clock" warned you about.

`casez` treats `z` and `?` **in the case items** as don't-cares, with `?` the readable spelling. It is the right tool for priority encoders and leading-one detection — exactly what an FP normaliser needs.

`casex` treats `x` **and** `z` as don't-cares on **both** sides, including in the selector, and that is a disaster. `bad_casex.v` runs the same four selectors through both:

```
  sel=1000 : casex -> 1xxx	casez -> 1???
  sel=0100 : casex -> 01xx	casez -> 01??
  sel=0010 : casex -> default	casez -> default
  sel=x000 : casex -> 1xxx	casez -> default
```

One unknown bit in the selector — from an uninitialised register, a reset glitch, an undriven net — and `casex` silently matched the **first** item. The design looks like it is working. It also destroys `x` propagation, which is the main early-bug detector you have.

> **Trap.** **Never write `casex`.** Use `casez` when you need don't-cares in the items, or `==?` when you need a masked compare. Note that `casez` is safer, not perfectly safe: a `z` in the *selector* still wildcard-matches. In practice internal signals rarely carry `z`, so the residual risk is small.

### `for` loops are unrolled hardware

This is the point that most reliably breaks a programmer's intuition. A `for` loop with constant bounds, inside a combinational `always` block or a `function`, becomes **N parallel copies of the logic** in hardware. It is a code-generation device rather than iteration: ten iterations means ten copies, all existing simultaneously. In simulation the loop really does loop — Icarus simulates, it does not synthesise — but it does so in **zero simulated time**, which is what makes the hardware picture the right one to carry.

Here is `lzc8.v` — chapter 1's priority encoder, written as a loop:

```verilog
`timescale 1ns/1ps
`default_nettype none

// Leading-zero count over 8 bits: chapter 1's priority encoder, spelled as a
// loop. In hardware the loop becomes eight parallel comparisons, so it costs
// eight copies of the logic; in simulation it iterates in zero elapsed time.
// An all-zero input returns 8, which is why the result needs 4 bits.
module lzc8
  (input  wire [7:0] x,
   output wire [3:0] count);

  function [3:0] lzc;
    input [7:0] v;
    integer j;
    begin
      lzc = 4'd8;
      for (j = 7; j >= 0; j = j - 1)
        if (v[j] && lzc == 4'd8)
          lzc = 4'd7 - j[3:0];
    end
  endfunction

  assign count = lzc(x);

endmodule

`default_nettype wire
```

`tb_lzc8.v` checks all 256 inputs against an independent golden model and passes:

```
lzc8(00110110) = 2
lzc8(00000001) = 7
lzc8(00000000) = 8
```

`tb_procedural.v` makes the "no time passes" claim measurable, and contrasts it with a loop whose body contains a delay:

```
-- a for loop inside a function is unrolled, not iterated
  popcount8(00110110) = 4, computed between t=0.000 and t=0.000
-- a loop whose body has a delay does consume time
  loop iteration 0 at t=1.000
  loop iteration 1 at t=2.000
  loop iteration 2 at t=3.000
```

An eight-iteration population count completed between t=0 and t=0. The three-iteration testbench loop took three nanoseconds — because of the `#1` in its body, not because of the loop. **Delays make time pass; loops do not.**

> **Seed for chapter 9.** `lzc8` is the leading-zero counter from chapter 1's "The encoder, and the priority encoder". After an effective subtraction of two nearly equal floats, the significand can have many leading zeros, and normalisation must left-shift by exactly that count while decrementing the exponent by the same amount. The chain is priority encoder → shift amount → barrel shifter → exponent adjust, and you now have Verilog for the first and the third: this function, and `[base +: width]`.

The corollary that costs money: a loop of a thousand iterations is a thousand copies of hardware. Loop bounds must be compile-time constant, and you should think of the bound as an area figure.

There is a structural cousin, `generate for`, which replicates *instances and continuous assignments* rather than statements. It must use a `genvar` — an elaboration-time index — not an `integer`; using the wrong one gives `error: genvar is missing for generate "loop" variable 'i'`. Use `integer` for procedural loops, `genvar` for generate loops, and name the generate block so the instances get stable hierarchical names.

### `function` and `task`

|  | `function` | `task` |
|---|---|---|
| Returns a value | yes, by assigning to its own name | no — use `output` arguments |
| Arguments | at least one input, no outputs (classic Verilog) | any mix, or none |
| Timing controls (`#`, `@`, `wait`) | **forbidden** | allowed |
| Executes in | zero simulation time | may consume time |
| Usable in an expression | yes | no — it is a statement |
| Synthesisable | yes, as combinational logic | only without timing controls |

A `function` is the right tool for reusable combinational blocks in the FP adder: leading-zero count, rounding decision, special-case classification. Declare the return width explicitly — `function [4:0] lzc24;`.

`function automatic` and `task automatic` allocate arguments and locals per call on a stack, instead of the Verilog-1995 default of one static shared copy. You need `automatic` for concurrent invocation from multiple processes, and for recursion to be *reliable*.

That second word is doing real work, and the honest version of this claim is more interesting than the folklore. Without `automatic` there is one static copy of the arguments **and of the return variable**, shared by every invocation — so whether a recursive function works comes down to the order in which the operands of the recursive expression happen to be evaluated. `bad_recursion.v` writes the same factorial four ways and runs them:

```
-- recursion without `automatic' is evaluation-order dependent
  static    fact = n * fact(n-1) : fact(5) = 120
  static    fact = fact(n-1) * n : fact(5) = 1
  automatic fact = n * fact(n-1) : fact(5) = 120
  automatic fact = fact(n-1) * n : fact(5) = 120
```

The two static versions differ by nothing but the order of the multiplication's operands. With `n` written first, Icarus reads it before the recursive call overwrites the shared storage, and the answer survives; with the call written first, the shared return variable is clobbered on the way back out and the whole thing collapses to 1. Neither ordering is *guaranteed* by anything — the first one is luck, and it is luck that another simulator, or another expression, need not repeat.

So do not reason about which spelling survives. Straight-line combinational helpers do not need `automatic`, and it costs nothing, so write it on every `function` and `task` you declare.

> **Seed for chapter 3.** Everything about *how* to write these blocks correctly is next. Chapter 3 owns the difference between blocking `=` and non-blocking `<=`, why `<=` belongs in clocked blocks and `=` in combinational ones, `always @(posedge clk)` and reset styles, latch inference in full — this chapter has named only the `case`-without-`default` version — and the event-region scheduling model that makes the rules work rather than merely being conventions. This chapter has used only `always @(*)` with `=`, and `initial` in testbenches, on purpose. Why it must be `=` here and `<=` there is the next chapter's first job.

## The Toolchain: Directives, System Tasks, and What Icarus Really Supports

Two of the lines at the top of every listing in this chapter start with a backtick. They are **compiler directives**: handled by the preprocessor, before parsing, and — this is the part that surprises people — their effect is **global and file-ordered**. A `` `define `` in one file is visible in every file compiled after it on the same `iverilog` command line. There is no per-translation-unit scoping the way C has it.

The ones you need:

- **`` `timescale <unit>/<precision> ``** — two arguments doing two different jobs. The **unit** is what a bare `#1` means. The **precision** is the granularity to which all delays are rounded, and the tick size of the simulation clock; the simulator's global resolution is the *smallest* precision anywhere in the design. Both must be `1`, `10` or `100` followed by `s ms us ns ps fs`, and the precision must not be coarser than the unit. Use `` `timescale 1ns/1ps `` at the top of every file. A design with no timescale anywhere runs with a one-second unit and produces confusing output like `$finish called at 3 (1s)`.
- **`` `default_nettype none ``** at the top of every file and `` `default_nettype wire `` at the bottom, for the reasons established earlier.
- **`` `define ``, `` `undef ``, `` `ifdef ``, `` `ifndef ``, `` `elsif ``, `` `else ``, `` `endif ``** — text substitution and conditional compilation. Use a leading backtick at the point of use: `` `WIDTH ``. Define from the command line with `-DDEBUG`. Parenthesise macro arguments and bodies exactly as in C.
- **`` `include "defs.vh" ``** — textual inclusion, with `-I dir` for the search path. There are no include guards in Verilog; write them yourself with `` `ifndef ``.

> **Trap.** Prefer `parameter` and `localparam` for anything numeric. Macros are untyped, unscoped, and leak across every file compiled after them. Reserve `` `define `` for conditional-compilation switches.

### System tasks and functions

Everything with a `$` prefix is a system task or function — the simulation-control half of the language. The ones you will use constantly:

`$display` prints with a newline; `$write` without one. Format specifiers behave like C's with additions:

```
  dec=165 hex=a5 oct=245 bin=10100101 char=A str=hi
```

`%d` pads to the operand's width, so use `%0d` almost always. `%b`, `%h`, `%o` zero-pad to the operand width. `%t` prints time as configured by `$timeformat`. `%m` prints the current hierarchical scope and takes no argument. `%s` prints a vector as characters — and remember from earlier that the zero padding shows up as leading spaces.

`$time` returns an integer **rounded to the module's time unit**; `$realtime` keeps the fraction. In a self-checking testbench print `$realtime`, or you will chase a rounding artefact:

```
  after #1.25 : $time = 1   $realtime = 1.250000
```

`$clog2(n)` is the ceiling of log2 — "how many bits to index n things". Verified exactly:

```
  $clog2(1)=0 $clog2(2)=1 $clog2(3)=2 $clog2(8)=3 $clog2(9)=4 $clog2(0)=0
```

so `$clog2(8)` is 3 and `$clog2(9)` is 4, and `$clog2(0)` is defined to be 0 rather than an error. The standard idiom is `localparam AW = $clog2(DEPTH);`. `$bits(x)` gives a width, and is the quickest way to check that a signal is as wide as you think.

`$signed` and `$unsigned` reinterpret signedness without changing width or bits. `$random` returns a **signed** 32-bit value, and this catches everybody:

```
-- $random is SIGNED, so $random % N is negative half the time
  $random % 16 = 4	{$random} % 16 = 1
  $random % 16 = -7	{$random} % 16 = 3
  $random % 16 = 13	{$random} % 16 = 13
  $random % 16 = -11	{$random} % 16 = 2
  $random % 16 = 1	{$random} % 16 = 13
  $random % 16 = 6	{$random} % 16 = 13
```

Two of those six are negative. The fixes are `{$random} % N` — concatenation strips signedness, as you now know — or `$urandom_range(0, N-1)`. `$random` is seeded identically on every run, which is exactly what you want for reproducible regressions.

Waveform dumping (`$dumpfile` and `$dumpvars`) and memory loading (`$readmemh` and `$readmemb`) all work in Icarus 13.0, and all four belong to chapter 4, which owns testbenches and waveform tooling.

The **severity tasks** are the ones that decide whether your build is honest. Verified behaviour and exit codes:

- `$info`, `$warning`, `$error` — print `INFO:` / `WARNING:` / `ERROR:` with file, line, time and scope, then **continue**. The process exit code stays **0**.
- `$fatal(code, "msg", args)` — prints `FATAL:` with the same detail and terminates immediately with exit code **1**.
- `$finish` — ends the simulation with exit code 0. `$stop` drops to the interactive `vvp>` prompt; with stdin closed it prints `** Continue **` and runs on anyway.

```
INFO: tb_systasks.v:80: this is $info
      Time: 1250  Scope: tb_systasks
WARNING: tb_systasks.v:81: this is $warning
         Time: 1250  Scope: tb_systasks
ERROR: tb_systasks.v:82: this is $error -- note the run still exits 0
       Time: 1250  Scope: tb_systasks
PASS tb_systasks
```

That run printed a loud `ERROR:` and exited 0. A continuous-integration job would call it green. **A testbench that must fail a build has to end in `$fatal`, or count its errors and call `$fatal` at the end.** Every testbench in this guide does the latter.

> **Icarus reality.** Icarus does **not** gate system tasks by `-g` level — verified by compiling the same file at `-g1995`, `-g2005` and `-g2012` and diffing the output. `$clog2`, `$bits`, `$error`, `$fatal` and `$urandom` behave identically at all three. What `-g` gates is **syntax**: the `'0`/`'1` fill literals, size casts, `shortreal`, and `logic`. `shortreal` is a syntax error at `-g2005` and works from `-g2005-sv`; `==?`/`!=?` are accepted from `-g2005`.

> **Icarus reality.** An unrecognised system task is **not** a compile-time error, and getting this wrong will cost you a CI job. `iverilog` accepts the file and exits 0. The diagnostic comes from `vvp` when it *loads* the program, before time advances:
>
> ```
> $ iverilog -g2012 -Wall -o one.vvp one.v
> iverilog exit: 0
> $ vvp one.vvp
> one.v:4: Error: System task/function $nosuchtask() is not defined by any module.
> one.vvp: Program not runnable, 1 errors.
> vvp exit: 1
> ```
>
> The function form `$nosuchfunc(3)` behaves identically. So you can still probe support cheaply, but you have to actually run `vvp` to do it — checking that the design compiles proves nothing about whether the system task exists.

### The command line

```sh
iverilog -g2012 -Wall -o sim design.v tb.v
vvp sim
```

That is the whole invocation, and it is the one this guide uses everywhere. The rest of the flag surface — `-s`, `-I`, `-D`, `-c`, `-E`, `-t null` and `-gstrict-expr-width` — belongs to chapter 4, which owns the toolchain and the build.

One of them needs its warning here rather than there. `-t null` is often recommended as a fast syntax gate for CI, and it is a *syntax* gate and nothing more: run it on a file that calls `$nosuchtask()` and it exits 0, exactly as a full compile does. Such a job reports green on a design `vvp` refuses to load.

Source file order does not matter for finding modules — elaboration binds instances by name — but it *does* matter for macro and `` `default_nettype `` visibility.

**What `-Wall` actually turns on**, per the installed 13.0 manual page, is exactly seven warning classes: `anachronisms`, `implicit`, `macro-replacement`, `portbind`, `select-range`, `timescale`, `sensitivity-entire-array`. It does **not** include `infloop` or `sensitivity-entire-vector`; add them explicitly with `-Winfloop` if you want them.

Only two of the warnings you have seen in this chapter actually came from that set: `implicit definition of wire 'godo'` (the `implicit` class) and `Part select [35:32] is selecting after the vector v[31:0]` (`select-range`). Drop `-Wall` and both go quiet.

The other four are **ungated** — Icarus emits them whether or not you ask for warnings, and you cannot switch them off: `Port 2 (b) of module adder_ansi expects 8 bit(s), given 1`, `@* found no sensitivities so it will never trigger`, `Numeric constant truncated to 4 bits`, and — at `-g2005` only — `Using SystemVerilog 'N bit vector`, quoted back in "Writing Numbers Down".

> **Icarus reality.** The port-width warning looks as though it should belong to the `portbind` class, and it does not: `-Wno-portbind` leaves it exactly where it was. `man iverilog` describes `portbind` as warning about *unconnected* ports — a dangling input — which is a different diagnostic. This is worth knowing for the general reason rather than the specific one: warning-class names are a rough index, not a contract, and the only reliable way to learn what a switch covers is to toggle it and diff the output. That is a two-command experiment, and it is the same instinct this whole chapter is trying to build.

And the list of what `-Wall` will never tell you is the one to pin above your desk: **silent truncation on assignment to a narrower target, signed/unsigned contamination, self-determined truncation inside a concatenation, and multiple drivers on a net.** Those four are on you.

## Exercises

You have 40 working files and a harness. Use them. Each of these takes minutes, and each one fails in a way that teaches something.

**1. Round to nearest even.** `align_sticky.v` produces `guard`, `round` and `sticky`; the rounder that consumes them is four lines. Write `round_ne.v` with inputs `lsb`, `guard`, `round`, `sticky` and one output `round_up`, implementing the rule from the sticky-bit callout: round up when the discarded part exceeds half an ULP — one ULP being the weight of the last significand bit you kept, so half an ULP is exactly the guard position — and on an exact tie round up only when `lsb` is 1. Then write a testbench that checks all sixteen input combinations against a *different* formulation — treat `{guard, round, sticky}` as a three-bit magnitude and compare it with `3'b100`. The worked answer is `round_ne.v` and `tb_round_ne.v`:

```
-- round to nearest even, decided by guard/round/sticky
  lsb=0 g=0 r=1 s=1 -> round_up=0   below a tie   -> down
  lsb=0 g=1 r=0 s=0 -> round_up=0   exact tie, LSB even -> stay
  lsb=1 g=1 r=0 s=0 -> round_up=1   exact tie, LSB odd  -> up
  lsb=0 g=1 r=0 s=1 -> round_up=1   above a tie   -> up
PASS tb_round_ne (16 exhaustive cases)
```

**2. Break the sticky bit on purpose.** In your own copy of `align_sticky.v`, change `assign sticky = |shifted[W-1:0];` to `|shifted[W+1:0]` — that is, fold the guard and round positions back into sticky, which is the bug this chapter's own reference module used to contain. Run `tb_align_sticky.v` unchanged. It reports twenty failures, and the one to look at is `mant=000010 shamt=5`, where an exact tie is misreported as a value above a tie. Confirm you can say why that single wrong bit makes round-to-nearest-even impossible rather than merely inaccurate.

**3. Take the aligner to double precision.** Instantiate `align_sticky` at `W=53`, the significand width of an IEEE 754 binary64. Try `SHW=5` first. Work out from the precondition what the smallest legal `SHW` is before you compile, then check yourself against the elaboration error.

**4. Write a `bad_*` file of your own.** Every trap in this chapter has a file that reproduces it and self-checks. Signedness contamination does not yet have one. Compute an exponent difference from two unsigned `reg [7:0]` operands, assign it to a `reg signed [8:0]`, and show that it gives the wrong sign when the second exponent is the larger. Then make it self-check in the `bad_*` style: assert the *wrong* answer, so that `PASS` means the trap still reproduces. Add it to `targets.txt` and confirm `run_all.sh ch02` stays green.
