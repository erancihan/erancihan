## The Bits Never Know

Chapter 5 ended by pointing out what the verification machinery still lacks: a specification to verify *against*. Before chapter 7 can state what the 32 bits of an IEEE 754 number mean, this chapter has to establish what any bits mean — and the honest answer is: nothing, until someone signs a contract.

`8'b11111111` is 255, or −1, or −0.0078125, or "the exponent +128" (a stored value the excess-127 contract of "Biased Encoding: The Exponent's Format" will turn out to reserve). The register holds the same eight flip-flops in every case. A number system is not a property of the bits; it is an agreement about the **weight** each bit position carries, and everything in this chapter — two's complement, bias, Q-format — is a different weight table laid over the same storage. That is not a philosophical framing. It is, literally, how Verilog behaves: this chapter's `tb_signtraps.v` drives one pattern, `8'hFD`, into a `reg` and a `reg signed` and measures 253 out of one and −3 out of the other, with `u == s` true throughout, because comparison is on bits and only the *reading* differs. The bits never know which system they are in. When an expression mixes two contracts, the tool does not stop you; it silently picks one, and the section "Signedness in Verilog: Silent, All of It" measures exactly how.

The chapter runs in one arc. Positional notation, and the first honest reason floating point will have to round: 0.1 has no finite binary form. Then what an N-bit adder actually computes (arithmetic mod 2^N), why the same adder subtracts, and the four ways of reading negative numbers off one set of wires — two of which, sign-magnitude and bias, turn out to be the load-bearing ones for this guide, because IEEE 754 is built from both. Then overflow, precisely: carry and overflow are different questions with a one-XOR answer. Then the measured Verilog traps. Then fixed point: the binary point as a design-time agreement, alignment before addition (the direct ancestor of chapter 8's exponent alignment), and rounding as a policy whose bias you can measure. The chapter ends where fixed point runs out of dynamic range, which is the doorstep of chapter 7.

Everything below was verified this session: every arithmetic claim by `python3`, every Verilog claim by compiling with **Icarus Verilog 13.0** (`iverilog -g2012 -Wall`) and running under `vvp` on this machine. Every listing is a file in `src/ch06/`, and all five build targets run green through `run_all.sh ch06`.

## Radix, and the Fraction That Never Terminates

A numeral in radix r gives each digit position a weight that is a power of r, with the radix point separating the non-negative powers from the negative ones. So `1011.101₂ = 8 + 2 + 1 + 0.5 + 0.125 = 11.625₁₀` — verified, like every worked number in this chapter, with `python3`.

Converting an integer the other way is repeated division by 2, collecting remainders least-significant first:

```
217 = 2*108 + 1
108 = 2*54 + 0
54 = 2*27 + 0
27 = 2*13 + 1
13 = 2*6 + 1
6 = 2*3 + 0
3 = 2*1 + 1
1 = 2*0 + 1
217 = 11011001  check bin(): 0b11011001
```

The algorithm is not magic: `n mod 2` *is* the lowest bit, and `n div 2` is n shifted right by one, so each division strips one bit off the bottom — the same observation that makes `x % 2` and `x >> 1` free in hardware. Hex and octal are not new systems but 4- and 3-bit *groupings* of the binary string (16 = 2⁴, 8 = 2³): `11011001` grouped in fours from the point is `1101 1001` = `0xD9`, in threes `011 011 001` = `0o331`. That is why `%h` dominates in practice — hex is a view of the bits with no arithmetic in it, where decimal needs real division to produce. Chapter 2's "Writing Numbers Down" taught the literal syntax; this is why the groupings work.

Fractions mirror the integers: repeated multiplication by 2, collecting integer parts most-significant first, because doubling moves the radix point right and the bit that crosses it is the next fraction bit. For 0.375 the digits come out `[0, 1, 1]`: `0.375₁₀ = 0.011₂`, terminating in three steps.

Now run the same algorithm on 1/10, in exact rational arithmetic (`fractions.Fraction`, so no float noise contaminates the demonstration). The first five steps of the run:

```
step 1: 2 * 1/10 = 1/5  -> bit 0, remainder 1/5
step 2: 2 * 1/5 = 2/5  -> bit 0, remainder 2/5
step 3: 2 * 2/5 = 4/5  -> bit 0, remainder 4/5
step 4: 2 * 4/5 = 8/5  -> bit 1, remainder 3/5
step 5: 2 * 3/5 = 6/5  -> bit 1, remainder 1/5
```

The remainder after step 5 equals the remainder after step 1 — both 1/5 — so the process cycles with period 4, forever: `0.1₁₀ = 0.0001100110011…₂`, the group `0011` repeating. It is not slow to terminate; it *cannot* terminate. A reduced fraction p/q has a finite base-2 expansion iff q is a power of 2, because each emitted bit removes one factor of 2 from the denominator and nothing ever removes an odd factor. Verified across six fractions: 1/2, 3/8 and 7/16 terminate (odd part 1); 1/10, 1/3 and 1/5 repeat (odd parts 5, 3, 5). And the repeating tail really is worth exactly 1/10: the geometric sum of the pattern is (3/2)·(1/15) = 1/10, confirmed in exact arithmetic.

So any finite register holds not 0.1 but a neighbor of it. What your machine actually stores, measured with `decimal` and `struct`:

```
Decimal(0.1) = 0.1000000000000000055511151231257827021181583404541015625
0.1 as float64 bits: 0x3fb999999999999a
0.1 as float32 bits: 0x3dcccccd
float32 0.1 exact value: 0.100000001490116119384765625
```

Read the hex tails: `9 = 1001`, `c = 1100` — the same four repeating bits, phase-shifted, with the last digit bumped up by round-to-nearest. Truncating to 20 fraction bits instead gives `104857/1048576 = 0.09999942779541016`, in error by exactly 3/5242880 ≈ 5.72e−7 — low, because truncation always lands below.

This one example carries the chapter's whole motivation chain: a repeating expansion forces a finite register to round; *how* it rounds is a policy with measurable bias ("Shortening a Result: Rounding and Its Bias"); and IEEE 754 stores exactly this kind of rounded neighbor.

> **Seed for chapter 7.** Keep `0x3dcccccd` in your pocket. When chapter 7 has given you the field layout, you will decode it by hand — sign 0, exponent `01111011`, fraction `1001100…1101` — and watch the repeating pattern and the final round-up fall out of the fields.

## The Register Is an Odometer

An N-bit register cannot hold integers; it holds *residues mod 2^N*, and the adder computes exactly `(a + b) mod 2^N`, with the discarded quotient bit appearing as the carry-out. At four bits, verified in `python3` and then exhaustively over all 256 pairs:

```
9 + 8 = 17 ; mod 16 -> 1 ; carry-out = True ; bits: 1001+1000=0001 cout=1
15 + 1 = 16 ; mod 16 -> 0 ; carry-out = True ; bits: 1111+0001=0000 cout=1
7 + 7 = 14 ; mod 16 -> 14 ; carry-out = False ; bits: 0111+0111=1110 cout=0
```

`15 + 1 = 0` is the odometer rolling over, and the carry-out is the only record that it did. Hold on to the framing, because it governs everything downstream: **wraparound is not an error condition in the hardware**. The adder is doing exact modular arithmetic; "overflow" exists only relative to a *claim* that the register was supposed to hold an ordinary integer. That distinction is what makes "Carry Is Not Overflow" a real question and saturation ("Saturation Is a Policy") a policy rather than a fix.

Mod 2^N is also why one adder subtracts. Since `~b = (2^N − 1) − b`, we get `a + ~b + 1 = a − b + 2^N ≡ a − b (mod 2^N)` — invert, add one, and the difference falls out. Worked at four bits:

```
13 - 6: ~6&15= 9, +1=10; 13+10=23 -> result 7 (0111), carry-out=1 ; true diff mod 16 = 7
6 - 13: ~13&15= 2, +1= 3; 6+3=9 -> result 9 (1001), carry-out=0 ; true diff mod 16 = 9
8 - 8: ~8&15= 7, +1= 8; 8+8=16 -> result 0 (0000), carry-out=1 ; true diff mod 16 = 0
```

Two things in that table matter beyond the trick. First, `6 − 13 = 9`: the "wrong" answer is the mathematically right residue, −7 + 16 — your first meeting with a bit pattern whose meaning depends on interpretation, one section before that becomes official. Second, the carry-out doubles as a **not-borrow** flag: exhaustively over all 256 pairs, `cout` of `a + ~b + 1` equals `a >= b`. (That is the ARM convention; x86's carry flag inverts it on subtraction. Flag conventions are ISA lore, not arithmetic.)

Chapter 1's "How Hardware Writes Numbers Down" stated the complement trick on paper. This chapter can do better, because chapter 2 shipped the actual adder: `ripple4.v`, four structural full adders with a chained carry. `tb_sub4.v` wires chapter 2's own file — not a copy — with `b` through inverters and the carry-in tied high:

```verilog
  // b through inverters, carry-in tied to 1: the adder is now a subtractor.
  ripple4 dut (.a(a), .b(~b), .cin(1'b1), .sum(diff), .cout(cout));
```

and sweeps all 256 pairs against `(a − b) mod 16` and the not-borrow property. Its run, `$finish` trailer aside:

```
subtract-via-complement on ripple4: 0 errors in 256 cases
example: 13-6: a=1101 b=0110 ~b=1001 diff=0111 (7) cout=1
PASS tb_sub4 (one adder, one inverter row, cin=1)
```

The hardware cost of turning an adder into an adder–subtractor is one XOR per bit (a conditional inverter) plus routing the mode bit into `cin`. The FP adder of chapters 8 and 9 uses exactly this on aligned mantissas when the operands' signs differ.

Read the anomalies straight off it: ones' complement and sign-magnitude each have two zeros (`0000`/`1111` and `0000`/`1000`); two's complement has one zero and an orphan −8 with no positive partner; excess-8 is the unsigned column shifted down by eight, so its patterns sort in value order. Every claim below is one of these observations made precise.

### Two's complement is positional notation with one negative weight

Chapter 1's "How Hardware Writes Numbers Down" gave you the facts of two's complement; here is the single definition they all fall out of. An N-bit two's-complement word is ordinary positional notation in which the MSB's weight is **−2^(N−1)** — verified against all sixteen patterns. Corollaries, each verified exhaustively this session rather than recited:

- **Asymmetric range.** Max is `0111…1 = 2^(N−1)−1`, min is `1000…0 = −2^(N−1)`: one more negative value than positive, because the single zero sits in the "positive" half.
- **Negation is `~x + 1`**, since `x + ~x` is all ones = 2^N − 1, so `~x + 1 ≡ −x (mod 2^N)`. It has exactly two fixed points, verified: 0 and −8 — `−(−8) = −8` at four bits. Negation *itself* can overflow, on exactly one input.
- **The same adder works.** Two's complement is the residue system of "The Register Is an Odometer" with the upper half `[2^(N−1), 2^N)` relabeled as negatives. Addition of representatives mod 2^N therefore gives the true signed sum whenever that sum is representable — verified over all 256 4-bit pairs: 192 have representable sums, and the plain unsigned sum pattern, reinterpreted, is correct on every one of them. The other 64 — 25% of the space — are the subject of "Carry Is Not Overflow".
- **Sign extension replicates the MSB**, because the retired weight −2^(N−1) must be re-expressed as −2^(M−1) plus all-ones above the old position. Replication preserves the value on all sixteen patterns; zero-extension corrupts every negative: `1101` (−3) zero-extends to `00001101` = +13. Hold that number — the same +13 resurfaces twice in "Signedness in Verilog: Silent, All of It", where zero-extension is what the *language* silently does.
- **Pattern order is not value order.** Unsigned comparison of patterns disagrees with signed comparison of values (measured: the two orders differ — `1000`, the unsigned largest-half, is the signed minimum). This resurfaces in the comparison traps, and it is the defect bias encoding exists to fix.

> **Seed for chapter 8.** `−(−8) = −8` looks like a curiosity. It is a datapath bug waiting for a magnitude computation: the FP adder's subtract path needs `|a − b|`, and a negate-if-negative on the one pattern with no positive partner silently fails. Chapter 5's corner-case discipline applies: the corner is a single point, so a directed vector must aim at it.

### The two losers, and why one of them wins after all

**Ones' complement** negates by bitwise NOT alone. The table shows the price — two zeros — and its adder needs the *end-around carry*: wrap the carry-out back into bit 0. Verified this session: with end-around carry, the 4-bit ones'-complement adder is correct on every representable sum (excluding −0 + −0). It lost to two's complement over the double zero and the extra carry path, and survives as step one of `~x + 1`.

**Sign-magnitude** — a sign bit plus an unsigned magnitude — also has two zeros, and its adder cannot even start without a comparator: same signs means add magnitudes, different signs means subtract smaller from larger and take the larger's sign. For integers that was disqualifying. But chapter 1's "How Hardware Writes Numbers Down" already told you where this goes: **IEEE 754 is sign-magnitude.** The float format is a sign bit over magnitude fields — which is why floats have ±0 (chapter 5's corner-case taxonomy already met signed zero from the verification side), and why chapter 8's adder must contain exactly the compare-then-add-or-subtract machinery sign-magnitude integers would have needed. The "obsolete" encoding is the substrate of this guide's entire target; you will spend chapters 8 through 12 building the hardware tax it imposes.

## Biased Encoding: The Exponent's Format

The fifth column of the table stores `value + B` as a plain unsigned number — **excess-B**, here excess-8. Two measured properties define its character, both verified exhaustively this session:

- **Monotonicity.** Over all 256 pattern pairs, unsigned comparison of excess-8 patterns agrees with comparison of the encoded values. Two's complement fails this (measured in "One Pattern, Five Numbers"); bias fixes it by construction, because `x ↦ x + B` preserves order.
- **It is two's complement in disguise.** For every pattern, the excess-2^(N−1) encoding equals the two's-complement encoding **with the MSB flipped**. Bias is not exotic: it is the signed number line rotated so the most negative value lands on all-zeros.

Why does IEEE 754 store exponents this way? Because with sign, exponent and fraction laid out MSB-first and the exponent biased, *the float's magnitude bits — everything below the sign — compare like an integer*: of two floats, the larger magnitude has the lexically larger exponent-and-fraction field, so magnitude comparison needs only the unsigned comparator of chapter 1's "The Combinational Toolbox" — no signed hardware anywhere. (The sign bit must be handled aside: with it included, −1.0's pattern `bf800000` is lexically *above* 2.0's `40000000`.) Chapter 8's alignment question — which operand has the bigger exponent, and by how much? — becomes an unsigned compare-and-subtract of raw fields.

The concrete anchor, read from real binary32 bit patterns with `struct` this session:

```
1.0                          bits 0x3f800000 sign 0 exp 127 (0b01111111) frac 0x000000   actual exp 0
2.0                          bits 0x40000000 sign 0 exp 128 (0b10000000) frac 0x000000   actual exp 1
0.5                          bits 0x3f000000 sign 0 exp 126 (0b01111110) frac 0x000000   actual exp -1
1.1754943508222875e-38       bits 0x00800000 sign 0 exp   1 (0b00000001) frac 0x000000   actual exp -126
3.4028234663852886e+38       bits 0x7f7fffff sign 0 exp 254 (0b11111110) frac 0x7fffff   actual exp 127
```

Stored exponent minus 127 gives the actual exponent in every row: excess-127, exactly the toy excess-8 column at eight bits and a different B.

> **Seed for chapter 7.** Note what B is *not*: binary32's bias is 127 = 2^(8−1) − 1, not the "natural" 2^(N−1) = 128 of the excess-8 toy. IEEE offsets by one and reserves stored 0 and 255 — which is why the table's extremes show actual exponents −126 and +127 rather than −128 and +127, and why the reserved endpoints exist at all (subnormals at one end, Inf/NaN at the other) is chapter 7's opening business.

## Carry Is Not Overflow

Two different questions hide behind "did it overflow?". Carry-out (**C**) answers: did the *unsigned* sum exceed 2^N − 1? The overflow flag (**V**) answers: is the *signed* result wrong? They are logically independent — all four combinations occur, and a census over all 256 4-bit pairs (computed in `python3`, then re-counted by the testbench below) splits them **neither = 108, C-only = 84, V-only = 28, both = 36**. One example per quadrant, from `tb_ovf4.v`'s own output:

```
  5+4   (V, no C): 0101(5) + 0100(4) = 1001(signed -7, unsigned 9) C=0 V=1
  -7+-6 (V and C): 1001(-7) + 1010(-6) = 0011(signed 3, unsigned 3) C=1 V=1
  -1+1  (C, no V): 1111(-1) + 0001(1) = 0000(signed 0, unsigned 0) C=1 V=0
  3+2   (neither): 0011(3) + 0010(2) = 0101(signed 5, unsigned 5) C=0 V=0
```

`−1 + 1` is the row that kills the folk belief "a carry means something went wrong": reaching 0 from −1 *requires* wrapping past 2^N, the carry is routine, and the signed answer is exactly right.

Chapter 1's "How Hardware Writes Numbers Down" already stated the detection rule; now make it hardware, three equivalent ways:

1. **V = (carry into the MSB) XOR (carry out of it)** — the hardware rule. The intuition: the MSB is where the negative weight lives, and a disagreement between the carry entering and leaving that position means the true sum needed a weight the register does not have.
2. **V = (operands have the same sign) AND (result sign differs)** — adding opposite signs can only shrink magnitude and can never overflow, so overflow is exactly "same signs in, that sign not out".
3. **Widen by one**: sign-extend both operands to N+1 bits, add, and V is the XOR of the two top result bits.

All three were checked against ground truth — the true sum falling outside [−2^(N−1), 2^(N−1)−1] — over all 256 pairs at 4 bits, with zero mismatches; rule 1 also over all 65,536 pairs at 8 bits in `python3`, zero mismatches.

The satisfying part is where the signals come from. Chapter 2's `ripple4` computes its carry chain internally but exports only `cout` — and no port change is needed, because the full adder's own sum equation, `sum[3] = a[3] ^ b[3] ^ c3`, can be solved for the carry. `tb_ovf4.v`:

```verilog
  // Carry into the MSB, recovered from the ports.
  wire c3 = s[3] ^ a[3] ^ b[3];
  wire v  = c3 ^ cout;                       // rule 1: two MSB carries differ
  wire v_sign = (a[3] == b[3]) && (s[3] != a[3]);  // rule 2: sign rule

  // Rule 3: widen by one, V = XOR of the two top result bits.
  wire signed [4:0] wide = $signed(a) + $signed(b);
  wire v_wide = wide[4] ^ wide[3];
```

Its run checks all three rules against ground truth on every addition pair, asserts the census, then re-runs the sweep as subtraction via `a + ~b + 1` — the same V detects `a − b` overflow with no new logic. The summary lines of the run (the quadrant examples above and the verdict follow them):

```
V rules 1,2,3 vs ground truth: 0 mismatches in 256 add pairs
V and C independence: neither=108 C-only=84 V-only=28 both=36
subtraction V via a+~b+1: 0 mismatches in 256 pairs
```

Inside a real `ripple4` netlist, V is one XOR gate on two wires the last full adder already produces. For behavioral RTL, where the internal carries of `+` are invisible, use rule 3 — the widen-by-one habit — and note that it walks straight into the standing width discipline from chapter 2's "Width and Signedness: The Rules That Will Break Your Adder": if you forget the extra bit, `-Wall` will not say a word. That silence is measured again in "Signedness in Verilog: Silent, All of It".

> **Seed for chapter 8.** In the FP adder, unsigned C returns with a starring role: the mantissa sum's carry-out is what triggers the normalize-right-by-one step. Signed V never appears — IEEE 754 is sign-magnitude, so its mantissa arithmetic is all unsigned. You are learning V for general RTL literacy, and C because the adder depends on it.

## Signedness in Verilog: Silent, All of It

Chapter 2's "Width and Signedness: The Rules That Will Break Your Adder" stated the law: *an expression is signed only if every operand is signed; one unsigned operand makes the whole expression unsigned, and every operand is then read as a bit pattern.* This section is that law's casebook — the corollaries that bite in real code, each one measured on Icarus 13.0 this session and asserted by a known-answer check in `tb_signtraps.v`. Which is the only place they *can* be asserted:

> **Icarus reality.** `tb_signtraps.v` contains every bug class in this section — signed/unsigned mixing, a poisoned `>>>`, two silent truncations, a signed-vs-unsigned comparison, an unsigned literal negation. Compiling it with `iverilog -g2012 -Wall` produces **no output at all**: zero warnings, exit 0, measured this session — and enforced on every harness run, because `run_all.sh` fails any `run` target whose compile log is non-empty, so this silence is a regression-guarded property rather than a one-time observation. Chapter 3 taught you to name the tool that catches each trap. For this entire family the answer is: none. Only a testbench with known answers does.

The five headline classes fit in five continuous assignments — this block is lifted straight from the file:

```verilog
  // Five bug classes in five continuous assignments. Compiled with
  // iverilog -g2012 -Wall: not one word about any line below.
  reg signed [7:0] es;                  // -3
  reg        [7:0] eu;                  // 2
  wire [7:0] mix    = es + eu;          // poisoned: es read as 253
  wire [7:0] prodl  = es * es;          // product computed at 8 bits
  wire [3:0] narrow = es + es;          // 8-bit sum truncated to 4
  wire       cmp    = es < eu;          // unsigned compare: -3 < 2 is 0
  wire [7:0] shft   = (es + eu) >>> 1;  // >>> degraded: the sum is unsigned
```

Measured: `mix = 255`, `prodl = 9`, `narrow = 10`, `cmp = 0`, `shft = 127`. Now the casebook, with the testbench's own output as evidence (`sa = −3` signed, `sb = 2` signed, `u2 = 2` unsigned; excerpts from one run, grouped to follow the prose).

**Poisoning outvotes everything.** It is not "strongest operand wins": one unsigned operand outvotes any number of signed ones, *including signed literals*:

```
  ok signed + signed into 9 bits = -1
  ok signed + UNSIGNED into 9 bits = 255
  ok signed + $signed(u) (repaired) = -1
  ok sa < sb (signed compare) = 1
  ok sa < u  (POISONED: 253 < 2) = 0
  ok sa / sb = -1
  ok sa / u (poisoned: 253/2) = 126
  ok u * -8'sd1 (poisons a signed literal) = 254
  ok 200 > -8'sd1 (-1 became 255) = 0
```

Addition, comparison and division all flip. The one repair that works is `$signed()` on the offending operand. The one that does not is adding a signed zero — see the widening rows below.

**`>>>` is arithmetic only in a signed context.** Three distinct traps, one line each:

```
  ok signed  >>> 2 (sign fills) = -3
  ok signed  >>  2 (always logical) = 61
  ok unsigned >>> 2 (degrades) = 61
  ok $signed(u) >>> 2 (repaired) = -3
  ok (s + u*0) >>> 2 (u*0 poisons) = 61
```

`>>` stays logical no matter what you declared. `>>>` on an unsigned operand silently becomes logical. And the nastiest: `(s + u*0) >>> 2` shifts logically, because the *shifted expression* was poisoned by `u` — multiplying by zero launders the value but not the type. (The shift *amount* is self-determined and outside the poison's reach; the shifted operand is not.) One more pair worth pinning now because "Shortening a Result: Rounding and Its Bias" turns on it:

```
  ok -13 >>> 2 (floor) = -4
  ok -13 /   4 (toward zero) = -3
```

Verilog's two spellings of "divide by 4" disagree on negative odd values: `>>>` floors, `/` truncates toward zero.

**Widening extends by the RHS's signedness — the LHS is irrelevant.** With `s4 = 4'b1101` (−3) and `u4` the same pattern:

```
  ok signed  -> signed  wide = -3
  ok signed  -> UNSIGNED wide (sign-extends anyway) = 253
  ok unsigned -> signed wide (zero-extends) = 13
  ok u4 + 4'sd0 (folk repair fails) = 13
  ok $signed(u4) first, THEN widen = -3
```

Row 2: a signed value sign-extends even into an unsigned target (the pattern is `11111101`; the unsigned target then *reads* it as 253). Row 3 is the +13 promised in "One Pattern, Five Numbers" — the language zero-extending where the arithmetic needed sign replication. Row 4 kills the folk repair: `u4 + 4'sd0` is unsigned by the poison rule, so it still zero-extends. Row 5 shows the fix and the order of operations: cast first, then widen.

**Part-selects and concatenations are always unsigned — `s[7:0]` is not `s`.** With `s = −3` in eight bits:

```
  ok whole vector into 16 bits = 65533
  ok s[7:0] full-width part-select = 253
  ok {s} concatenation = 253
  ok s[7:0] >>> 2 (arithmetic shift killed) = 63
```

A part-select is unsigned by definition *even when it covers every bit*, so it zero-extends where the whole vector sign-extends, and it degrades `>>>` — the shift trap triggered by a syntactically invisible cause. Chapter 2 gave `{x}` as the idiom for deliberately stripping signedness; this is the same behavior arriving by accident. (In chapter 9 this default is actually *correct*: FP field extraction like `x[30:23]` yields magnitudes, which are unsigned by design.)

**Unsigned comparisons against zero are constants.** `u = 5 − 10` holds 251; `u < 0` is not a runtime bug but a statically-false branch, compiled without comment. The shipping form is the countdown loop — with a 4-bit unsigned index, `i >= 0` is always true, and the testbench's bounded loop confirms it never terminates on its own (40 iterations at the abort guard, where a signed index gives 11).

**Products are context-determined.** `(-128)*(-128)` into a 16-bit target is 16384 — Icarus widens the operands *before* multiplying, the same context rule chapter 2 measured against the `1 << 40` folklore. Into an 8-bit target it is 0, an error of 16384, in silence. Declare product targets `[2N−1:0]`, always.

**Based literals are unsigned: `-8'd3` is not minus three.** `w = -8'd3` *happens* to store −3 (negation runs at context width and the wrapped pattern reads back right), which is what makes the trap survivable in testing. The damage appears in a wider expression: measured, `sa + (-8'sd3)` gives −6 but `sa + (-8'd3)` gives **250** in a 9-bit target, because the unsigned literal poisons the sum and both operands zero-extend. And `sa == -8'd3` is *true* — equality is on patterns — so the two spellings even test as interchangeable. House rule: negative constants in signed arithmetic are written `-8'sd3` or plain `-3`, never `-8'd3`.

**`%d` follows the expression's signedness**, which is why one pattern prints as 253 or −3 depending on the declaration, and why chapter 5's FP testbenches compare `%h` patterns instead. Measured detail: `%d` pads to the widest decimal the operand's width-and-signedness could produce — four characters for signed 8-bit (`-128`), three for unsigned (`255`) — so columns jump when a declaration changes; `%0d` suppresses it.

The section in one table. The last column is a measurement, not an opinion:

| Trap | Symptom | Repair | Warned by `-Wall`? |
|---|---|---|---|
| unsigned operand in signed expression | whole expression goes unsigned | `$signed()` the operand | no |
| `>>` on a signed operand | logical shift | use `>>>` *and* keep the expression signed | no |
| `>>>` on an unsigned or poisoned expression | logical shift | `$signed()` first | no |
| widening an unsigned RHS | zero-extension | `$signed()` before assigning | no |
| part-select / concatenation | always unsigned, kills `>>>` | `$signed(s[..])` if needed | no |
| `u < 0`, unsigned `i >= 0` loop | constant branch / endless loop | signed index, or restructure | no |
| product into a same-width target | silent mod 2^N | `[2N-1:0]` target | no |
| `-8'd3`-style negative constants | unsigned constant poisons | `-8'sd3` or plain `-3` | no |

## Fixed Point: The Binary Point Is a Comment

Fixed point adds nothing to the hardware. An N-bit integer plus an *agreement* that its value is `raw × 2^−n` — that is the entire mechanism. The binary point exists in the designer's head and comments; the same `+` computes fixed-point addition because scaling by a constant commutes with it. This is the chapter's spine again, now with fractions: one pattern, three values, computed this session —

```
pattern 01010000 as Q8.0: 80.0
pattern 01010000 as Q4.4: 5.0
pattern 01010000 as Q1.7: 0.625
```

**Notation, and a hazard.** **Qm.n** here means m integer bits *including the sign*, n fraction bits, N = m + n total, signed two's complement; UQm.n is unsigned. Q-notation is not standardized: in the TI convention the sign bit is not counted in m (a 16-bit full-fraction word is Q15), in the ARM convention it is (the same layout is Q1.15). This guide uses the ARM-style count because it makes width arithmetic come out clean — `Qa.b × Qc.d → Q(a+c).(b+d)` with no +1 corrections. In the wild, the only safe habit is to state total width and fraction bits explicitly.

**Range and resolution.** Signed Qm.n covers `[−2^(m−1), 2^(m−1) − 2^−n]` in steps of 2^−n:

```
Q4.4 (8 bits): range [-8.0, 7.9375], step 0.0625
Q2.6 (8 bits): range [-2.0, 1.984375], step 0.015625
Q1.15 (16 bits): range [-1.0, 0.999969482421875], step 3.0517578125e-05
Q16.16 (32 bits): range [-32768.0, 32767.99998474121], step 1.52587890625e-05
UQ4.4 (8 bits): range [0.0, 15.9375], step 0.0625
UQ0.8 (8 bits): range [0.0, 0.99609375], step 0.00390625
```

At fixed N, every bit moved from integer to fraction halves the range and halves the step. The signature property: **resolution is uniform across the whole range** — absolute error at most step/2 everywhere. That is fixed point's virtue and its curse, because the *relative* error explodes near zero; "Where Fixed Point Runs Out" measures how badly.

**Encoding a real number is `raw = round(x · 2^n)` plus a range check**, and the check is not optional:

```
pi in Q2.14: ideal raw=51472, fits=False; 16-bit register holds 51472 -> signed -14064 -> value -0.8583984375
pi in Q3.13: ideal raw=25736, fits=True; 16-bit register holds 25736 -> signed 25736 -> value 3.1416015625
```

Pi does not fit in Q2.14's range [−2, 2), and the 16-bit register wraps the encode to **−0.858…** with no error signal anywhere. (An early draft of this chapter's own research script printed a plausible "pi in Q2.14 = 3.1416" because the check was missing. The bug class teaches itself.) The good encode errs by |3.1416015625 − π| ≈ 8.9e−6, inside Q3.13's step/2 bound of 2^−14 ≈ 6.1e−5.

### Alignment: you may only add matching points

Raw integers may be added **only when their binary points agree**. Otherwise the sum is meaningless in every format — not wrong in one and right in the other. Worked and verified: `a = 1.703125` in Q2.6 (raw 109) and `b = 5.0625` in Q4.4 (raw 81):

```
a = 1.703125 = Q2.6 raw 109 (01101101); b = 5.0625 = Q4.4 raw 81 (01010001)
naive raw add: 109+81 = 190; as Q2.6 -> 2.96875 ; as Q4.4 -> 11.875 ; true sum = 6.765625
aligned: b<<2 = 324 (Q4.6); sum raw 433 as Q?.6 -> 6.765625 == true 6.765625: True
```

The naive sum is wrong under *both* candidate readings. The fix shifts the coarser operand left by the difference in fraction bits (Q4.4 → Q4.6 here), after which integer addition is exact. Width bookkeeping: an overflow-proof Q2.6 + Q4.4 sum needs Q5.6, because max |sum| = 2 + 8 = 10 needs five integer bits with sign — in general, **budget one extra integer bit per addition**, since max + max is exactly one bit more.

> **Seed for chapter 8.** This left-shift-to-a-common-scale is the *same operation* as floating-point mantissa alignment, with one inversion. Fixed point shifts the coarser operand **left**, because the scales are static and the designer provisions the wider intermediate at design time. Floating point cannot — its register width is fixed — so it shifts the smaller operand's mantissa **right** instead, moving the scale rather than the width, and pays for the discarded bits with the guard/round/sticky machinery that chapter 2's "Reduction Operators and the Sticky Bit" already built as `align_sticky.v`. Both are instances of one rule: equalize the exponents of 2 before adding raw integers. Chapter 8 does this at runtime, in hardware, on every operation.

### Multiplication grows, and once it grows too far

A signed N×N product needs 2N bits, and exactly one input pair needs the very top one — verified at 4×4: products span [−56, **+64**], 64 needs the eighth bit, and only (−8)·(−8) reaches it. In Q terms the bookkeeping is clean: `Qa.b × Qc.d = Q(a+c).(b+d)` **exactly** — verified for all 256 Q2.2 pairs, the raw product read at 2^−(b+d) has no rounding in it at all. Rounding enters only when the product is squeezed back to a working format, which is the business of "Shortening a Result: Rounding and Its Bias".

The famous corner lives at Q1.15, the audio-DSP workhorse. Q1.15 × Q1.15 = Q2.30, whose top two bits are redundant sign copies for every input pair except one, so real datapaths shift left by one to drop the spare sign bit and keep Q1.31. Computed this session:

```
Q1.15: (-1)*(-1) raw product = 1073741824 = 2^30: True ; Q2.30 max pos raw = 2147483647
as Q1.31 (<<1): 2147483648 vs 32-bit signed max 2147483647 -> overflows: True
next largest product: 1073709056 from -32767 * -32768 ; fits in Q1.31 after <<1: True ( 2147418112 <= 2147483647 )
```

The standard fractional multiply overflows on exactly `(−1)·(−1)` and on nothing else — one point in a 2^32 input space. DSP hardware saturates that single case in silicon (TI's C6x `SMPY` family behaves this way); an RTL designer must saturate it or keep Q2.30. Chapter 5's lesson recurs with teeth: a corner this sharp is invisible to random stimulus at any believable volume — directed tests or bust.

## Shortening a Result: Rounding and Its Bias

Every fixed-point datapath repeatedly shortens results: a Q8.8 product has to fit back into a Q8.4 register, an accumulator has to feed a 12-bit DAC. Dropping k fraction bits is division by 2^k plus a **policy** for the lost remainder, and the policies differ only in fractions of an LSB per sample — and in what those fractions sum to. Measured exhaustively over all raws in [−256, 256), dropping k = 2 bits, errors in units of one output LSB:

```
floor (>> k, plain truncation of bits)       mean error -0.375000 LSB, max |error| 0.750 LSB
toward zero (C-style)                        mean error +0.000000 LSB, max |error| 0.750 LSB
round-half-up (add 0.5 LSB then floor)       mean error +0.125000 LSB, max |error| 0.500 LSB
round-half-even (convergent)                 mean error +0.000000 LSB, max |error| 0.500 LSB
```

Four readings. **Truncating bits is floor** — toward −∞, not toward zero; the `-13 >>> 2 = -4` versus `-13 / 4 = -3` pair measured in "Signedness in Verilog: Silent, All of It" is exactly this distinction living inside one language, and it routinely surprises C programmers. Floor is biased by −(2^k − 1)/2^(k+1) LSB (−3/8 here) and is also *free* — you just do not wire the low bits — which is why the bias argument has to be made: the default is the biased one. **Toward-zero's measured 0 is an artifact** of averaging over a sign-symmetric input set; its error always shrinks magnitude, so it distorts signals even when the DC average cancels — do not read that row as "unbiased". **Half-up** cuts the worst case to 0.5 LSB but keeps +2^−(k+1) of bias, entirely from ties: the remainder is exactly half for 1/2^k of inputs, and every one is pushed up. **Half-even** sends ties to the even neighbor, half up and half down, and the systematic error goes to zero. The tie cases, measured:

```
 raw +2 (1/2): floor->0 halfup->1 halfeven->0
 raw +6 (3/2): floor->1 halfup->2 halfeven->2
 raw -2 (-1/2): floor->-1 halfup->0 halfeven->0
 raw -6 (-3/2): floor->-2 halfup->-1 halfeven->-2
 raw +10 (5/2): floor->2 halfup->3 halfeven->2
```

### Fractions of an LSB, integrated

Per-sample the numbers look ignorable. Accumulated, they are the difference between a working filter and a drifting one. One hundred thousand zero-mean random 12-bit samples (`random.seed(42)`, `randint(-2048, 2047)`), each requantized by k = 4 bits, then summed:

```
floor/truncate: sum of rounded =   -45667, exact/16 =  1147.50, drift = -46814.50 output LSBs (-0.46814/sample)
half-up       : sum of rounded =     4188, exact/16 =  1147.50, drift =  +3040.50 output LSBs (+0.03041/sample)
half-even     : sum of rounded =     1027, exact/16 =  1147.50, drift =   -120.50 output LSBs (-0.00120/sample)
predicted per-sample: floor -15/32 = -0.46875, half-up +1/32 = +0.03125, half-even ~0
```

The measured drifts match the closed forms to three decimals. Truncation injects a DC offset ~15× larger than half-up's; half-even's residual is another ~25× smaller and is noise, not bias — it shrinks relatively as samples accumulate. In a feedback loop — an IIR filter, a PLL, an AGC — a rounding DC offset does not sit still; it integrates. That is why convergent rounding exists in silicon.

### Three bits are enough

Round-half-even *looks* like it needs all k dropped bits. It needs three summary values: the kept LSB (**L**), the most significant dropped bit (**R**, the round bit), and the OR of everything below that (**S**, the sticky bit). Verified exhaustively at k = 4 over raw ∈ [−4096, 4096):

```
increment = R & (S|L) vs arithmetic half-even, raw in [-4096,4096), mismatches: 0
half-up increment = R alone, mismatches: 0
```

`RNE increment = R & (S | L)`: round up iff the round bit is set AND (something is set below it — not a tie — OR the tie-break target is odd). Half-up is just `increment = R`. Two remarks. The sticky OR is what makes the rule width-independent — the formula contains no k — which is the whole reason a 24-bit-plus-G/R/S datapath can round as if it had kept every bit of an aligned addend. And the rule was verified here on two's-complement raws with the dropped field read as an unsigned remainder above the floor: it works unchanged for negatives, no sign special-case. (IEEE 754 rounds in sign-magnitude, so its rounding logic never even sees a negative — a quiet payoff of the encoding.)

> **Seed for chapter 8.** Chapter 2's `align_sticky.v` exposes `guard`, `round` and `sticky` as three ports because FP needs one bit more than this section did: normalization can shift the result left by one *after* the round position is chosen, promoting G to a real mantissa bit and R to the new round bit. Pure fixed-point requantization has no post-round shift, so L/R/S suffice — you have now derived the fixed-point version of the machinery chapter 8 will run at full width.

### The hardware idiom, and a multiply to run it on

`fixmul44.v` is the section's DUT: a Q4.4 × Q4.4 multiply producing the exact Q8.8 product and three Q8.4 requantizations of it —

```verilog
  assign p_full = a * b;                // context widens to 16 bits: exact

  assign p_trunc  = p_full >>> 4;              // drop the bits: free, biased
  assign p_halfup = (p_full + 16'sd8) >>> 4;   // add half an output LSB
```

— and, for half-even, the trick that production DSP RTL actually uses, from Gisselquist's ZipCPU rounding article: add a data-dependent constant, then truncate —

```verilog
  // Round-half-even as a single add (the ZipCPU convergent-rounding idiom):
  // add { L, ~L~L~L } just below the kept part, then truncate. The addend
  // is 7 when the kept LSB L is 0 and 8 when L is 1, so the carry into the
  // kept part fires exactly when R & (S | L) says round up. The concat is
  // unsigned and poisons the +, which is harmless here: addition produces
  // the same bit pattern either way (mod 2^16), and cvg's own declaration
  // restores the signed reading before the >>> that does care.
  wire signed [15:0] cvg = p_full + {12'b0, p_full[4], {3{!p_full[4]}}};
  assign p_even = cvg >>> 4;
```

Work the derivation once and it stops being magic: with L = 0 the addend is `0111` = 7, so the carry into the kept part fires only when the dropped field exceeds 8 — above the tie, round up, ties stay on the (even) floor. With L = 1 the addend is `1000` = 8, so the carry fires at 8 and above — the tie rounds up, to the even neighbor. That is `R & (S | L)` folded into one adder, no compare tree. FPGA hard DSP blocks bake the same options into silicon (AMD/Xilinx DSP48E1, via its C-input and carry machinery).

`tb_fixmul44.v` sweeps all 65,536 pairs against an arithmetic reference built from `%` and if-statements — deliberately nothing like the DUT's shift-and-add — and keeps a bias ledger in sixteenths of an output LSB, asserted against totals computed independently in `python3`. Its run, verdict trailer aside:

```
fixmul44: 0 errors in 65536 pairs (exact product + 3 requantizers)
bias, sixteenths of an output LSB over all pairs:
  floor -425984 (mean -0.40625 LSB)  half-up +65536 (mean +0.06250 LSB)  half-even 0
  ties: 8192 of 65536 pairs end in ...1000
   0.375 * 0.25 = raw 24 (1.5 output LSBs): trunc 1  halfup 2  halfeven 2
   0.625 * 0.25 = raw 40 (2.5 output LSBs): trunc 2  halfup 3  halfeven 2
  -0.625 * 0.25 = raw -40 (-2.5 output LSBs): trunc -3  halfup -2  halfeven -2
```

Compare the measured means with the uniform-input table above and notice they *moved*: floor came out −0.406 rather than −0.469, and half-up's tie bias **doubled** to +0.0625, because products are not uniform in their low bits — trailing zeros are common, and a remainder of exactly 8 occurs for 8192/65536 = 1/8 of pairs instead of the uniform 1/16. Rounding bias depends on the data's low-bit distribution, which is why it is measured here rather than assumed. The one line that did not move: **half-even's total error over all 65,536 products is exactly zero.**

Where should each mode go? The practitioner recommendation — ZipCPU's, matched by what the DSP blocks support — is to truncate freely at *internal* points where a later stage re-rounds anyway, and spend the convergent round once, at the output format boundary. That is practice-lore, not a theorem; the measurements above are the reason it is the standard advice.

## Saturation Is a Policy

Rounding is the policy for the fraction end of a squeeze; saturation is the policy for the integer end. Wraparound is what the adder does for free ("The Register Is an Odometer"); saturation — clamp to the nearest representable extreme — has to be built. The case for paying: a wrapped overflow is *maximally* wrong. In the 8-bit audio example from Wikipedia's saturation-arithmetic article, a true 130 saturates to 127 — slightly flat — or wraps to −126, a full-scale click; the article characterizes wraparound's effect as "a catastrophic loss in signal-to-noise ratio", and saturating instructions are mainstream, not exotic: Intel MMX/SSE2/AVX2 and ARM NEON all provide them.

The idiomatic RTL structure is this chapter's pieces snapped together — widen by one so nothing is lost, detect V with the top-two-bits rule, mux the clamp. `satq44.v`, a Q4.4 saturating adder:

```verilog
  wire signed [8:0] full = a + b;    // widen by one: no information lost

  assign y_wrap = full[7:0];         // wraparound = just drop the top bit
  assign ovf    = full[8] ^ full[7]; // top-two-bits rule ("Carry Is Not
                                     // Overflow"): sign bit vs the bit above
  assign y_sat  = !ovf    ? full[7:0] :
                  full[8] ? 8'h80 :  // negative overflow -> -8.0
                            8'h7f;   // positive overflow -> +7.9375
```

The sign of the *widened* sum, `full[8]`, picks the clamp direction; the wrapped sign bit `full[7]` is exactly the bit you cannot trust. `tb_satq44.v` proves the module over all 65,536 pairs against an integer reference model, asserts the overflow census — 16,384 pairs, the same 25% measured at 4 bits in "One Pattern, Five Numbers" — and prints the two policies side by side (verdict trailer omitted):

```
satq44: 0 errors in 65536 pairs; overflow pairs: 16384 (25%)
   5.2500 +  4.5000 = true   9.7500 : wrap -6.2500  sat  7.9375  ovf=1
  -7.0000 + -6.0000 = true -13.0000 : wrap  3.0000  sat -8.0000  ovf=1
   5.2500 + -4.5000 = true   0.7500 : wrap  0.7500  sat  0.7500  ovf=0
```

5.25 + 4.5 wraps to **−6.25** — a large positive result turned large and negative — where saturation answers 7.9375, wrong by only what the format cannot hold.

> **Trap.** Forget the widening — `wire signed [7:0] full = a + b;` — and the tool still says nothing; `ovf` becomes garbage quietly. This is chapter 2's silent-truncation warning applied verbatim, and it is why the testbench checks `ovf` against an independent range test on every pair rather than trusting the structure.

## Where Fixed Point Runs Out

**Dynamic range** is the ratio of the largest representable magnitude to the smallest nonzero one — for an N-bit fixed format, 2^N − 1, or in decibels 20·log₁₀(2^N − 1) ≈ 6.02·N. Computed exactly:

```
8-bit fixed: max/min = 2^8-1 =          255 ->    48.1 dB  (rule of thumb 48.2 dB)
16-bit fixed: max/min = 2^16-1 =        65535 ->    96.3 dB  (rule of thumb 96.3 dB)
24-bit fixed: max/min = 2^24-1 =     16777215 ->   144.5 dB  (rule of thumb 144.5 dB)
32-bit fixed: max/min = 2^32-1 =   4294967295 ->   192.7 dB  (rule of thumb 192.6 dB)
```

The audio anchors make those tangible: 16-bit ≈ 96.3 dB is CD audio; 24 bits already exceed the ~120 dB from hearing threshold to pain. For a signal whose scale is *known and roughly constant*, fixed point is not merely adequate — it is the better tool: exact addition, uniform absolute error, cheap hardware. The honest case for floating point is not "fixed point is bad". It is: **fixed point requires knowing the scale in advance.**

When the scale is unknown, or spans decades, the format dies at the small end. Take Q16.16 — range ±32768, step ≈ 1.5e−5, a perfectly reasonable general-purpose choice — and hand it small values, measured against float32:

```
x=0.001: Q16.16 raw = 66 -> 1.007080e-03, rel err 0.00708 ; float32 -> 1.000000e-03, rel err 4.75e-08
x=1e-05: Q16.16 raw = 1 -> 1.525879e-05, rel err 0.526 ; float32 -> 1.000000e-05, rel err 2.53e-08
Q16.16 max = 32767.99998474121 => 40000.0 fits? False
```

At 0.001 the fixed format is off by 0.7% where float32 is off by 5e−8. At 1e−5 it is wrong by **52.6%** — the format is down to one significant bit — while float32 still delivers 2.5e−8. And the same word cannot hold 40000 at all. The two designs make opposite trades: Q16.16's relative step swings from 1.5e−2 at x = 0.001 to 1.5e−8 at x = 1000, while float32's is 2^−23 ≈ 1.19e−7 everywhere in its normal range. Fixed point has uniform *absolute* error and wild relative error; floating point spends its 2^23 fraction values per octave instead of per interval, making *relative* error uniform.

The span comparison ends the argument:

```
float32 max normal = 3.4028235e+38; min normal = 1.1754944e-38; min subnormal = 1.4012985e-45
float32 normal-range dynamic range: 1529 dB
float32 incl subnormals: 1668 dB
fixed-point bits to span at min-subnormal resolution: 277 -> 278 with sign
```

A 32-bit float spans 1529 dB — 1668 with subnormals — against 192.7 dB for 32 fixed bits; matching that span at constant resolution would take a **278-bit** fixed register. The price is everything this chapter measured about rounding, now applied on every operation, plus the alignment shift performed by hardware at runtime instead of by you at design time.

## Bridge to Chapter 7

You now hold every part floating point is made of. A binary32 number is a fixed-point significand — UQ1.23, an unsigned value in [1, 2) with a constant hidden integer bit — under a sign-magnitude sign, scaled by a power of two whose exponent is stored in excess encoding. Nothing in that sentence is new to you anymore. The costs transfer with the parts: adding two floats means equalizing scales first (this chapter's alignment rule, with the shift direction inverted), the significand adder wraps and carries exactly as in "The Register Is an Odometer", a carry-out forces a renormalization (the C flag, employed), and the squeeze back to 24 bits rounds with the L/R/S logic you verified — widened by one guard bit. "Floating point is fixed point plus a hardware-managed exponent" is the one-sentence version, and chapter 8 is this chapter replayed inside a single datapath. What chapter 7 must settle first is the encoding's own corners: what happens when the exponent itself overflows (Inf), what fills the gap between zero and the smallest normal number (subnormals), what 0/0 stores (NaN) — the corner cases chapter 5's taxonomy already named from the verification side, now defined from the format side. And the first thing you will decode there is a number this chapter already handed you: `0x3dcccccd`.

**Verified web sources (fetched and read in this chapter's research pass)**

3. Dan Gisselquist, "Rounding numbers", ZipCPU blog — <https://zipcpu.com/dsp/2017/07/22/rounding.html>. The convergent-rounding correction-constant idiom reproduced in `fixmul44.v` and verified exhaustively here; its truncation-bias and half-up-bias statements match this session's measurements.
4. Wikipedia, "Q (number format)" — <https://en.wikipedia.org/wiki/Q_(number_format)>. The TI convention (sign bit not counted in m) versus the ARM convention (counted), as stated in the notation note.
5. Wikipedia, "Saturation arithmetic" — <https://en.wikipedia.org/wiki/Saturation_arithmetic>. The 8-bit audio example (130 → 127 vs −126), the "catastrophic loss in signal-to-noise ratio" characterization, and the MMX/SSE2/AVX2/NEON instruction support.

**By title (no link asserted)**

7. Stuart Sutherland and Don Mills, "Standard Gotchas: Subtleties in the Verilog and SystemVerilog Standards That Every Engineer Should Know", SNUG Boston 2006 — the practitioner catalogue of the signedness trap family.

11. M. Morris Mano and Michael D. Ciletti, *Digital Design*, 6th ed., ch. 1; Israel Koren, *Computer Arithmetic Algorithms*, 2nd ed.; Behrooz Parhami, *Computer Arithmetic: Algorithms and Hardware Designs*, 2nd ed. — number systems, complements, bias and rounding at textbook depth.
