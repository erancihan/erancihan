## Two Kinds of Logic, and One Language for Both

One question classifies any circuit. **Can I write this down as a truth table with no notion of "before"?** If yes it is **combinational**: the output is a pure function of the inputs as they are right now, settling after some gate delay. If the description needs the word "previously" it is **sequential**, and somewhere inside it there is a flip-flop. Chapter 1's toolbox — multiplexer, decoder, priority encoder, ripple-carry adder, barrel shifter — was entirely combinational, and chapter 1's "Taming Time With a Clock" introduced the one device that makes the other kind possible. For a programmer the reframing that makes the pair click is this: combinational logic is a pure expression re-evaluated continuously and forever, and sequential logic is that expression plus a latched checkpoint that only moves on a clock edge. One language expresses both, which is convenient and is also the source of every bug in this chapter, because the two are told apart by details a careless reader skims over: an `@(*)` against an `@(posedge clk)`, an `=` against a `<=`.

Before any of the syntax, there is an idea to install, because everything else follows from it. **Verilog is not executed by the FPGA.** It is executed by a *simulator*, and separately *pattern-matched* by a synthesis tool. `always @(posedge clk) q <= d;` is not a command meaning "when the clock rises, copy `d` into `q`". It is a **pattern the tool has been taught to recognise as a D flip-flop**, whereupon it reaches into its library and emits one. There is no `flipflop` keyword in Verilog and there never was. You do not create a flip-flop; you write something a tool *infers* one from, and this guide says "infer" deliberately and consistently.

Three consequences follow, and they are why this chapter is mostly rules. Code outside the recognised patterns either fails to synthesise or synthesises into something you did not intend, the accidental latch being the classic case. The simulator will happily run non-synthesisable code, so **a passing simulation is not evidence that you have described hardware**. And two fragments that look almost identical can infer completely different circuits: `q <= d` and `q = d` inside a clocked block differ by one character and describe different machines.

Those patterns collectively are the **synthesisable subset**, far smaller than the language. Chapter 2 taught the language; this chapter teaches the part that becomes hardware. There are three idioms.

| Idiom | Infers | Reach for it when |
|---|---|---|
| `assign y = <expr>;` | combinational logic | the logic fits in one expression |
| `always @(*) begin ... end` | combinational logic | you need `if`, `case`, a loop, or a temporary |
| `always @(posedge clk) ... <= ...` | flip-flops | you need to remember something |

`assign` and `always @(*)` infer *identical* hardware for identical logic; the choice between them is purely which reads better. Only the third idiom builds state.

> **Icarus reality.** Icarus does not synthesise. It has no notion of a gate, a flip-flop or a latch anywhere in its data structures — it is an event simulator executing procedural code. Every rule in this chapter about what a tool *infers* is therefore a rule you are personally responsible for, because the tool in front of you is not checking. That is not a criticism; it is the correct division of labour. It is also why "What the Simulator Will and Will Not Tell You" below is a section rather than a footnote.

## Describing Combinational Logic Three Ways

Write down the same AND gate three ways and watch what happens. This is `tb_regwire.v`, and the three lines in the middle are the whole experiment:

```verilog
  assign y_assign = a & b;

  always @(*)           y_always = a & b;

  always @(posedge clk) y_flop  <= a & b;
```

`y_assign` is declared `wire`. `y_always` and `y_flop` are both declared `reg`. Run it:

```
  t=2 a=1 b=1 | y_assign=1 y_always=1 y_flop=x
  t=6 a=1 b=1 | y_assign=1 y_always=1 y_flop=1
  t=8 a=1 b=1 | y_assign=1 y_always=1 y_flop=1
  t=9 a=1 b=0 | y_assign=0 y_always=0 y_flop=1
PASS tb_regwire
```

At t=2 the inputs have been valid for two nanoseconds and no clock edge has happened. `y_assign` and `y_always` already have the answer; `y_flop` is still `x`, because nothing has clocked it. At t=9 the inputs change and the same two move together while `y_flop` keeps its stale value until the next edge. `y_assign` and `y_always` are the same circuit — zero flip-flops, one AND gate each, updating at the same instant. `y_flop` is the only register in the file, and it is a register because of the `@(posedge clk)`, not because of the word `reg`. Chapter 2's "`reg` does not mean register" made this claim; here is the measurement that settles it.

So the choice between the first two idioms is stylistic. Use `assign` when the logic is one expression, and `always @(*)` when you want `if`, `case`, a `for` loop or a local temporary, because those exist only inside procedural blocks. The one hard rule is a language rule, not a hardware one: **the target of an `assign` must be a net, and the target of any assignment inside an `always` block must be a variable.** That is assignment mechanics and says nothing about what gets built.

Here is the procedural form as you should always write it. `sel_mux.v`, in full:

```verilog
`timescale 1ns/1ps
`default_nettype none

// A three-input selector written as a combinational always block. Two habits
// make it combinational rather than latched: the unconditional default
// assignment on the first line, and the `default:` arm on the case. Either one
// alone would be enough here. Both together survive the next edit.
module sel_mux
  (input  wire [1:0] sel,
   input  wire [3:0] a,
   input  wire [3:0] b,
   input  wire [3:0] c,
   output reg  [3:0] y);

  always @(*) begin
    y = 4'b0000;
    case (sel)
      2'b00:   y = a;
      2'b01:   y = b;
      2'b10:   y = c;
      default: y = 4'b0000;
    endcase
  end

endmodule

`default_nettype wire
```

Four things in there are habits rather than requirements, and every one is load-bearing. The sensitivity list is `@(*)` and never an explicit list of signals — "Sensitivity Lists, and What `@(*)` Really Covers" below shows what an explicit list costs you. The assignment operator is `=` throughout, for reasons derived in "Blocking and Non-Blocking, Derived From the Queue" below. The first statement gives `y` an unconditional value, so no path through the block leaves `y` unassigned. And the `case` carries a `default:` arm even though its three explicit arms plus the default already cover the two-bit selector — the arm catches `sel` being `x`, and survives somebody widening `sel` to three bits next year.

Those last two are the same habit, and they are the cure for the accidental latch. You will meet the disease shortly. One naming convention goes with them, worth adopting now because it makes review possible: suffix genuinely registered signals `_q` or `_r` and leave combinational ones bare or suffixed `_c`, so a reader can tell what kind of signal they are looking at without scrolling to find the block that drives it.

> **Seed for chapters 9 and 12.** Almost the entire floating point datapath is combinational: exponent compare, alignment shift, mantissa add, leading-zero count, normalisation shift, rounding decision, repacking. Every one is a block of exactly the shape above, and chapter 2's `align_sticky.v` and `round_ne.v` are already the `assign` form of it. The sequencing — which runs when, and where results are captured — is the only sequential part, and it is what "State Machines" below and chapter 11 are about. Keep the two apart in your head and in your files.

## Remembering Things: the Flip-Flop and Its Templates

Chapter 1's "Taming Time With a Clock" described the D flip-flop as a device that samples its input at a clock edge and holds it for the rest of the cycle — state that changes at an *instant* rather than over an *interval*. Here is how you ask for one, and for the three variants you will actually use. These are the four `always` blocks of `flop_templates.v`, each one a pattern a synthesis tool has been taught to map onto a flip-flop from its library.

A plain D flip-flop, no reset, powering up holding whatever the silicon settled on:

```verilog
  always @(posedge clk)
    q <= d;
```

A counter with **synchronous** reset. `rst_n` is ordinary data into the flop, so it is not in the sensitivity list and is only sampled at a clock edge:

```verilog
  always @(posedge clk)
    if (!rst_n) q <= 4'd0;
    else        q <= q + 4'd1;
```

The same counter with **asynchronous** reset. `negedge rst_n` *is* in the sensitivity list:

```verilog
  always @(posedge clk or negedge rst_n)
    if (!rst_n) q <= 4'd0;
    else        q <= q + 4'd1;
```

And a **clock enable**. The enable is an `else if`, never an extra term in the sensitivity list — `@(posedge clk or posedge en)` would be asking for a second clock. There is deliberately no final `else`:

```verilog
  always @(posedge clk)
    if (!rst_n)  q <= 4'd0;
    else if (en) q <= q + 4'd1;
```

`tb_flop_templates.v` runs all three counters off one clock with a five-nanosecond half period, so rising edges land at t=5, 15, 25 and so on. Reset is released at t=7, then a second and much shorter reset pulse is applied at t=42 and removed at t=44 — entirely between the edges at t=35 and t=45. The enable drops at t=52.

```
  t=8 rst_n=1 en=1 | q_sync=0 q_async=0 q_en=0
  t=16 rst_n=1 en=1 | q_sync=1 q_async=1 q_en=1
  t=26 rst_n=1 en=1 | q_sync=2 q_async=2 q_en=2
  t=36 rst_n=1 en=1 | q_sync=3 q_async=3 q_en=3
  t=43 rst_n=0 en=1 | q_sync=3 q_async=0 q_en=3
  t=46 rst_n=1 en=1 | q_sync=4 q_async=1 q_en=4
  t=56 rst_n=1 en=0 | q_sync=5 q_async=2 q_en=4
  t=66 rst_n=1 en=0 | q_sync=6 q_async=3 q_en=4
PASS tb_flop_templates
```

Three things to read off it, and each will come back.

At **t=43** the asynchronously reset counter is already at zero, and no clock edge has happened since t=35. That is the entire meaning of "asynchronous": the reset does not wait to be asked. The synchronous counter stays unaware — `q_sync` was 3 before the pulse and counts 4, 5, 6 afterwards, so **it never saw the reset at all**, because the pulse was narrower than a clock period and no rising edge fell inside it. That is the most useful practical fact about synchronous reset and the one beginners are never shown: it must be held for at least one full clock period, and the clock must be running.

At **t=56** the enabled counter freezes at 4 while the other two carry on. Look back at `cnt_en`: there is no `else`, so when `en` is low nothing assigns `q` and `q` holds. In a **clocked** block that is completely normal and infers a flip-flop with an enable, which is what almost every register in a real design is. The identical shape in a **combinational** block is the accidental latch. Same code, opposite verdict, and the only thing separating them is the sensitivity list at the top.

> **Trap.** Every term in an edge-sensitive list must be an edge. `always @(posedge clk or rst_n)` mixes an edge with a level and is outside the synthesisable subset. The correct asynchronous form is `always @(posedge clk or negedge rst_n)`, and the polarity there must match the polarity of the test — `negedge rst_n` pairs with `if (!rst_n)`. The reset branch must be first and must test nothing but the reset: `if (!rst_n && en)` is not a template, it is a puzzle for the synthesiser.

> **Icarus reality.** Under `-g2012` Icarus also accepts SystemVerilog's `always_ff`, `always_comb` and `always_latch`: the same three idioms with the intent written down. IEEE 1800-2017 §9.2.2.2 and §9.2.2.4 say a software tool *should* check that intent — warn when an `always_comb` block infers a latch, or when an `always_ff` body is not a legal flop template. *Should*, not *shall*; a tool that reports nothing is still conforming, and this one reports nothing. **Measured at `-g2012 -Wall`: `always_comb` around an incomplete `if`, and `always_ff` around a blocking assignment, both compile silent, exit 0, and both bugs still reproduce at run time.** `bad_svalways.v` and its transcript are in "The Accidental Latch" below. The only `always_*` rule this simulator enforces is that an `always_ff` sensitivity list be edge-only, and that is a warning, not an error. Adopt the keywords anyway — they state intent where a reviewer and a diff can see it, and the checks are real in the tools that implement them, which includes Vivado, Questa, VCS and Verilator — none of which is installed here, so that last claim comes from their documentation, not from a run on this machine. They are certainly not real here, so a reader working only in Icarus gets the documentation and none of the enforcement. This guide stays with `always @(*)` and `always @(posedge clk)` because that is what every existing codebase uses.

> **Seed for chapter 13.** Chapter 13 takes the SystemVerilog transition properly, and enforcement is the reason to make it: which tools implement IEEE 1800's *should*-check rules, what the three keywords are worth in a flow that has a linter and a synthesiser in it, and what is left of that on a machine carrying only a simulator. The measurement above is where that argument starts, and it is the argument, not the syntax, that decides whether switching buys anything.

## How a Simulator Actually Runs Your Code

The rest of the chapter is a corollary of this section. Everything you are about to be told to do — use `<=` in clocked blocks, `=` in combinational ones, never write one variable from two blocks, never trust `#0` — follows from a single mechanism, and with the mechanism you can derive the rules instead of memorising them.

Start with the part most unlike a program. **Simulated time is not wall-clock time, and it is not one step per statement.** Everything happening at one value of `$time` is a **time slot**, and a time slot is not one pass through your code: it is an arbitrary number of iterations over a set of ordered queues, and time does not advance until every queue is empty. A whole cascade of combinational logic settles inside one time slot with `$time` unmoved.

IEEE 1364-2005 calls those queues the **stratified event queue**, and there are five, in order:

1. **Active** — blocking assignments, evaluation of the right-hand sides of non-blocking assignments, continuous-assignment updates, `$display`, procedural statements generally. Events here may execute **in any order**. This is where races live.
2. **Inactive** — events deferred with `#0`. Touched only once the active queue is empty.
3. **Non-blocking assign update** — the *left-hand side updates* of non-blocking assignments whose right-hand sides were evaluated earlier in this slot. This is the region that makes `<=` behave like a flip-flop.
4. **Monitor** — `$monitor` and `$strobe`, after all value updates for the slot are complete. IEEE 1800 renames this **Postponed** and adds regions for assertions and program blocks.
5. **Future** — everything scheduled for a *later* time slot. These make time advance.

The rule people miss: **draining the active queue can put new events back into the active queue**, and the simulator keeps going until it is genuinely empty before looking at the inactive queue. The loop is *if anything is active, do it; otherwise promote the earliest non-empty region and start again.* One **promote-and-drain pass** over those queues at a fixed value of `$time` is what everyone calls a **delta cycle**: it advances no simulation time. IEEE 1364 never uses the term — it is borrowed from VHDL — which is why you will see it used loosely elsewhere, sometimes for a single event execution. This chapter always means the promote-and-drain pass.

Two experiments make this visible. Here is the interesting half of `tb_regions.v` — one clocked block writing `r` with a non-blocking assignment, then reading it back four ways:

```verilog
  always @(posedge clk) begin
    $display("  [active    region] $display before 'r <= d'  : r=%0d", r);
    r <= d;
    $display("  [active    region] $display after  'r <= d'  : r=%0d   (unchanged)", r);
    seen_after_nba  = r;
    #0;
    $display("  [active, after #0] $display after  '#0'      : r=%0d", r);
    seen_after_zero = r;
    $strobe ("  [postponed region] $strobe  end of time slot : r=%0d", r);
  end
```

That block is an **instrument, not a template**: `#0` never belongs in RTL, for the reason Cummings' Guideline #8 gives in "Blocking and Non-Blocking, Derived From the Queue" below. Note also what the third label does *not* say. Nothing executes "in the inactive region"; `#0` defers the continuation *into* it, and when the active region empties those events are promoted back into the active region and run there. The inactive region is a holding pen, not an execution context.

A second `always @(posedge clk)` block does nothing but read `r`, and there is a `$monitor`. With `r` starting at 0 and `d` at 7, the whole first clock edge looks like this:

```
  [monitor   region] $monitor                  : t=0 r=0
  [active    region] a second clocked block reads r=0
  [active    region] $display before 'r <= d'  : r=0
  [active    region] $display after  'r <= d'  : r=0   (unchanged)
  [active, after #0] $display after  '#0'      : r=0
  [postponed region] $strobe  end of time slot : r=7
  [monitor   region] $monitor                  : t=5 r=7
PASS tb_regions
```

Every claim in the region list is in that transcript. The `$display` **after** `r <= d` prints 0: the assignment evaluated `d`, captured 7, put an update event in region 3 and moved on without touching `r`, and the process did not block — which is exactly why the operator is called non-blocking. The other clocked block on the same edge also reads 0, and **this is the whole reason `<=` works**: every clocked block on that edge sees the pre-edge state of the machine, exactly like a room full of real flip-flops sampling their D inputs at the same instant. The `#0` does not help, because the NBA region is scheduled *after* the inactive region; a beginner reaching for `#0` to "let the value settle" has reached for a queue that runs too early. And `$strobe` prints 7, which is Cummings' Guideline #7 in one line: use `$strobe`, not `$display`, to print values assigned with `<=`.

The second experiment, `tb_delta.v`, chains three inverters, each in its own `always @(*)` block, and samples the cascade at increasing delta depth:

```
  t=1  a_decl=0 -> ya=x        b_init=0 -> yb=1
  same time slot, right after 'p = 0' : s1=x s2=x s3=x
  after one  #0                       : s1=1 s2=0 s3=1
  after two  #0                       : s1=1 s2=0 s3=1
PASS tb_delta
```

The line right after `p = 0;` shows all three stages still `x`: assigning `p` *scheduled* the blocks, it did not run them, because the writing process keeps the processor until it blocks. Then, by the time a single `#0` has returned, the **entire three-block cascade has already settled**, and a second `#0` changes nothing. That is region 1 draining to exhaustion before region 2 is looked at. So `#0` is not merely useless for observing non-blocking results; it is also unnecessary for combinational settling, and between them those cover most of the reasons people write it. Counted in delta cycles: a cascade of `=` blocks settles inside **one** promote-and-drain pass however deep it is, while the same cascade written with `<=` costs one delta cycle per stage, because each update has to wait for the NBA region to be promoted before it can wake the block downstream.

The first line of that transcript is a different lesson, and deserves its own callout.

> **Trap.** An `always @(*)` block does not self-start. `ya` is driven by `always @(*) ya = ~a_decl;` where `a_decl` was initialised **at its declaration**, and a declaration initialiser generates no event, so the block never ran and `ya` was `x` for the whole first time step. `yb`, whose input was assigned from an `initial` block, produced its answer immediately. An `always @(*)` block is not a continuously true equation; it is a process asleep on an event list that only produces a value in response to a change. In a real design this rarely bites, because inputs come from logic that does change. In testbenches it bites on the first line you write, and it explains a surprising number of stray `x` values.

Now the part that motivates "Blocking and Non-Blocking, Derived From the Queue" below. IEEE 1364-2005 §11.4.1 *Determinism* guarantees that statements inside one `begin`/`end` execute in source order and that an NBA's right-hand side is sampled before any NBA update lands, and §11.3 fixes the order of the regions themselves. What §11.4.2 *Nondeterminism* explicitly **leaves to the implementation** is *the order in which multiple processes in the active region are executed*: two ready `always @(posedge clk)` blocks may run in either order, and a simulator may even interleave them. So two standards-compliant simulators can give different answers for the same code and both be right. `bad_race.v` contains two modules with the same two statements in opposite source order:

```verilog
  always @(posedge clk) a = d;
  always @(posedge clk) b = a;
```

```verilog
  always @(posedge clk) b = a;
  always @(posedge clk) a = d;
```

Both start from `a = 0, b = 0`, both have `d = 1`, and both get exactly one rising edge:

```
    t=5  BLOCK-B runs
    t=5  BLOCK-A runs
  after one rising edge, d=1:
    race_ab (a=d first in the source) : a=1 b=0
    race_ba (b=a first in the source) : a=1 b=1
    t=15  BLOCK-A runs
    t=15  BLOCK-B runs
    t=25  BLOCK-B runs
    t=25  BLOCK-A runs
    t=35  BLOCK-A runs
    t=35  BLOCK-B runs
    t=45  BLOCK-B runs
    t=45  BLOCK-A runs
PASS tb_race (source order still decides the answer)
```

`b` came out 0 in one module and 1 in the other. Nothing changed but the order two independent `always` blocks appear in the file. That is a race, made visible without a second simulator.

The `BLOCK-A` / `BLOCK-B` lines come from a third module that does nothing but report which of two same-edge blocks Icarus actually runs first. Read the pattern: B,A then A,B then B,A then A,B. **Icarus alternates the order between time steps inside a single run.** Most descriptions of race conditions imply a simulator picks an order and sticks to it; this one does not. The alternation is not a bug — §11.4.2 permits it, and §11.5 *Race conditions* is the short consequence section that points back at it — and it is the mechanism behind the nastiest testbench failure in this chapter, in "Simulation Artifacts That Will Cost You an Evening" below.

The design rule that follows is not "avoid simulators that do this". It is: **do not write code whose answer depends on that order.** That is what "Blocking and Non-Blocking, Derived From the Queue" below is about.

## Blocking and Non-Blocking, Derived From the Queue

You now know enough to derive the rule rather than be handed it.

A **blocking** assignment, `=`, does all its work in the active region: the right-hand side is evaluated and the left-hand side updated *before the simulator moves to the next statement in that process*. Statement order inside a `begin`/`end` is therefore load-bearing, exactly as in C.

A **non-blocking** assignment, `<=`, is two-phase. In the active region the right-hand side is evaluated and captured and an update event is placed in the NBA region; the left-hand side is untouched. In the NBA region the captured value is written. Between the phases every read of the left-hand side still returns the **old** value, and the process does not block — the next statement runs at once, still in the active region.

Two lines demonstrate the difference completely. `tb_swap.v` contains this:

```verilog
  always @(posedge clk) begin
    a_nb <= b_nb;
    b_nb <= a_nb;
  end
```

and this:

```verilog
  always @(posedge clk) begin
    a_bl = b_bl;
    b_bl = a_bl;
  end
```

Both start from `a = 0x11, b = 0x22`:

```
  t=1   a_nb=11 b_nb=22  |  a_bl=11 b_bl=22
  t=11   a_nb=22 b_nb=11  |  a_bl=22 b_bl=22
  t=21   a_nb=11 b_nb=22  |  a_bl=22 b_bl=22
PASS tb_swap (nba swaps, blocking destroys a value)
```

The non-blocking pair swap, and swap back on the next edge, forever. The blocking pair both become `22` on the first edge and never change again: statement one overwrote `a_bl`, statement two read the new value, and `11` is gone. No temporary was needed for the swap, and none could have saved the copy.

Why does this correspond to hardware? Real flip-flops on a common clock all sample their D inputs at approximately the same instant and change their Q outputs slightly later, so every flop reads the *pre-edge* state. Nothing reads another flop's *post-edge* value on the same edge; that would need the new value to travel through the combinational logic and arrive before the edge that produced it. Non-blocking assignment encodes exactly that: all right-hand sides evaluate in the active region, so every clocked block reads pre-edge state, and all left-hand sides update in the NBA region, so every flop changes together after all the reads. Because every read precedes every write, **the order in which the blocks run cannot matter**. The race above is not avoided by care; it is eliminated by construction.

That is the sentence to keep: *a `<=` block reads the old state and writes the new state, and there is no moment at which any block can observe a half-updated machine.*

The corollary is that **statement order inside a `<=` block is irrelevant**, which is strange to accept if you write software. `shift3.v` is a three-stage shift register:

```verilog
  always @(posedge clk) begin
    q1 <= din;
    q2 <= q1;
    q3 <= q2;
  end
```

`bad_shift3.v` contains the same three flops with `=`, in natural order:

```verilog
  always @(posedge clk) begin
    q1 = din;
    q2 = q1;
    q3 = q2;
  end
```

and again with the statements reversed:

```verilog
  always @(posedge clk) begin
    q3 = q2;
    q2 = q1;
    q1 = din;
  end
```

One single-cycle pulse is injected on `din`, and all three are sampled every cycle:

```
  cyc 0 |  nba 100  |  blocking 111  |  blocking reversed 100
  cyc 1 |  nba 010  |  blocking 000  |  blocking reversed 010
  cyc 2 |  nba 001  |  blocking 000  |  blocking reversed 001
  cyc 3 |  nba 000  |  blocking 000  |  blocking reversed 000
  cyc 4 |  nba 000  |  blocking 000  |  blocking reversed 000
PASS tb_shift3 (collapse reproduced, reversal accidentally works)
```

The non-blocking version walks the pulse one stage per cycle, which is what a shift register is for. The blocking version shows `111` in cycle 0 — the pulse reached all three outputs in the *same* cycle. Three flip-flops collapsed into a wire and the pulse arrives two cycles early. A synthesis tool reading that code typically infers one flip-flop and two wires, so netlist and RTL simulation agree; they are simply both wrong relative to what you meant.

Now the third column, because it is why the rule is absolute rather than advisory. **The reversed blocking version works.** `100`, `010`, `001` — a correct three-stage shift register built entirely with `=`, because reversing the statements happens to preserve read-before-write. Blocking assignment in a clocked block is not always wrong; it is wrong *unpredictably*, depending on the order you typed the lines in, and it stops working the moment the stages live in different `always` blocks, where there is no defined order at all. Code that is correct only because of typing order is code a second simulator need not agree with, and code the next maintainer will break by tidying it. That is precisely why the bug survives testing: it passes.

The mirror-image question — why `=` in combinational blocks — has the same kind of answer. Such a block has no memory and no edge, and you want its temporaries to behave like local variables: assign, then use the new value. `<=` there compiles and usually works, but costs a delta cycle per assignment, exactly as `tb_regions.v` measured, so a chain of such blocks settles later than the equivalent `assign` chain and anything sampling in between sees two answers for one gate. Worse, if the block reads a variable it also writes with `<=`, the NBA update re-triggers the block and you have an oscillation at a single simulation time. Hence a reviewer's heuristic: **the assignment operator tells you what kind of block you are in**, and if the operator and the sensitivity list disagree, one of them is a bug.

The canonical statement of all this is Clifford Cummings' *Nonblocking Assignments in Verilog Synthesis, Coding Styles That Kill!*, SNUG-2000 San Jose. Five of its eight guidelines are the ones you will use daily, verbatim:

> **Guideline #1:** When modeling sequential logic, use nonblocking assignments.
> **Guideline #3:** When modeling combinational logic with an always block, use blocking assignments.
> **Guideline #5:** Do not mix blocking and nonblocking assignments in the same always block.
> **Guideline #6:** Do not make assignments to the same variable from more than one always block.
> **Guideline #8:** Do not make assignments using `#0` delays.

And the paper's own framing of why any of it matters, also verbatim, is the sentence to carry out of this section:

> "Ignoring the above guidelines can still infer the correct synthesized logic, but the pre-synthesis simulation might not match the behavior of the synthesized circuit."

The rules are not about getting different gates. They are about your simulation of the RTL agreeing with the hardware built from it. Break them and you can ship something that works on the bench and fails in simulation, or the reverse — the worst failure mode available, because your regression suite starts lying to you.

So, the whole thing in four lines:

1. Combinational `always` block: `always @(*)` and `=` everywhere.
2. Clocked `always` block: `always @(posedge clk)` and `<=` everywhere.
3. Never mix `=` and `<=` in one block.
4. Never assign one variable from two blocks.

And the reason, in one: **`<=` makes your simulation behave like a real flip-flop; `=` makes it behave like a real wire.**

> **Seed for chapter 11.** A pipeline is nothing but a long shift register with logic between the stages. Every stage boundary is a non-blocking assignment, and the read-before-write property is exactly what lets you write all the stages in one block, in any order, and get a pipeline instead of a wire. The `blocking` column above is what a pipeline built with `=` looks like: every stage computing in the same cycle, the depth gone, the timing closure you paid for thrown away. That column is the failure chapter 11 is guarding against.

## Sensitivity Lists, and What `@(*)` Really Covers

The sensitivity list is the block's wake-up condition, and there are four ways to spell it. `always @(a or b)` is the Verilog-1995 form, where — say this out loud once — the `or` is a **separator**, not a logical OR; it does not compute `a | b`. `always @(a, b)` is the Verilog-2001 comma form and means the same thing. `always @*` and `always @(*)` are the implicit list and are equivalent; this guide writes `@(*)`, and the reason to write nothing else is that every alternative goes stale silently. `bad_sens.v` has the same two-input mux three times; the broken one is this:

```verilog
  always @(a)
    y = sel ? b : a;
```

`b` and `sel` are read by the block and are not in its event list, so the block only wakes when `a` changes. Walk it through five input changes:

```
-- an incomplete sensitivity list
  a=0 b=0 sel=0 | y_bad=0 y_full=0 y_star=0   start
  a=1 b=0 sel=0 | y_bad=1 y_full=1 y_star=1   a changed: all three agree
  a=1 b=0 sel=1 | y_bad=1 y_full=0 y_star=0   sel changed: y_bad is stale
  a=1 b=1 sel=1 | y_bad=1 y_full=1 y_star=1   b changed: y_bad stale but right
  a=0 b=1 sel=1 | y_bad=1 y_full=1 y_star=1   a changed: y_bad wakes up
```

Row three is the bug: `sel` went high, so the answer should be `b` = 0, and `y_bad` is stuck at 1. Row four is why the bug survives your test suite — `y_bad` is still stale and now *coincidentally correct*, which a stale one-bit output will be about half the time. Row five is the strangest: the block wakes because `a` changed, an input that at `sel = 1` does not affect the result at all, so its behaviour now depends on the history of an irrelevant signal. Synthesis builds the full mux regardless, because a synthesiser reads the logic and constructs the real cone of inputs. **The gates are right and the simulation is wrong** — the same simulation/synthesis mismatch Cummings warns about, arriving from a different direction.

So what does `@(*)` cover? Per IEEE 1364-2005 §9.7.5, every net and variable **read** by any statement in the block. Three details in that sentence will catch you.

"Read" means read *anywhere*, including on the right-hand side of an assignment to itself. A variable appearing only as a left-hand side is excluded, which is what stops most blocks self-triggering — but `y = y + 1` reads `y`, so it does self-trigger, forever, at one value of `$time`.

Indexing adds the **whole** vector or array, not the selected element. `bad_arraysens.v` reads `mem[idx]` and `v[idx]` in one `@(*)` block, and the array half draws one of only two sensitivity-list diagnostics Icarus offers anywhere in this chapter — the other being the `always_ff` edge-only complaint from `bad_svalways.v`:

```
bad_arraysens.v:25: warning: @* is sensitive to all 4 words in array 'mem'.
  idx=1 | y_mem=11 y_vec=1
  after writing mem[3], which idx does not select: y_mem=11
PASS bad_arraysens
```

The block wakes when *any* word of `mem` is written, including one `idx` is not selecting. The standard prescribes that, so the behaviour is right and the warning is about performance and intent rather than correctness. The identical rule covers the vector select on the next line, and `-Wall` is silent there because `sensitivity-entire-vector` is not one of its classes. Ask for the class by name and the second line appears:

```
bad_arraysens.v:26: warning: @* is sensitive to all bits in 'v[3:0]'.
```

The third detail is the one that will actually cost you a day. **Signals read inside a called `function` or `task` are not added to the implicit list.** `bad_sens.v` has a module with two functions, one of which reaches out to a module-level signal:

```verilog
  function [3:0] f_hidden;
    input [3:0] x;
    begin
      f_hidden = x + q;
    end
  endfunction
```

`q` never appears at the call site — the block reads `y_auto = f_hidden(p);` and `@(*)` sees only `p`. The other function takes the same value as an argument. Changing `q` alone:

```
-- a signal read only inside a called function
  p=1 q=0 | y_auto=1 y_manual=1   start
  p=1 q=5 | y_auto=1 y_manual=6   only q changed: y_auto did not move
  p=2 q=5 | y_auto=7 y_manual=7   p changed: y_auto catches up
```

`y_auto` did not respond to `q` at all. It caught up only when `p` moved, at which point it re-evaluated and produced the right answer — so the bug is intermittent as well as invisible. A synthesiser reads the function body and wires `q` in properly, so once again the gates are right and the simulation is wrong. There are two cures: pass every input as a function argument so it appears at the call site, or use SystemVerilog's `always_comb`, whose inferred sensitivity list is specified by IEEE 1800-2017 §9.2.2.2 to include variables read by called functions. That is a language-level difference, not a matter of taste, and it is the one `always_comb` property Icarus 13.0 does implement — measured in `bad_svalways.v` — because an inferred list is *computed*, not *checked*.

Finally, edges. `posedge` on a one-bit signal covers more transitions than you expect, and on a multi-bit signal it covers fewer. `bad_edge.v`:

```
  bus=1110 : rising edges on bus so far = 0
  bus=0001 : rising edges on bus so far = 1
  s=x    : rising edges on s   so far = 1
  s=1    : rising edges on s   so far = 2
PASS bad_edge (edges use the LSB; x transitions count)
```

`bus` going from `0000` to `1110` — a large increase — produced **no** rising edge, and going from `1110` to `0001` produced one, because edge detection on a vector uses the **least significant bit only**. Never put a vector in an edge expression; it compiles, it simulates, and it means something you did not ask for. The scalar half is the other surprise: on a one-bit signal `0 → x` and `x → 1` both count as rising edges, along with `0 → z` and `z → 1`, which is how an uninitialised reset or an `x` clock fires clocked blocks at time zero in ways nobody predicts.

## The Accidental Latch

Chapter 1's "Taming Time With a Clock" promised you would meet this before you could commit it. Here it is with numbers.

The rule, stated exactly: in a **combinational** block, a synthesis tool infers a level-sensitive latch for a variable if there exists **any execution path through the block on which that variable is not assigned**. The tool has no alternative. You wrote "under condition C, `y` keeps whatever it had", and the only hardware that keeps a value without a clock is a latch.

Three refinements matter. The test is **per variable**, so one block can produce three clean combinational outputs and one latch. It is **per path**, so an `if` whose `else` assigns some *different* variable still leaves a path on which the first one is unassigned. And a `case` without a `default:` is incomplete unless its items provably cover every value of the selector — four arms of a two-bit selector is complete, four arms of a three-bit selector is not, and tools differ in how hard they try to prove it.

Four further shapes catch experienced people, and none of them looks like a missing `else`. A **partial vector assignment** — `y[3:1] = ...` on a path where `y[0]` is never written — latches bit 0 alone. A **`for` loop that does not cover every index** does the same thing bit by bit, and is invisible to a review that reads only the loop bound. A **read-before-write of a block-local temporary**, `if (c) t = a; y = t;`, reads `t` on a path where nothing assigned it, so `t` latches. And an **empty `default: ;` arm** is a `default:` arm that assigns nothing and therefore cures nothing. All four turn up in exactly the alignment and rounding code chapter 9 will write.

`bad_latch.v` has both classic spellings, with the same port list as `sel_mux.v` so one testbench can drive all three. The `if` version:

```verilog
  always @(*)
    if      (sel == 2'b00) y = a;
    else if (sel == 2'b01) y = b;
    else if (sel == 2'b10) y = c;
```

and the `case` version:

```verilog
  always @(*)
    case (sel)
      2'b00: y = a;
      2'b01: y = b;
      2'b10: y = c;
    endcase
```

Neither assigns `y` when `sel` is `2'b11`. Run all three modules through the same stimulus:

```
  sel=01 a=1 b=5 c=9 | y_mux=5  y_if=5  y_case=5
  sel=11 a=1 b=5 c=9 | y_mux=0  y_if=5  y_case=5
  sel=11 a=1 b=a c=9 | y_mux=0  y_if=5  y_case=5
  sel=00 a=1 b=a c=9 | y_mux=1  y_if=1  y_case=1
PASS tb_latch (latch behaviour reproduced, sel_mux clean)
```

Row two: `sel` moved to the uncovered value, and both broken modules **held** the 5 they had from the previous row while `sel_mux` correctly produced its default of 0. Row three: `b` changed from 5 to `a`, and they went on holding 5 — an output that ignores its inputs. That held value *is* the latch, and you are watching it work.

Why is that almost always a bug? You wanted a mux and got a mux plus a storage element. Latches are transparent while their enable is high, so data flows *through* them and the timing analyser must reason about paths that begin and end mid-cycle — much harder than flop-based analysis. How badly the fabric itself takes it is family-specific and not worth folklore: on some families the latch is built in a lookup table with combinational feedback, on others the slice's storage element can simply be configured as a latch instead of a flop. The family-independent objection is the one that matters: the output now depends on *when* things changed rather than only on what they are, so a functional test can pass while the real part fails. For this guide specifically: a latch in the alignment or normalisation logic gives you an adder that is right for one vector and wrong as soon as you stream vectors through it, and that failure looks like an arithmetic bug when it is not.

One nuance in the transcript cuts against the pattern of "Blocking and Non-Blocking, Derived From the Queue" and "Sensitivity Lists, and What `@(*)` Really Covers". **This is not a simulation/synthesis mismatch.** RTL and gate-level simulation of a latch agree; the simulator is faithfully reproducing the hardware you asked for. It is a design bug both stages reproduce honestly, which tells you what the cures are for — they fix the design, not the simulation. That agreement is about *function*, at zero delay. A real transparent latch has an aperture — enable-to-Q, data-to-Q through the open window, glitch sensitivity on the enable — that an `always @(*)` model has no representation for, and the timing half is the half that kills you.

There are three cures, and a fourth if you will move languages. **Give every output an unconditional default at the top of the block.** This is not merely the habit that scales, it is the only cure that scales: it stays correct per variable, per path and per bit however the block grows, and it covers all four of the extra shapes above. The other two are local patches. **Complete every `if` with an `else`** is fine for two-way logic and brittle as soon as a third branch appears. **Put a `default:` arm on every `case` that assigns every variable the block writes** — the qualifier is the whole rule, because `default: ;` is a latch with a comment on it. Or **use `always_comb`**, where IEEE 1800-2017 §9.2.2.2 says a tool *should* check the block is combinational and report an inferred latch — real in Vivado, Questa, VCS and Verilator, and measurably absent in Icarus, as the callout below shows. On what to assign in that `default:` — `4'bxxxx` tells the synthesiser "don't care" and makes an unreachable case loudly visible in simulation, while a defined value is safer against real `x` propagation and against a machine reaching an illegal state. Prefer the defined value.

One case is not a bug. A latch you actually *meant* — a clock-gating enable latch is the usual one — is rare, and is written so that the intent is on the page: `always_latch` rather than `always @(*)`, and non-blocking assignment inside it, which is Cummings' Guideline #2. Anything else that holds a value in a combinational block is an accident.

Which brings us to detection, where the honest answer is uncomfortable. **In synthesis it is easy, and every tool reports it**: Vivado prints `WARNING: [Synth 8-327] inferring latch for variable 'y_reg'` (UG901), Quartus prints `Warning (10240): Inferred latch for "y"`, and Yosys emits `$dlatch` cells from its `proc` pass. Those three strings were **read in vendor documentation, not captured here**: none of the three tools is installed in this guide's environment, which is true of Verilator as well and is flagged again where its warning classes appear in "What the Simulator Will and Will Not Tell You" below. Every other block of output in this chapter is real stdout. So **read the synthesis log for the word "latch" on every build**. A latch you actually meant is rare enough that any occurrence deserves a look.

> **Icarus reality.** Icarus reports no latch. Not with `-Wall`, and not with anything else, because there is no other flag:
>
> ```
> $ iverilog -g2012 -Wall -o /tmp/sim sel_mux.v bad_latch.v tb_latch.v
> exit=0
> $ iverilog -g2012 -Wall -Wextra -o /tmp/sim sel_mux.v bad_latch.v tb_latch.v
> Ignoring unknown warning class extra
> exit=0
> ```
>
> No warning, no note, and `-Wextra` is not even a class this tool has heard of. **And not with `always_comb` either**, which is the cure most readers will reach for first. `bad_svalways.v` puts the incomplete `if` above under `always_comb` and the collapsing shift register of "Blocking and Non-Blocking, Derived From the Queue" above under `always_ff` with `=`:
>
> ```
> bad_svalways.v:84 warning: Synthesis requires the sensitivity list of an always_ff process to only be edge sensitive. sv_ff_level.lvl is missing a pos/negedge.
>   always_comb, sel=11 : y=5
>   always_comb, b 5->a : y=5  (held: still a latch)
>   always_ff with '=' : q1=1 q2=1 q3=1  (collapsed to one stage)
>   always_comb, q 0->5 : y=6  (function read: the list saw it)
> PASS bad_svalways (checks absent, inferred list present)
> ```
>
> One diagnostic, and it is about a *third* module's sensitivity list rather than about either bug — and it is a warning, exit 0. `y` held 5 across a change of `b`, which is the same latch `tb_latch.v` measures, and the `always_ff` shift register collapsed to one stage exactly as `bad_shift3.v` does. The last line is the half that does work: `always_comb`'s inferred list reached inside a called function, so `y` followed `q` alone. Inferring a list is computation; deciding whether a block is combinational is analysis. This tool does the first and not the second.
>
> All of which is expected and correct: **Icarus is a simulator, not a synthesiser.** It never asks "what gates would this be?" It executes the procedural code you wrote, and code that holds a value between events is perfectly ordinary procedural code. There is no latch object anywhere in `vvp`'s data structures to warn about. The internet is full of advice implying otherwise, and it is wrong: **a simulator cannot warn you about a latch. Only a synthesiser or a linter can.** For a latch-finder you can install today, `verilator --lint-only -Wall` documents a `LATCH` check and costs nothing to run alongside Icarus. Write `always_comb` for the intent; get the enforcement from a tool that implements it.

What simulation *can* do is test for the behaviour, which is what `tb_latch.v` does: hold the block in its unhandled input state, change a signal the output should depend on, and assert that the output moved. Rows two and three above are exactly that test, and it is the only latch check available inside this toolchain.

One piece of history, because you will meet it in older code: `case (sel) // synopsys full_case parallel_case`. `full_case` asserts that every selector value is covered, so the tool stops inferring the latch without anything about the code changing — the simulator still holds the old value on an uncovered selector, while synthesis now treats that value as a don't-care and may emit anything. `parallel_case` asserts something else entirely: that the case items are mutually exclusive, so the tool may build a flat multiplexer instead of a priority chain. If the items do overlap in reality, RTL simulation takes the first match and the netlist takes whatever the flattened logic gives, and the design works until an input combination nobody tested arrives. Cummings' *"full_case parallel_case", the Evil Twins of Verilog Synthesis* (SNUG-1999 Boston) is the standard demolition, calling the belief that they "always make designs smaller, faster and latch-free" false and noting that they "can obscure the fact that latches have been inferred". They are **comments**, so only the synthesiser reads them — a mechanism whose whole purpose is to make simulation and synthesis disagree — and they suppress the report rather than the missing assignment. A `default:` arm is portable, standard and shorter. SystemVerilog's `unique case` and `priority case` replaced them, and the simulator checks those.

## Reset Strategy

"Remembering Things: the Flip-Flop and Its Templates" above showed the two reset templates and the measurement that separates them: a reset pulse falling between two clock edges cleared the asynchronously reset counter instantly and was invisible to the synchronous one. That is the whole behavioural difference. What remains is deciding which you want, which is a real engineering choice.

**Synchronous reset** treats reset as ordinary data into the flop, so it is covered by ordinary setup and hold analysis with no special timing arcs, a glitch on the reset net is filtered by the flop instead of resetting your design, and everything stays synchronous and easier to verify formally. Against it: **it needs a running clock**, so a design that must come up in a known state before its PLL locks cannot use it; it adds a term to the data path, lengthening the `t_logic_max` of chapter 1's setup inequality in "The setup constraint, and where f_max comes from"; and the pulse must be wide enough to be sampled, as the t=43 row above showed rather brutally.

**Asynchronous reset** works with no clock and guarantees a known state at power-up, and on most FPGAs and standard-cell libraries the flop has a dedicated asynchronous clear pin so it costs nothing in the data path. Against it: the *release* is dangerous, a glitch on the reset net resets the flop for real, and an asynchronous reset tree is by definition an asynchronous signal crossing into your clock domain.

That "release is dangerous" is where chapter 1's "Metastability" comes back. An asynchronous reset creates two timing checks that are the setup and hold analogues for release. **Recovery time** is the minimum time the reset must be *de-asserted* before the active clock edge for that edge to be captured reliably; **removal time** is the minimum it must stay asserted *after* the edge. Violate either and the flop goes metastable exactly as a setup or hold violation would — and different flops in the same register can resolve differently, so a four-bit counter can come out of reset holding `0011`.

Notice the asymmetry: *asserting* an asynchronous reset is safe, because nothing is being decided. **De-asserting it is the hazard.** Hence the rule: assert asynchronously, de-assert synchronously. The circuit that does this is the two-flop reset synchroniser, `reset_sync.v`:

```verilog
`timescale 1ns/1ps
`default_nettype none

// The standard two-flop reset synchroniser. Assertion is asynchronous and
// instant; de-assertion takes two clocks and lands just after a clock edge, so
// recovery and removal downstream become an ordinary timing closure problem
// instead of an unconstrained asynchronous one. One of these per clock domain.
// In a real flow s1 and s2 also carry a synthesis attribute telling the tool
// not to merge, retime or spread them - `(* ASYNC_REG = "TRUE" *)` on AMD
// (Xilinx). Attributes are out of scope for this guide; the omission is
// deliberate, not an oversight.
module reset_sync
  (input  wire clk,
   input  wire arst_n,
   output wire rst_n_sync);

  reg s1, s2;

  always @(posedge clk or negedge arst_n)
    if (!arst_n) {s2, s1} <= 2'b00;
    else         {s2, s1} <= {s1, 1'b1};

  assign rst_n_sync = s2;

endmodule

`default_nettype wire
```

The flops are cleared asynchronously — instantly, no clock needed — and then walk a `1` through on the clock, which is why de-assertion takes two edges and lands aligned to one. `tb_reset_sync.v` runs two identical counters, one on the raw reset and one on the synchronised version, releasing the raw reset at t=13, two nanoseconds before the rising edge at t=15:

```
  t=6 arst_n=0 rst_n_sync=0 | q_raw=0 q_sync=0
  t=16 arst_n=1 rst_n_sync=0 | q_raw=1 q_sync=0
  t=26 arst_n=1 rst_n_sync=1 | q_raw=2 q_sync=0
  t=36 arst_n=1 rst_n_sync=1 | q_raw=3 q_sync=1
  t=46 arst_n=1 rst_n_sync=1 | q_raw=4 q_sync=2
PASS tb_reset_sync
```

`q_raw` starts counting at the t=15 edge, two nanoseconds after its reset was released. `q_sync` does not start until t=35, because `rst_n_sync` did not rise until the t=25 edge and the counter sampled it at t=35. The synchronised path costs two clock cycles of latency out of reset and buys a release aligned to a clock edge instead of arriving whenever the board felt like it. Be precise about what that buys. The alignment holds at the synchroniser's own output; across a real reset tree with thousands of loads and real skew, recovery and removal still have to be closed in static timing analysis, and large designs pipeline the reset tree to do it. The synchroniser turns an unconstrained asynchronous question into an ordinary timing closure problem. It does not answer it.

> **Icarus reality.** Notice what is *not* in that transcript: `q_raw` looks perfectly fine. RTL simulation cannot show you a recovery violation, because it has no recovery time — the reset either was or was not high at the sampling instant, and there is no aperture. The synchroniser's entire value is invisible here. It appears in static timing analysis and in silicon, and nowhere in between. This is one of the places where "it simulated fine" is worth precisely nothing, and it is worth knowing which those places are.

For this guide's target the practical answer is simple: **use synchronous, active-low reset throughout.** Synchronous because it keeps the design fully synchronous, needs no synchroniser, avoids every recovery and removal question, and does not block FPGA register packing. Active-low for a different reason, and it is worth being honest about which: not because it matches the fabric — AMD (Xilinx) 7-series and later flip-flop control inputs are active-**High**, so an active-low reset costs an inverter there — but because it is the near-universal convention in existing RTL and in standard-cell libraries, where the asynchronous pins are named `RN` and `SN` for a reason. One convention across a whole codebase is worth more than the inverter. The asynchronous form is here so you can read other people's code and so you have the synchroniser when you need it — one per clock domain.

Two FPGA facts change the calculus. Modern FPGA flip-flops typically have **one** dedicated set/reset input, and insisting on the wrong flavour can cost fabric and block shift-register-LUT, block-RAM and DSP register packing — check the specifics against your device family's coding-style guide rather than folklore. And FPGA configuration initialises every flop from the bitstream, so a `reg [3:0] cnt = 4'h0;` declaration initialiser genuinely does define the power-up value there; on an ASIC it is a simulation-only fiction.

The last question is which registers to reset at all, and the answer is not "all of them". **Control state must be reset** — a state register, a valid or ready handshake bit, a counter that gates something, a busy flag — because a machine that can come up in an illegal state may never reach a legal one, and that is a correctness requirement. **Datapath pipeline registers usually need no reset.** The mantissa, exponent and sign registers between stages hold garbage for the first few cycles, and that is fine, because the `valid` bit travelling alongside them *is* reset and nothing downstream acts on garbage that is not marked valid. Resetting them buys nothing and costs real money: reset is a high-fanout net, and removing thousands of loads from it makes the design far easier to time. The rule to remember is **reset the bits that decide, not the bits that carry.**

> **Seed for chapter 11.** When the adder becomes a pipeline, this is the line you draw. The registers carrying aligned mantissas, exponent differences and shift amounts down the pipe get no reset; the `valid` pipeline and any stall or flush control bits get one. If you find yourself resetting a 24-bit significand register, ask what would consume it before it is written, and the answer is usually nothing.

## State Machines

A finite state machine is the first thing in this guide that *combines* both kinds of logic: a state register, which is the clocked template, plus next-state and output decode, which is the combinational template. Everything in the last four sections shows up at once, which is why it comes here. There are three standard coding styles, and `fsm.v` contains the same machine — wait for `go`, be busy for two cycles, pulse `done` — written all three ways so they can be run side by side, with the state encoding as `localparam` rather than magic numbers. Here is the style to reach for by default, complete:

```verilog
module fsm_two_block
  (input  wire       clk,
   input  wire       rst_n,
   input  wire       go,
   output reg        busy,
   output reg        done,
   output wire [1:0] state);

  localparam [1:0] S_IDLE = 2'd0,
                   S_RUN1 = 2'd1,
                   S_RUN2 = 2'd2,
                   S_DONE = 2'd3;

  reg [1:0] s_state, s_next;

  always @(posedge clk)
    if (!rst_n) s_state <= S_IDLE;
    else        s_state <= s_next;

  always @(*) begin
    s_next = s_state;                     // default: hold state
    busy   = 1'b0;                        // default: outputs deasserted
    done   = 1'b0;
    case (s_state)
      S_IDLE:  if (go) s_next = S_RUN1;
      S_RUN1:  begin busy = 1'b1; s_next = S_RUN2; end
      S_RUN2:  begin busy = 1'b1; s_next = S_DONE; end
      S_DONE:  begin done = 1'b1; s_next = S_IDLE; end
      default: s_next = S_IDLE;
    endcase
  end

  assign state = s_state;

endmodule
```

One clocked block holding the state, one combinational block computing the next state and the outputs. Every rule from earlier is visible: `<=` in the clocked block and `=` in the combinational one, `@(*)` rather than an explicit list, an unconditional default for every variable the combinational block writes, and a `default:` arm. That `s_next = s_state;` on the first line is the FSM form of the latch cure — without it, a `case` arm that forgets to assign `s_next` infers a latch on your machine's next state, which is a spectacularly bad place for one. The style reads like the state diagram and the outputs line up with the state they are named for, which makes it the easiest to review against a specification; the cost is that the outputs are **combinational**, so they can glitch within the cycle and add delay to whatever they drive.

The **one-block style** puts everything in the clocked block:

```verilog
  always @(posedge clk)
    if (!rst_n) begin
      s_state <= S_IDLE;
      busy    <= 1'b0;
      done    <= 1'b0;
    end
    else begin
      busy <= 1'b0;                       // default: outputs deasserted
      done <= 1'b0;
      case (s_state)
        S_IDLE:  if (go) begin s_state <= S_RUN1; busy <= 1'b1; end
        S_RUN1:  begin s_state <= S_RUN2; busy <= 1'b1; end
        S_RUN2:  begin s_state <= S_DONE; done <= 1'b1; end
        S_DONE:  s_state <= S_IDLE;
        default: s_state <= S_IDLE;
      endcase
    end
```

It is compact, only one assignment operator is in play so the blocking mistake cannot happen, and every output is registered for free — glitch-free and good for timing. The catch is in the `S_IDLE` arm: `busy` must be asserted *in the state before* the one it belongs to, because the assignment lands a cycle later, and that gets harder to read as the machine grows.

The **three-block style** buys back both properties: state register, next-state decode, then a separate output decode that is registered — the trick being that the output decode reads `s_next`, not `s_state`:

```verilog
  always @(*) begin
    busy_c = 1'b0;                        // unconditional defaults: these two
    done_c = 1'b0;                        // lines are what make the empty
    case (s_next)                         // `default:` arm below safe. On its
      S_RUN1, S_RUN2: busy_c = 1'b1;      // own, `default: ;` assigns nothing
      S_DONE:         done_c = 1'b1;      // and cures no latch at all.
      default:        ;
    endcase
  end
```

Decoding `s_next` cancels the register's one-cycle delay exactly, so the outputs are registered *and* in the right cycle. It is also the most code, and overkill for four states. Read the comment on that `default: ;` carefully, because it is the trap from "The Accidental Latch" above wearing a disguise: the empty arm is safe **only** because `busy_c` and `done_c` are unconditionally assigned two lines earlier. Delete those two lines and this block latches both outputs while still looking like it has a `default:`.

Does the choice change the behaviour? `tb_fsm.v` runs all three off one clock with one `go` pulse:

```
  t=10 go=0 | one-block 0 0 0 | two-block 0 0 0 | three-block 0 0 0
  t=20 go=0 | one-block 1 1 0 | two-block 1 1 0 | three-block 1 1 0
  t=30 go=0 | one-block 2 1 0 | two-block 2 1 0 | three-block 2 1 0
  t=40 go=0 | one-block 3 0 1 | two-block 3 0 1 | three-block 3 0 1
  t=50 go=0 | one-block 0 0 0 | two-block 0 0 0 | three-block 0 0 0
  t=60 go=0 | one-block 0 0 0 | two-block 0 0 0 | three-block 0 0 0
```

Each group is state, `busy`, `done`. All three are identical in every row — same state sequence, same output cycles. The choice is about readability and about where the outputs are registered, not about what the machine does. Learn the two-block style as your default, reach for three blocks when a downstream path needs a registered output, and keep one block for machines small enough to hold in your head.

The other axis is *what the outputs depend on*. A **Moore** output is a function of state only; a **Mealy** output is a function of state *and* the current inputs. Mealy machines usually need fewer states and respond a cycle earlier; Moore outputs are stable for a whole cycle and cannot glitch on input noise. The `mealy_registered` module in `fsm.v` has `assign mealy_y = st & x;` and the same term through a flop, and the second half of the transcript is the part to stare at:

```
-- Mealy responds a cycle earlier than the same term registered
  t=70 x=1 mealy_y=1 reg_y=0
  t=80 x=1 mealy_y=1 reg_y=1
  t=90 x=1 mealy_y=1 reg_y=1
-- and it moves with no clock edge at all
  t=91 x=1 mealy_y=1 reg_y=1
  t=92 x=0 mealy_y=0 reg_y=1
PASS tb_fsm (three styles agree; Mealy is combinational)
```

The Mealy output asserts at t=70 and the registered one at t=80: one cycle earlier, as advertised. But look at the last two lines. Between t=91 and t=92 there is **no clock edge**. `x` dropped and `mealy_y` followed it immediately, while `reg_y` did not move. A Mealy output is a wire from your inputs to your outputs, and it inherits their glitches, their timing and their asynchrony.

Be careful with the name, because this is mis-taught constantly. `reg_y` is **not** a Moore output. It is `st & x` sampled by a flop, so it is a function of the *previous* state and the *previous* input: a registered Mealy. Registering a Mealy output buys you Moore's stability — one value per cycle, no mid-cycle motion, which is what the transcript shows — without making it a function of state alone. A genuine Moore output here would be a decode of `st` and nothing else.

> **Trap.** Never feed a Mealy output into another module's clock or asynchronous reset, and think hard before feeding one into another state machine's input — you are building a combinational path between two state machines, and it will turn up on your critical path with both machines' decode logic in it.

A word on encoding, because the choice matters less than it looks. **Binary** uses `ceil(log2(N))` flops and the most decode logic; **one-hot** uses one flop per state, making next-state logic a small OR and output decode a single bit test, which usually wins on an FPGA where a flip-flop sits beside every lookup table anyway; **Gray** changes one bit per transition and earns its place only when crossing a clock domain or minimising switching power. The note that surprises everyone: **synthesis tools re-encode state machines by default**, so writing binary `localparam`s does not mean you get binary flops.

Finally, the idiom that makes all of this survive maintenance. Give `s_next` and **every** output an unconditional default at the top of the combinational block, then write only the exceptions in each `case` arm. That guarantees no latches however many states and outputs you add later, and it makes each arm read as "what is different about this state", which is how a state diagram reads. One clause about the `default:` arm of a state machine in particular: assigning `x` there tells the synthesiser the illegal states are don't-cares, which licenses it to optimise the recovery away completely. That is why safe-FSM extraction exists as a separate synthesis option — Vivado's `FSM_SAFE_STATE`, Quartus's safe state machine. In a state machine, name a real recovery state in the `default:` arm and mean it.

> **Seed for chapter 11.** A multi-cycle floating point adder decomposes into almost exactly this machine, one state per step: idle, unpack, align, add or subtract, normalise, round, pack, done. Each state's datapath is combinational — chapter 1's shifters, adders and leading-zero counter — and the machine only decides which is active and when its result is captured. That control/datapath split is the whole idea, and rounding's ability to force a second normalisation is why it would need a state machine and not a counter. This guide does not build the multi-cycle version: chapter 11 goes straight to the pipeline, where the states become stages, the state register becomes the `valid` bit travelling down the pipe, and every stage boundary is a non-blocking assignment. The decomposition is the same, and it is the one to have in your head when you read someone else's FPU.

## Simulation Artifacts That Will Cost You an Evening

These are not design bugs. They are the simulator doing something correct that you did not ask for, and each is worth recognising by shape, because otherwise each costs you an evening of blaming the wrong module. The first four are testbench failures rather than RTL failures, and chapter 4 is where testbenches become the subject; they are here because you will hit them before you get there.

**The clock that never starts.** `always #5 clk = ~clk;` is the standard testbench clock, and it has one failure mode: `~x` is `x`, so a clock that begins at `x` stays at `x` forever. `bad_clkinit.v` runs three of them — never initialised, initialised at its declaration, and initialised from an `initial` block:

```
  t=1 clk_bad=x clk_decl=0 clk_init=0
  t=6 clk_bad=x clk_decl=1 clk_init=1
  t=11 clk_bad=x clk_decl=0 clk_init=0
  t=16 clk_bad=x clk_decl=1 clk_init=1
  t=21 clk_bad=x clk_decl=0 clk_init=0
  rising edges seen: clk_bad=0 clk_decl=3 clk_init=3
PASS bad_clkinit (an x clock never starts)
```

Zero rising edges in twenty-six nanoseconds. No clocked block ever runs, the design stays `x`, and you spend an hour blaming reset or a mis-wired port. Both cures work; this guide's idiom names the half period once and puts the initial value where you can see it:

```verilog
  localparam CLK_HALF = 5;

  reg clk = 1'b0;
  always #CLK_HALF clk = ~clk;
```

**Stimulus on the wrong edge.** Change a design input at the instant the design samples it and you have written the race from "How a Simulator Actually Runs Your Code" above, with the testbench as one of the two processes; there is no setup time in RTL simulation, so the outcome depends on process ordering. `bad_tbedge.v` puts two identical D flip-flops side by side, one driven from a `posedge clk` block — the edge the design samples — and one from a `negedge clk` block. Both are asked for a one-cycle pulse:

```
  t=10 | d_same=0 q_same=0 | d_opp=0 q_opp=0
  t=20 | d_same=1 q_same=0 | d_opp=1 q_opp=0
  t=30 | d_same=0 q_same=0 | d_opp=1 q_opp=1
  t=40 | d_same=0 q_same=0 | d_opp=0 q_opp=0
  t=50 | d_same=0 q_same=0 | d_opp=0 q_opp=0
  t=60 | d_same=0 q_same=0 | d_opp=0 q_opp=0
PASS bad_tbedge (same-edge stimulus swallowed the pulse)
```

`d_opp` pulses and `q_opp` captures it a cycle later. `d_same` pulses too — the `1` is there at t=20 — and **`q_same` never goes high at all.** The pulse was silently dropped. The design is fine; the testbench is broken, and it looks exactly like a design bug.

The mechanism is the block-ordering alternation from earlier: at one edge the design ran first and read the old `0`, at the next the stimulus block ran first and cleared `d_same` before the design read it, so the `1` was never visible at any sampling instant. Hence the rules for every testbench from here on. Drive design inputs on `negedge clk` when the design samples on `posedge clk`, or drive them with `<=` from a `posedge` block, which is safe for exactly the reason non-blocking pipeline registers are. Sample outputs on `negedge` or with `$strobe`, and never mix conventions inside one testbench. Chapter 4 turns that from a warning into a testbench structure.

**Printing the wrong value.** `$display` runs in the active region, at the point of the call; `$strobe` and `$monitor` run in the monitor region, once every value in the slot has settled — measured in `tb_regions.v` above. That one fact is the origin of the commonest confusion in RTL debugging, "why is my log one cycle off from my waveform?", and neither is wrong: the log is right about the active region, the waveform about the whole slot.

**`x` that never goes away.** A register with no reset does not hold "random garbage that settles". `tb_xprop.v` runs an unreset counter alongside a synchronously reset one:

```
  t=10 rst_n=0 | no_rst=xxxx with_rst=0000 sum_bad=xxxxx any_bad=x any_ok=0
  t=20 rst_n=0 | no_rst=xxxx with_rst=0000 sum_bad=xxxxx any_bad=x any_ok=0
  t=30 rst_n=1 | no_rst=xxxx with_rst=0001 sum_bad=xxxxx any_bad=x any_ok=1
  t=40 rst_n=1 | no_rst=xxxx with_rst=0010 sum_bad=xxxxx any_bad=x any_ok=1
  t=50 rst_n=1 | no_rst=xxxx with_rst=0011 sum_bad=xxxxx any_bad=x any_ok=1
PASS tb_xprop (x is permanent and contagious)
```

`no_rst` is `x` after five rising edges and will be `x` after five million, because `x + 1` is `x`. And it is contagious: the adder downstream is `x`, and so is `any_bad`, which is `|no_rst` — the reduction OR that chapter 2's "Reduction Operators and the Sticky Bit" introduced as the floating point sticky bit. An unreset mantissa makes the sticky bit `x`, which makes the rounding decision `x`, which makes the entire result `x`. Keep that chain in mind when a waveform full of red appears in chapter 9.

Real hardware behaves differently: a flip-flop with no reset powers up holding *some* definite value, unknown to you but not a third state. Hardware has garbage-but-defined, simulation has `x`, which makes RTL **pessimistic** here — it shows failures hardware would not have, usefully, because it is telling you the design depends on a value you never specified. Gate level has its own pessimism: a netlist mux with an `x` select and both data inputs at 1 reports `x`, where RTL's `if (x) a = 1; else a = 1;` gives a confident and correct `1`. But RTL is **optimistic** too, and that is the direction that hurts: `if (sel) y = a; else y = b;` with `sel === 1'bx` silently takes the `else` branch and reports a confident `y = b`, when the real part could produce either. That is how a design with an unreset control bit passes an entire regression and fails on the bench. `x` propagation is a heuristic, not a sound approximation in either direction. Treat any `x` in a waveform as a bug until proven otherwise, and fix it by resetting the register *or* initialising it in the testbench — not by sprinkling resets everywhere, which pays hardware cost to clean up a simulation artifact.

**`#` inside logic.** `bad_combdelay.v` puts a three-nanosecond delay inside a combinational block, `always @(*) begin #3 y_delay = ~a; end`, next to the same expression written plainly, then applies a two-nanosecond pulse to the input:

```
  t=1 a=0 | y_plain=1 y_delay=x
  t=4 a=0 | y_plain=1 y_delay=1
  t=10 a=0 | y_plain=1 y_delay=1
  transitions: y_plain=3 y_delay=1
PASS bad_combdelay (a pulse invisible to the delayed block)
```

It compiles clean under `-Wall`, it simulates, and it produces plausible numbers. It is also not synthesisable — synthesis ignores `#` delays outright, so the netlist has no `#3` in it and RTL and gates disagree by construction. Worse is the transition count: `y_plain` moved three times and `y_delay` once, because **while the block is waiting out its delay it is not sensitive to anything.** The input pulse arrived inside the window and was lost. A `#` in a combinational block turns logic into a sampler with an undocumented aperture. `#` belongs in testbenches; in a file that will be synthesised it is a bug.

**Two blocks writing one variable.** `bad_multidrive.v` has two `always` blocks assigning the same `reg`:

```
  after a pulse on trig_a       : r=a
  after a pulse on trig_b       : r=5
  after trig_a again            : r=a
PASS bad_multidrive (whichever block ran last wins)
```

Legal Verilog, last-writer-wins, and **unsynthesisable** — no gate does this. Contrast two `assign` statements driving one `wire`, which chapter 2 demonstrated as a genuine multiple-driver contention resolving to `x`; the variable version does not even give you that warning sign. One signal, one driver, always. That is Cummings' Guideline #6, and it is the hardware version of "no two threads write the same variable without a lock".

> **Icarus reality.** Exactly one mistake in this chapter is refused outright, and you have met it before — chapter 2 quoted the same diagnostic. An `always` block with no event control and no delay — `always y = ~a;`, written meaning "y is always `~a`" — is a zero-delay infinite loop, and rather than hanging, Icarus rejects it at compile time: `error: always process does not have any delay. : A runtime infinite loop will occur.` That is `bad_zerodelay.v`, the chapter's only `xfail` target. It is worth meeting twice, because it is the entire list.

## What the Simulator Will and Will Not Tell You

Every bug in this chapter has now been demonstrated with a running program. It is time to count how many of them the tooling actually reported.

Every file in `src/ch03/` whose name begins with `bad_` was compiled with `iverilog -g2012 -Wall`, which is the strictest invocation this toolchain has. Here is the complete result, alongside what genuinely does catch each one. Read the third column as a claim about *kinds* of tool — a simulator, a synthesis tool, a linter, a self-checking testbench, or a human following a rule — because the whole argument of this section is that they catch different things and only one of them is in front of you.

| Bug | Icarus 13.0, `-g2012 -Wall` | What actually catches it |
|---|---|---|
| Incomplete sensitivity list | **silent** | `always_comb`, whose list is computed rather than typed — and Icarus does implement that; a testbench that toggles every input independently. Not synthesis: it builds the real cone and says nothing. |
| Inferred latch, incomplete `if` | **silent** | the synthesis log; a linter (Verilator documents a `LATCH` check); a behavioural hold test, which is what `tb_latch.v` is |
| Inferred latch, incomplete `case` | **silent** | the same three |
| Either latch above, rewritten under `always_comb` | **silent** | a tool that implements IEEE 1800's recommended check — Vivado, Questa, VCS, Verilator. Measured here: **not Icarus** (`bad_svalways.v`). |
| Blocking assignment in a clocked block | **silent** | a linter (Verilator's `BLKSEQ` class); code review; a test that checks a signal takes N cycles to arrive. Not synthesis: it infers one flop and two wires and reports nothing. |
| Blocking assignment inside `always_ff` | **silent** | the same three. Measured: the keyword changes nothing on this simulator (`bad_svalways.v`). |
| Blocking assignment that works by luck of statement order | **silent** | a linter — `BLKSEQ` again, because the construct is identical and statement order is irrelevant to it; code review. **No test can distinguish it**, because it is functionally correct. |
| Two `always` blocks writing one `reg` | **silent** | synthesis, as a multiple-driver error; a linter (Verilator's `MULTIDRIVEN`); code review |
| `#3` delay inside `always @(*)` | **silent** | a lint rule banning `#` in a synthesisable file. Nothing else reports it: synthesis silently ignores the delay, and RTL and netlist then disagree. |
| Race between two same-edge `always` blocks | **silent** | the coding rule that makes it unwritable (`<=` in every clocked block); reordering the source and diffing the output; a second simulator. **Not** re-running — measured byte-identical here. |
| `posedge` on a multi-bit signal | **silent** | code review, and a coding rule banning any vector in an edge expression. Nothing in this flow reports it. |
| `@*` sensitised to a whole array | **warns** | Icarus — one of only two warnings it emits anywhere in this chapter |
| `@*` sensitised to a whole vector | **silent** | Icarus, but only with `-Wsensitivity-entire-vector`, which `-Wall` does not include |
| `always` with no event control and no delay | **compile error** | Icarus, at elaboration — the chapter's only `xfail` target |

Fourteen bugs; one warning at `-Wall`; one further warning available only if you name a class `-Wall` leaves out; one compile error. Everything else is silence, and the one thing `-Wall` volunteers is the construct on that list least likely to be a bug. `bad_svalways.v` does emit a second `-Wall` warning, but it is not about any row here: it comes from a third module in that file written specifically to provoke the one `always_*` rule Icarus enforces, which is that an `always_ff` sensitivity list be edge-only.

Four of those cells name a Verilator warning class. Verilator is not installed in this environment, so unlike almost everything else in this chapter those class names come from its documentation rather than from a run here. The Icarus column is measured, all fourteen rows.

It gets slightly worse when you go looking for more. `-Wextra` does not exist; Icarus answers `Ignoring unknown warning class extra` and carries on compiling. `-Wall` on this build is documented in `man iverilog` as exactly seven classes — `anachronisms`, `implicit`, `macro-replacement`, `portbind`, `select-range`, `timescale` and `sensitivity-entire-array` — and none of the other six are about anything in this chapter. `sensitivity-entire-vector` exists but is not in `-Wall`. And `infloop`, which is documented for precisely the self-triggering combinational block described in "Sensitivity Lists, and What `@(*)` Really Covers" above, did not fire on the textbook case: a three-line module containing `always @(*) y = y + a;` compiled silently both with `-Wall` and with `-Wall -Winfloop` on this machine. Do not promise yourself that flag will find your loop.

A second piece of standard advice also fails here, and it fails more interestingly. **"Run it again and see if the answer changes" does not reveal a race.** Textbook descriptions emphasise non-determinism, which leads people to expect flakiness. Icarus is not flaky: `tb_race.v` produces byte-identical output on every run, and so does the swallowed pulse in `bad_tbedge.v`. A race here is a stable, reproducible, confident wrong answer. What *does* change the answer is editing something apparently unrelated — swapping two independent `always` blocks, as `race_ab` and `race_ba` show — and within one run the `BLOCK-A` / `BLOCK-B` trace showed the order alternating from one time step to the next. So a race does not present as randomness. It presents as *this worked yesterday, and all I changed was moving a block.* Learn that sentence; it is the symptom.

None of this is a criticism of Icarus. A simulator's job is to execute the procedural semantics of the language faithfully, and it does. A latch does not exist in those semantics — it is what a *synthesis* tool would build from code that holds a value, and there is no synthesis tool in this flow. A missing signal in a sensitivity list is not an error either; it is a legal, precisely specified event control that, as far as the simulator can tell, you wrote on purpose. The tool answers the question you asked. The problem is that it is not the question you care about.

Which leaves four detectors. The **synthesis tool** is the best latch and multiple-driver detector available and comes free with any FPGA toolchain, so read its log every build and grep it for "latch". A **linter** — Verilator in `--lint-only -Wall` mode is the cheapest to install next to Icarus — catches latches, blocking assignment in a clocked block and multiple drivers without a full synthesis run, and it is the only tool within reach that catches the *accidentally correct* blocking assignment, because it reads the construct and does not care what order you typed the statements in. A **self-checking testbench** catches behavioural consequences: an output that fails to move, a pulse in the wrong cycle, a value that persists when it should not, which is exactly what `tb_latch.v` and `tb_sens.v` do. And then there is the class where **no simulation can help at all**, however good the testbench: the accidentally correct blocking assignment again, the vector in an edge expression, the race currently giving you the answer you wanted. All three are plainly visible in the source text and completely invisible in a waveform. For the first, run the linter. For the other two the detector is **a careful reader following coding rules**, and there is no substitute.

That is the argument for the rules. If you could test your way to correct RTL, coding standards would be a matter of taste. You cannot, so they are not: you follow guidelines that make the bugs impossible to write, because the alternative is relying on tools that have been shown, above, not to be looking.

## Bridge to Chapter 4

You can now describe both kinds of logic and, more importantly, defend the descriptions: you know why `<=` belongs in a clocked block because you have seen the region it updates in, and you know why a latch appears because you have watched one hold a value across an input change. What you have also learned is that the tool in front of you is largely silent, which shifts the weight onto the thing that has been quietly doing the work in every experiment in this chapter — the testbench. Every transcript here came from a self-checking program that knew what the answer should be and said so. Chapter 4 makes that the subject rather than the scaffolding: how to structure a testbench, how to generate and apply stimulus, how to compare against a reference, what `$dumpfile` and `$dumpvars` do and how to read the resulting waveform in GTKWave or its maintained successors, and how to build the whole thing into a command you can run on every commit. You have written a dozen testbenches by accident already. Now write them on purpose.
