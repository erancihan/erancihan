## The Green Run That Means Nothing

Chapter 4 finished with fourteen green targets and one confession. Of eight wrong carry-out functions bolted onto its 8-bit adder, seven died. The eighth:

```verilog
  assign sum  = a + b;
  assign cout = a[7] | b[7];          // WRONG. Deliberately.
```

Every vector in that chapter agrees with it and every testbench passes. The regression is green, the exit codes are honest, the checks use `!==` and count what they find — and the design is wrong.

How wrong? Run all 65,536 operand pairs through the real adder and this one side by side — `tb_exhaustive.v` in `src/ch05/` does exactly that, in under a second, and reports `pairs=65536  adder8 mismatches=0  mutant disagreements=16512 (25.195 %)`.

**A quarter of all possible inputs produce the wrong carry out.** Not a corner case, not a subtle disagreement in the last place — one input in four, and a thorough-looking suite never touched one of them.

That gap is this chapter. Chapter 4 taught you to build the instrument; this one asks what the instrument cannot answer about itself — *which inputs, how many, and how do you know when you have enough?* You will get four answers and see all four applied to the mutant above: one kills it in about four vectors without anyone knowing what the bug was, one proves it dead, and one would have made the hole visible before anybody thought to break anything. Everything below was compiled with **Icarus Verilog 13.0** and run under `vvp` here, cross-checked with `python3` where the claim is arithmetic; every listing is a file in `src/ch05/`, all twelve targets green.

## Testing, Verification, and What "Done" Means

Three words get used interchangeably and mean different things. **Testing** is running the design and looking at what comes out. **Verification** is establishing that the implementation matches its specification — *did we build the thing right?* **Validation** is establishing that the specification was right — *did we build the right thing?* Chapter 4 taught testing; this chapter is verification. Validation appears once in this guide and has happened already: choosing IEEE 754-2019 binary32 as chapter 12's specification rather than "an adder that seems to work". A verification argument is always relative to a specification you can point at; without one you are not verifying, you are playing.

Split a testbench in half and the halves fail independently. **Stimulus** asks *did we ever reach the interesting state?* **Checking** asks *if we had, would we have noticed?* Chapter 4's suite had excellent checking — `!==` comparisons, an error count, `$fatal` — and stimulus that never once produced an operand of 128 or more with a sum that did not overflow. Perfect checking of a state you never entered verifies nothing, and so does perfect stimulus into a checker that cannot fail. **Coverage** measures the first, **mutation testing** the second.

Hardware makes this expensive in a way software does not: there is no patch after tapeout, so a bug found in silicon is a respin. The canonical example is Intel's 1994 FDIV bug — an error in a lookup table used by floating point division, found not by Intel's own suite but by an outside mathematician doing number theory, and written off at around $475 million. Notice the *kind* of bug: rare, data-dependent, corner-case arithmetic, in a floating point unit. That is what chapter 12 has to survive. Verification is also widely reported as the majority of ASIC project effort, and the gap widens with every process node, because the state space grows exponentially in state bits. You cannot verify a 32-bit floating point adder by trying harder. You need **abstraction** (a reference model, so expected values are free), **reduction** (a narrower float of the same structure, so exhaustive testing fits) and **measurement** (coverage).

Which leaves the uncomfortable question: when are you done? There is no completeness theorem for simulation. Exhaustive testing is a proof, everything else is evidence, and for binary32 addition exhaustive is 2^64 vectors, so you will never have the proof. "Done" therefore has to be **exit criteria written down in advance**, before the deadline arrives and standards start negotiating with themselves:

1. Every corner case in "Verifying Floating Point Specifically" below has a directed test, and each has been *seen to fail*.
2. The functional coverage model reports 100 % of its bins hit, on more than one seed.
3. Several million constrained-random vectors match the reference model bit for bit, and an exhaustive pass over a reduced-width float of the same structure is clean.
4. The whole regression is green from a clean checkout, on one command.

The last carries more weight than it looks: a "done" that nobody else can re-establish on demand is a memory of a good afternoon. Those criteria belong in a **verification plan** written *before* the RTL — not bureaucracy but the only ordering that works, because once the implementation exists your idea of what could go wrong is contaminated by what you happened to build. A plan derived from the specification lists features you have not implemented yet, which is how you discover you forgot one, and it carries an explicit **out of scope** list as a deliverable rather than an omission.

## The Reference Model

Chapter 4's vector file has eight lines. That is not an accident of taste — it is the number of expected values a person will compute by hand. A hand-built suite therefore stops at a few dozen vectors, exactly the size at which `cout = a[7] | b[7]` hides comfortably.

A **reference model** removes that cost. It is an independent implementation of the specification whose only job is to say what the answer should be; drive the same stimulus into design and model, and compare. The unbounded "is this right?" becomes the bounded "do these two disagree?", and because expected values are now free, *stimulus* is the only thing you pay for — ten thousand random vectors and 65,536 exhaustive ones in one afternoon. This is the most valuable idea in the chapter and everything else depends on it.

It has one failure mode and it is fatal: if the model shares the design's bug, the comparison passes forever. Same author, same misreading, same wrong answer twice, green run. Real independence means **decorrelating** the model on purpose. Use a **different abstraction level** — the RTL unpacks, aligns, adds, normalises, rounds and packs in stages, while the model says `z = x + y`, leaving no shared structure for a bug to live in. Use a **different language or engine**, since a Python model and a Verilog design cannot share a typo. And write it **from the specification, ideally before the RTL**: a model that calls the design's own rounding function leaves rounding unverified.

Even the integer testbenches in `src/ch05/` observe this. None checks `adder8` against `a + b`, which would be the design's own expression copied into the testbench; they call a `ref_add` function that ripples a carry through eight full adders, written from the definition of binary addition. Six lines longer, and it cannot share a typo with `assign {cout, sum} = a + b;`.

A model can live in four places, in rising order of independence and trouble: a `function` in the testbench, a separate behavioural module, the simulator's own `shortreal` arithmetic, or an external Python program writing golden files for `$readmemh`. The first two share a language and usually an author; the last is strongest and costs a two-step build and stale files.

The third is remarkable value for binary32, and chapter 2 already found it: **Icarus 13.0 supports `shortreal` with `$shortrealtobits` and `$bitstoshortreal`**, so the host's own IEEE 754 arithmetic is available inside the simulation as a golden model, free. It needs `-g2005-sv` or later — at `-g2005` the keyword is a syntax error — so the standing `-g2012` covers it. `tb_fpref.v`'s whole model is a nine-line `function [31:0] fp_add` with two `shortreal` locals: convert both operands with `$bitstoshortreal`, add, return `$shortrealtobits(fx + fy)`.

Driven through twenty-eight corner cases and compared against expected bit patterns computed independently in `python3` with `struct.pack('>f')`, it agrees on every one. Six lines of that run, chosen because they are the cases people get wrong — and note D2's `ffc00000`: this host's `inf+(-inf)` NaN arrives with its sign bit set, which is legal (a NaN's sign and payload are unspecified) and is why the suite compares NaN by class and quietness, never by bits:

```
  A2 (+0)+(-0)             00000000 + 80000000 = 00000000  ZERO+ZERO->ZERO
  B4 subnorm->normal       007fffff + 00000001 = 00800000  SUBNORM+SUBNORM->NORMAL
  C2 sNaN+1.0 -> quiet     7fa00000 + 3f800000 = 7fe00000  NAN+NORMAL->NAN
  D2 inf+(-inf) -> NaN     7f800000 + ff800000 = ffc00000  INF+INF->NAN
  G1 tie down (lsb 0)      4b800000 + 3f800000 = 4b800000  NORMAL+NORMAL->NORMAL
  G1 tie up   (lsb 1)      4b800001 + 3f800000 = 4b800002  NORMAL+NORMAL->NORMAL
PASS tb_fpref (28 corner cases, shortreal agrees with python3 on every one)
```

Read the last two lines together: the same operand `3f800000` added to neighbouring values rounds *down* in one case and *up* in the other, because round-to-nearest-even breaks a tie towards the even significand. A suite with only one of those vectors passes a design that always rounds ties up. That pair is worth more than a thousand random vectors, and no random campaign will produce it.

Now the trap, and it is the most dangerous thing in this guide.

> **Trap.** **Icarus stores a `shortreal` internally as a C `double`.** Arithmetic happens in binary64 and is rounded to binary32 only at `$shortrealtobits`. A single add survives that — double rounding binary32 → binary64 → binary32 is provably harmless for `+`, because 53 ≥ 2×24 + 2 — but a *chain* does not. The intermediate keeps precision binary32 does not have, and your reference model quietly becomes **more accurate than the specification**, which makes it mark a **correct** design wrong on exactly the rounding cases this guide exists to get right. The fix is one line: round-trip through the bit functions after every operation. One honesty note: you cannot yet *verify* any of these bit patterns — binary32 encoding is chapter 7's subject — so until then, take the pattern and the reason on trust.

`bad_srchain.v` runs both forms on 2^24 and 1.0, where the binary32 answer to both adds is 2^24. The natural way is `z = x + y; w = z + y;`; the correct way forces every intermediate back through the bit functions — `z = $bitstoshortreal($shortrealtobits(x + y));`, and the same for `w`. Side by side:

```
  x = 4b800000 (2^24), y = 3f800000 (1.0)
  CHAIN      z=4b800000  w=4b800001
  ROUND-TRIP z=4b800000  w=4b800000
  binary32 truth for both:  4b800000
  a CORRECT dut result of 4b800000 against the chained reference: reported as WRONG
  the same result against the round-tripped reference:        PASS
```

Three things there. `z` agrees either way, so the damage is invisible for one operation and appears at the second — you will have shipped the pattern before you meet the failure. The correct result `4b800000` is *reported as wrong* by the chained reference, which is the whole cost: a reference model that is too good trains you to ignore failures. And the file's last line shows `$display("%f", x + y)` printing `16777217.000000` about bits reading `4b800000`. **Compare and print bits, never `%f`.**

> **Seed for chapters 9 and 12.** Chapter 9's **two-input** adder performs one add per transaction, so the simple `$shortrealtobits(fx + fy)` form is legitimate *there* — and only there. Chapters 10 and 12 are the **four-input** adder, whose reference chains **three** adds, and every intermediate must round-trip through the bit functions or the reference silently becomes binary64. The cost of skipping that, measured over 200,000 random normal quadruples: the chained reference disagrees with true binary32 on **1.298 %** of them in tree order (2,595 of 200,000) and 1.295 % sequentially — about **one transaction in 77**, or roughly 13,000 false failures per million vectors against a *correct* design.

So: `shortreal` as the primary in-simulator reference for volume, `python3` `struct` as a second independent check over the corner cases — which is what `tb_fpref.v`'s table is. Python floats are binary64 too, so every intermediate must go back through `pack('>f')`/`unpack`, and `struct.pack('>f', x)` raises `OverflowError` rather than returning infinity. Two models disagreeing is a gift: exactly one is wrong, and you know to look.

## The Shape of a Suite You Can Trust

Chapter 4's testbenches all had one `initial` block that decides what to apply, applies it and checks the answer, in the same three lines. That works to about twenty vectors and then stops, because you cannot change *what* you test without editing the code that decides *how*. Four roles, named so they stop tangling:

- **Generator** — decides *what* to test. Knows nothing about pins, edges or timing. Produces transactions.
- **Driver** — turns a transaction into pin wiggles with the correct timing. Knows nothing about what the values mean.
- **Monitor** — watches the pins and reconstructs the transaction. Passive, never drives; its independence from the driver is what catches driver bugs.
- **Scoreboard** — holds the reference model, compares, counts, and records coverage.

In SystemVerilog with a class library these become objects, and the Accellera / IEEE 1800.2 **UVM** formalises exactly this decomposition. UVM needs class support Icarus lacks, so you cannot run it here, but the ideas transfer completely and here the four roles are two `task`s, an `always` block and a `task`. `tb_scoreboard.v` is 286 lines and contains all four. The monitor is one line — `always @(posedge clk) if (active) score(a, b, sum, cout);` — and its shape is the point.

It reads `a` and `b` from the pins, not from the generator's variables. Rewrite the driver to apply `a` twice and ignore `b` — a mutation applied in a scratch tree — and the answer stops matching the reference, because the monitor reports what happened rather than what was intended. A monitor that trusts the generator cannot catch a driver. The driver holds one rule: wait for `@(negedge clk)` before assigning, the opposite edge from the monitor, as chapter 4's "Clock and Reset Without Racing Your Own Design" requires. The monitor's `active` gate obeys the same rule: it opens in the *driver*, on the same negedge as the first real vector — opened at time 0 it hands the monitor a phantom `(00,00)` at the first posedge — and closes `#1` *after* the final posedge, so the last transaction is scored whichever order the simulator resumes the processes. A gate changed on the monitor's own edge is a same-edge race.

The payoff is a swappable generator. `tb_scoreboard.v` has two — constrained random, and a replay of chapter 4's eight vectors — chosen by a plusarg and sharing one driver, monitor and scoreboard. Chapter 12 adds an exhaustive sweep and changes nothing else.

**Check every transaction, not at the end of the run.** Per-transaction checking reports the failure in context, stops the run immediately with a small legible waveform, and stores nothing; end-of-test comparison against a golden file suits out-of-order designs and is git-diffable, but decouples the failure from its cause. There is a third pattern people skip: **end-of-test assertions about the run itself**. Did the driver apply the transactions it was asked for? Did the scoreboard ever run? Did every bin fill? Those catch the test that silently did nothing, which per-transaction checking cannot, because a check that never executes never fails. `tb_scoreboard.v` ends with seven — five about the run (`driven`, `checks` and `holes` against expected counts; `checks` against `driven`; and, in replay mode, the exact per-bin profile, computed independently in `python3`) plus two mode-dependent checks on the kill counts. Know what each one can see. A phantom sample before the first vector and a dropped sample after the last *cancel* in every total, `checks` against `driven` included; what catches that pair is the pinned profile, because each moves a bin the other does not, and random mode — which has no profile to pin — relies on the monitor's gate discipline being mechanically right. The honest job of `checks` against `driven` is attribution: an *unpaired* phantom or drop points at the monitor rather than the driver. A mutation disabling the monitor is caught by the count checks, not by any check on the design.

Now the message the scoreboard prints. `$display("FAIL")` tells you a bug exists and nothing else. Compare:

```verilog
        $display("FAIL tb_scoreboard: [%0t] check=%0d a=%02h b=%02h exp=%03h got=%03h xor=%03h",
                 $time, checks, ta, tb, want, got, want ^ got);
```

Every field earns its place. `$time` positions the waveform cursor, `check=%0d` says which of forty thousand transactions, and **the inputs are the reproducer**. `exp` and `got` share a radix and width. And `exp ^ got` is the cheap masterstroke: the xor names the *category* of the bug before you open anything. The same file against an `adder8` with its carry-out tied to zero:

```
FAIL tb_scoreboard: [15000] check=1 a=5c b=ce exp=12a got=02a xor=100
FAIL tb_scoreboard: [25000] check=2 a=c6 b=f3 exp=1b9 got=0b9 xor=100
```

Every line reads `xor=100`: bit 8 and nothing else, so the sum is perfect and the carry-out is the whole problem. In binary32 the field is even more useful — `00000001` is a last-place rounding bug, `00800000` an exponent off by one, `80000000` a sign bug.

Two habits go with the counting: give every test a **stable identifier**, and keep tests **order independent**, checked by running the suite in reverse and each test alone. Order dependence is how a suite silently loses power: test 40 passes only because test 39 left the right value behind.

Which brings back the rule chapter 4 ended on, now with a number attached. **A test you have never seen fail is not a test.** A checker with a typo, a monitor on the wrong edge, a comparison against a value taken from the design, a loop that runs zero times — all pass forever, in silence. The cure is **mutation testing**: break the design and confirm the suite goes red. The mechanics are chapter 4's "Automating the Build" pointed at a copy: mutate a *scratch copy* of the source, rebuild with the same one command, score a kill on `FAIL` or a non-zero exit, restore, verify the restore. This chapter's code was mutated forty-one times, thirty-seven kills and four survivors, recorded in `src/ch05/README.md`. That ratio is a **mutation score**, worth writing down because it makes "we tested it" comparable across chapters — provided the mutant sets are: a score over eight carry functions and one over forty-one mixed mutations are different measurements.

More useful than the score is what you do with a survivor. **A surviving mutant is a work item**: either the suite has a real gap, so fix it, or the mutation cannot change behaviour, so argue that in writing. Chapter 4's lesson stands — *a mutant that survives your stimulus is a gap in your stimulus long before it is an equivalent mutant.* Two survivors here were real gaps. Rewriting `counter6` to count *downwards* passed every assertion, because "q is never more than 5" is just as true backwards, so `tb_assert.v` gained a value-sequence check. And an *asynchronous* reset — chapter 4's own open concern on `counter4`, come home — passed every target, because `rst` only ever changed on a driving edge; so the stimulus now raises `rst` strictly between edges and requires `q` to wait for the clock. The most interesting of the four that remain is a blind spot rather than a gap — replacing `tb_exhaustive.v`'s reference model with the design's own output survives, because the comparison becomes a value against itself. Mutation testing measures your checking; it cannot measure a reference model that *is* the design.

That is the machinery. It still does not tell you which vectors to feed it.

## Choosing Stimulus: Directed, Exhaustive, Random

Understand the bug first, because the whole argument rests on it. The true carry-out of an 8-bit adder is `(a[7] & b[7]) | ((a[7] ^ b[7]) & c7)`, where `c7` is the carry out of the low seven bits — `c7 = 1` exactly when `a[6:0] + b[6:0] ≥ 128`. Against `a[7] | b[7]`, in the four cases of the top bits:

| `a[7]` | `b[7]` | true `cout` | mutant | agree? |
|---|---|---|---|---|
| 0 | 0 | always 0 (the most is 127+127 = 254) | 0 | always |
| 1 | 1 | always 1 (the least is 128+128 = 256) | 1 | always |
| 0 | 1 | `c7` | 1 | only when `c7` = 1 |
| 1 | 0 | `c7` | 1 | only when `c7` = 1 |

So the mutant is wrong on exactly one class of input, and that class has a plain-English name:

> **exactly one operand has its top bit set, and the sum does not actually overflow** — one of `a`, `b` is at least 128, and `a + b ≤ 255`.

Count them. With `a[7] ^ b[7] = 1` we have `a + b = 128 + (a[6:0] + b[6:0])`, so `a + b < 256` exactly when the low halves sum below 128 — `Σ(s=0..127)(s+1) = 8256` pairs in each mixed class. Twice 8256 is **16,512 of 65,536 pairs, or 25.195 %**, reproduced two ways and agreeing to the pair: an exhaustive loop in `python3`, and `tb_exhaustive.v` under `vvp`. The smallest members are `(0,128)`, `(128,0)`, `(0,129)`, `(1,128)`, so the simplest test that would have caught this bug is `a = 128, b = 0`.

### Why a careful directed test walked past it

Ask a competent engineer to test an adder's carry logic and they write two groups: *no carry* with small numbers, *carry* with big ones. It looks complete, and it has a pleasing symmetry. `tb_directed.v` writes it out:

```verilog
    // Seven "no carry" vectors, all with small operands...
    va[0]  = 8'd0;   vb[0]  = 8'd0;
    va[1]  = 8'd2;   vb[1]  = 8'd3;
    va[2]  = 8'd15;  vb[2]  = 8'd1;
    va[3]  = 8'd63;  vb[3]  = 8'd1;
    va[4]  = 8'd100; vb[4]  = 8'd27;
    va[5]  = 8'd127; vb[5]  = 8'd1;
    va[6]  = 8'd127; vb[6]  = 8'd127;
    // ...and seven "carry" vectors, all with big ones.
```

The carry half is `255+1`, `255+255`, `128+128`, `240+32`, `192+128`, `129+127`, `255+128`, and then one more the file adds on its own account: `aa + 55`.

Every "no carry" vector has both top bits clear; every "carry" vector really carries. The blind spot is the third possibility — **a big operand with no carry** — invisible because the two groups feel like a partition of the space. The run:

```
  killed by a=aa b=55 (sum=255): true cout=0, mutant cout=1
PASS tb_directed (14 carry-focused vectors, 7 of them carrying, mutant survives all 14; 1 more kills it)
```

Fourteen thoughtfully chosen vectors, and the mutant is right on all fourteen. One more — `0xAA + 0x55`, 170 + 85 = 255, a big operand one short of overflowing — and it dies instantly.

The sentence to take away: **directed tests are written from the same mental model as the design.** The engineer who wrote `cout = a[7] | b[7]` believed a big operand means a carry; the engineer who wrote the vector file believed the same. So the vectors and the bug agree, and will go on agreeing forever, because a directed test cannot find a bug living inside your own assumption. To find it you must bring in something that does not share it, and neither randomness nor exhaustion shares any assumption at all. Notice too how *fragile* the survival is: one arbitrary vector kills it, so the mutant survived chapter 4 by an accident of vector selection.

None of that makes directed tests bad, only insufficient alone: they remain right when the case is named in the specification, when you are reproducing a bug, and when the case is astronomically unlikely under random stimulus. They are wrong as your *only* method, because their coverage is the shape of your imagination, and so are your bugs.

### Exhaustive testing: do the arithmetic out loud

If the input space fits, stop arguing and enumerate it. An 8-bit adder with a carry-in has 2^8 × 2^8 × 2 = **2^17 = 131,072** input combinations. `tb_exhaustive.v` sweeps the 65,536 pairs through both adders, comparing against the bit-serial reference, in **0.91 s** on the arm64 machine that first timed it and **1.4 s** on the Linux container that re-verified this guide, against a compile time of 0.013 s. At this size anything less than exhaustive is a decision you must justify — and what you get is not evidence, it is a proof:

```
  first mutant disagreement at pair 128: a=00 b=80 sum=128 true cout=0 mutant cout=1
  pairs=65536  adder8 mismatches=0  mutant disagreements=16512 (25.195 %)
  excluded bins proven empty: cout=1 with both MSBs clear: 0;  cout=0 with both MSBs set: 0
PASS tb_exhaustive (65536 pairs, 0 mismatches, 16512 mutant kills)
```

Now scale it up and watch it die. Two-input binary32 addition has 2^32 × 2^32 = **2^64 = 18,446,744,073,709,551,616** operand pairs. At ten million vectors a second — optimistic for an event simulator — that is 1.845 × 10^12 seconds, about **58,000 years**; at a billion a second, 585 years. The ratio to the 8-bit adder is 2^47 ≈ 1.4 × 10^14: not a bigger number of the same kind, a different universe. Chapter 10's **four-input** version is 2^128 ≈ 3.4 × 10^38.

The lesson is not "exhaustive is useless" but **reduce the space until exhaustive fits**, because exhaustive over a slice is still a proof about that slice. "Verifying Floating Point Specifically" below does that with a narrower float.

### Random, and how fast it works

`tb_random.v` throws uniform random pairs at both adders. With Icarus's default `$random` stream the first vector kills the mutant, at `a=36, b=129` — luck, and it should be reported as luck. The honest number is the second:

```
  phase 1: 200 vectors, 58 kills, first at 0
  phase 2: 2000 trials, mean vectors to first kill = 3.9075 (theory 1/p = 3.9690)
PASS tb_random (58/200 fixed-stream kills, mean 3.9075 vectors to first kill)
```

The theory is one line. The probability that a uniformly random pair lands in the killing class is p = 16512/65536 = 0.251953125, so vectors until the first kill are geometric with mean 1/p = **3.969**. Two thousand consecutive trials measured **3.9075**; an independent 200,000-trial Monte Carlo in `python3` gave 3.963. Survival follows: `(1-p)^5 = 0.234`, `(1-p)^10 = 0.0549`, `(1-p)^20 = 0.00301`, `(1-p)^48 = 8.9 × 10^-7`. **Forty-eight random vectors drive the chance of missing this bug below one in a million.** Fifty lines of loop beat fourteen lines of carefully chosen table.

Four methods, one bug, measured:

| Method | Result |
|---|---|
| Directed, carry-focused, 14 vectors | **survives** |
| One targeted vector `a=0x80, b=0x00` | **dies** — if you think of it |
| Random, Icarus default stream | dies on vector 0; 58 kills in 200 |
| Random, expected case | dies after about 4 vectors |
| Exhaustive, 65,536 pairs | dies at pair 128, 16,512 kills, 0.91 s |

Rank them by what they teach rather than by which won. **Exhaustive is definitive when the space fits** — take the proof whenever it is offered. **Random is the transferable answer**, because it still works in chapter 12 where exhaustive is impossible, and it found this bug in about four vectors without sharing anybody's assumptions. **The reference model enables both.** And **coverage** would have *prevented* the situation rather than diagnosed it, which is the argument of "Coverage, and Building One by Hand" below.

> **Trap.** "Random" in Icarus is not random, and the way it is not will bite a measurement. Chapter 4's "Applying Stimulus" established that bare `$random` is a fixed stream; `tb_seed.v` measures the rest. Bare `$random` and `$urandom` **ignore a `+seed=` plusarg entirely** — only `$random(seed)` and `$urandom(seed)` respond. Worse, the *first draw after seeding* is close to linear in the seed: for seeds 1 to 4 it is `00010e00`, `00021c00`, `00032a00`, `00043800`, all with a zero low byte, so re-seeding per trial correlates the first vector of every trial. Measured on the killing class: 0.4720 that way, where one continuing stream measures 0.2465 against the theoretical 0.2520 — and this chapter's own "about four vectors" read 2.98 until that was found. **Seed once per run, print the seed, throw the first draw away.**

### Constrained random, and why unconstrained random is nearly useless for floating point

Uniform random worked above because the input space is uniform in the property that matters. Floating point is not, and the numbers are brutal. Read a uniformly random 32-bit pattern as binary32 and the encoding fixes the class distribution:

| class | probability | about 1 in |
|---|---:|---:|
| normal | 0.9921875 | 1.008 |
| subnormal, and NaN | 0.00390625 each | 256 |
| zero (±0), and infinity (±inf) | 4.66 × 10^-10 each | 2,147,483,648 |

With two independent random operands the probability that at least one is a **zero** is 9.31 × 10^-10, one in 1.07 billion, and the same for infinity. A billion-vector campaign expects *one* zero operand. You will never test `x + 0` by accident.

The magnitude distribution is worse still. Over uniformly random normal operands the exponent fields are uniform on 1..254, so the probability they differ by 25 or more is **0.8164** — in four transactions of five the smaller operand is below the larger's last place, the answer is the bigger operand, and the only live logic is the sticky bit. The probability they differ by at most 1, the region where cancellation, the leading-zero counter and the variable left shift do anything, is **0.01178**: **one transaction in 85**. Exact cancellation `a + (-a)`, at around 2 × 10^-10, will never happen.

Bluntly: **throwing uniformly random 32-bit patterns at a floating point adder mostly tests "return the larger operand".** A million vectors is roughly 816,000 repetitions of the easiest case, 12,000 attempts at the hard one, and zero infinities.

The fix is not more vectors. It is to stop randomising 32 bits and randomise the **fields**, with a weighted menu over the exponent. `tb_covfp.v`'s `gen_biased` draws a percentile and dispatches: 10 % subnormal (`e = 8'h00`, random mantissa), 4 % NaN, 6 % exact zero, 4 % exact infinity, 38 % *clustered* (`e = 8'h40 + ($urandom(seed) % 16)`) and 38 % over the full range (`e = 8'h01 + ($urandom(seed) % 254)`), then adds a random sign.

The **clustered** branch is the important one and the least obvious: it puts both operands inside a narrow exponent window, the only region where cancellation, leading-zero counting and normalisation happen at all. Without it the one-in-85 problem persists however many vectors you run. Two further biases: generate `b` **as a function of** `a` — `b = -a`, `b` perturbed slightly, `b` one exponent step away — which manufactures near-cancellation and tie cases independent sampling never produces; and sweep a fixed **corner-case library** once per run, so the campaign has a floor.

Which leaves the obvious question: how do you know your constraints are any good? You do not reason about it. You measure it.

## Coverage, and Building One by Hand

Coverage answers one question: **did my stimulus ever get there?** It says nothing about whether the answer was right. It is a property of the test suite; it can prove a hole and never correctness. Keep that close, because the industry has spent decades confusing a coverage report with a quality report.

**Code coverage** is instrumented automatically and comes in kinds:

| Kind | Measures | Tells you | Does not tell you |
|---|---|---|---|
| Line, statement, branch | each line and each `if`/`case` arm executed | dead code, untested control paths | whether the value was wrong, or ever checked |
| Toggle | each bit went 0→1 and 1→0 | stuck bits, unused bus lanes | anything about combinations |
| FSM state and transition | each state entered, each legal arc taken | unreachable states; untested arcs, where FSM bugs live | how you got there; illegal transitions you never modelled |
| Expression | each sub-term independently decided the result | that `a && b` saw each term deciding | whether it is the *right* expression |

Apply the whole table to `assign cout = a[7] | b[7];`. One statement, executed on the first vector, so **line, statement and branch coverage reach 100 % immediately**; toggle coverage follows after a few vectors that move every bit both ways, which chapter 4's eight do. Expression coverage would notice the two-term OR is only exercised with `0|0` and `1|1`, but that helps only if you already suspect the line. Every automatic metric available reports a perfect score on a design **wrong on a quarter of all inputs**. That generalises: **code coverage measures execution, not observation.** A line can execute, produce garbage and never reach a checker — and on a combinational datapath every `assign` executes on the first vector.

### Functional coverage

**Functional coverage** is a model you write by hand, listing the situations *the specification* calls interesting and counting whether each occurred. It is not derived from the code, which is why it can find a hole where there is no code to instrument. The SystemVerilog vocabulary is worth knowing: a **covergroup** is a sampled collection, a **coverpoint** one expression observed, **bins** the buckets, and **cross coverage** the Cartesian product — where functional coverage earns its money, because "we tested subnormals" and "we tested infinities" is far weaker than "we tested subnormal plus infinity".

Take the running example. The specification-level statement about a carry-out is that it depends on the top bits *and* on what the lower bits did, so cross `{a[7], b[7]}` with the observed `cout`: eight bins, three lines of Verilog in `tb_scoreboard.v`. Replaying chapter 4's eight cout-checked vectors:

```
  mode=ch04 seed=1
  coverage: {a[7], b[7], cout}
    a[7]=0 b[7]=0 cout=0 :      4
    a[7]=0 b[7]=0 cout=1 :      0   excluded (proven unreachable)
    a[7]=0 b[7]=1 cout=0 :      0   <-- HOLE
    a[7]=0 b[7]=1 cout=1 :      0   <-- HOLE
    a[7]=1 b[7]=0 cout=0 :      0   <-- HOLE
    a[7]=1 b[7]=0 cout=1 :      1
    a[7]=1 b[7]=1 cout=0 :      0   excluded (proven unreachable)
    a[7]=1 b[7]=1 cout=1 :      3
  bins hit 3 / 6 reachable, holes = 3
  transactions 8, adder8 mismatches 0, transactions exposing the mutant 0
PASS tb_scoreboard (8 checks, 3 holes, 0 mutant exposures)
```

**Three of six reachable bins were never entered, and two of the three are exactly the class on which the mutant is wrong.** That report is available after eight vectors, from a model written from the specification by somebody who has never heard of `cout = a[7] | b[7]`. The hole and the surviving mutant are one fact seen from two directions, and the coverage report gets there first — before anyone thinks to break anything. That is the whole argument for coverage, on a case you already care about.

Two bins are marked *excluded*, and this is the part beginners skip. Both top bits clear with a carry out is impossible (the largest such sum is 254); both set without one is impossible (the smallest is 256). Excluding a bin on a belief is how coverage models start lying, so the belief must be proved and the proof checked — `tb_exhaustive.v` counts both cases over all 65,536 pairs and fails the run if either is non-zero:

```
  excluded bins proven empty: cout=1 with both MSBs clear: 0;  cout=0 with both MSBs set: 0
```

Feed the same model the constrained-random generator and all six reachable bins fill within 200 transactions, 65 of which expose the mutant.

### What Icarus gives you: nothing

All of that was hand-written, and it had to be.

> **Icarus reality.** **Icarus Verilog 13.0 has no coverage instrumentation of any kind.** Measured here: `iverilog -t` selects a code generator and the installed set is `blif`, `null`, `pcb`, `sizer`, `stub`, `vhdl`, `vlog95`, `vvp`. `-t coverage` fails with `ERROR: Unable to read config file: .../lib/ivl/coverage.conf` — the same error as any misspelt name, so the target does not exist. `iverilog -h` has no `-cover`, `-toggle` or `-profile`; `vvp -h` offers only `-h -i -l -M -m -n -N -q -s -v -V`. And `covergroup` compiles at no language level: all four `-g` levels reject `bad_covergroup.v` with `syntax error` / `error: Invalid module item.`, which is why it is an `xfail` target here.

For honesty about the wider open-source flow: **Verilator** has real coverage — `--coverage` is an alias for `--coverage-line --coverage-toggle --coverage-expr --coverage-fsm --coverage-user`, processed afterwards by `verilator_coverage` — but it is a cycle-accurate two-state compiler rather than an event simulator, so moving a chapter 4 testbench to it is a change of model, not a flag. **Covered** was built for exactly this flow and integrates with Icarus through a VCD or a VPI module, but its site's copyright reads 2010 and it is not installed here.

### The hand-rolled model, in about sixty lines

So write it yourself, which teaches the concept better than a tool would, because choosing the bins is what matters. First, what its green target means: **`tb_covfp.v` contains no design under test** — it samples its own reference model, and replacing `fx + fy` with `fx - fy` leaves the target green. After four chapters of green `tb_*` targets meaning "the arithmetic checked out", know that this one is a coverage *instrument*: it tests stimulus, and nothing in it tests addition. `tb_covfp.v` builds the model chapter 12 will inherit: **thirty-four bins** in one `integer cov [0:NBINS-1]` array — twenty-five for the cross of the five operand classes, four for exponent-difference buckets, five for the result class. The buckets come from the *algorithm*: equal exponents are the cancellation region, 1 or 2 a normalisation shift, 3 to 24 keeps guard and round alive, 25 or more leaves only the sticky bit. A `cov_sample` task runs once per transaction, doing three array increments:

```verilog
      cov[ca*NCLS + cb] = cov[ca*NCLS + cb] + 1;
      if (ca == C_NORM && cb == C_NORM)
        cov[NCROSS + expdbin(x, y)] = cov[NCROSS + expdbin(x, y)] + 1;
      cov[NCROSS + NEXPD + fclass(r)] = cov[NCROSS + NEXPD + fclass(r)] + 1;
```

And the reporting step does what most commercial flows do not do by default: **an empty bin fails the run.** A non-zero hole count prints `*** COVERAGE FAILURE: %0d empty bins ***` and ends in `$fatal(1)`, so `make` goes red. A coverage report nobody opens changes nothing; one that is a test does.

Three stimulus regimes through the same model. First, 2000 uniformly random 32-bit patterns — the campaign that "feels" thorough, with the exponent-difference block reduced to its four counts:

```
  gen=uniform seed=1 transactions=2000
  operand class cross:
    ZERO          ZERO:  HOLE   SUBNORM:  HOLE    NORMAL:  HOLE       INF:  HOLE       NAN:  HOLE
    SUBNORM       ZERO:  HOLE   SUBNORM:  HOLE    NORMAL:    10       INF:  HOLE       NAN:  HOLE
    NORMAL        ZERO:  HOLE   SUBNORM:     7    NORMAL:  1966       INF:  HOLE       NAN:     5
    INF           ZERO:  HOLE   SUBNORM:  HOLE    NORMAL:  HOLE       INF:  HOLE       NAN:  HOLE
    NAN           ZERO:  HOLE   SUBNORM:  HOLE    NORMAL:    12       INF:  HOLE       NAN:  HOLE
  [ exponent difference: 9 / 39 / 338 / 1580 ]
  result class:
    ZERO     :        0   <-- HOLE
    SUBNORM  :        0   <-- HOLE
    NORMAL   :     1983
    INF      :        0   <-- HOLE
    NAN      :       17
  ---------------------------------------------
  bins hit 11 / 34 = 32 %   holes = 23
*** COVERAGE FAILURE: 23 empty bins ***
```

Eleven bins of thirty-four, and the arithmetic of "Choosing Stimulus: Directed, Exhaustive, Random" made visible: 1966 of 2000 transactions are the same easy normal-plus-normal case, 1580 of them more than 24 exponents apart. No zeros, no infinities, no subnormal plus subnormal, and no result of zero or infinity. It exits 1.

Second, the constrained generator plus a twenty-five-entry corner-case library — three lines of the report, and one bin still empty:

```
    >=25 (sticky only)  :       0   <-- HOLE
  bins hit 33 / 34 = 97 %   holes = 1
*** COVERAGE FAILURE: 1 empty bins ***
```

**That hole was a real bug in this chapter's own generator, and the coverage model found it, not the author.** The first version put every normal exponent into `8'h40 + (rand % 16)`, a sixteen-wide window, so a difference of 25 or more was unreachable by construction: the generator written to fix the one-in-85 problem had over-corrected into never testing the sticky path. That is the coverage-driven loop working on this guide's own code, preserved as `+gen=narrow` so you can watch it happen.

Third, with one branch added — a full-range exponent alongside the clustered one — the same three lines:

```
    >=25 (sticky only)  :     717
  bins hit 34 / 34 = 100 %   holes = 0
PASS tb_covfp (2025 transactions, 34/34 bins, coverage closed)
```

Closed, and closed on seeds 1, 2, 3, 99 and 12345. **Seed stability is worth checking**: a model that closes on one seed has not closed, it got lucky.

Now turn the same knife this section turned on code coverage against the hand-rolled model itself. Compile the same file with `-DALL_POSITIVE`, which forces the generated sign bit to zero in `gen_biased` — every operand in the run positive, and the corner library already is. The report's last two lines:

```
  bins hit 34 / 34 = 100 %   holes = 0
PASS tb_covfp (2025 transactions, 34/34 bins, coverage closed)
```

Full closure, green run — and not one transaction performed an effective subtraction, so the leading-zero counter, the variable left shifter, cancellation exact and catastrophic, and the sign of an exact-zero sum were never exercised: rows F and I of "Verifying Floating Point Specifically" below, untouched at 100 %. The model has no bin for the sign combination, so it cannot see the difference; a chapter-12 adder with a completely dead subtract path would be certified *coverage closed* by the model it inherits. That is "closure is necessary and not sufficient" as a demonstration rather than a slogan: a coverage model is silent about every dimension it does not name.

The loop those three runs describe is the standard one, and its product is not the percentage. Write the model from the specification, run random stimulus, read the report, and for every empty bin ask *why*, then take one of three actions: fix the generator, write a directed test, or prove the bin unreachable and exclude it with the justification written down. Re-run to 100 %, then **keep running random for volume**, because closure is necessary and not sufficient. Every empty bin forces a conversation about the design, and that conversation is what you are buying.

> **Seed for chapter 12.** Chapter 12 extends this file rather than replacing it, and the first extensions are the missing *dimensions*, not mechanics: bins for the sign combination — effective add against effective subtract, the blindness the `-DALL_POSITIVE` run just demonstrated — and bins for rounding events: a tie occurred, the guard bit was set, the sticky bit was set, the round carried out. Then the mechanical ones: per-bin minimum hit counts, `illegal_bins` as a plain `if (bad) $fatal(1)`, and the bin array dumped so coverage merges across a regression instead of being measured one run at a time.

## Assertions, and What You Can Actually Run Here

An assertion is an executable statement of something that must always be true, written where the property lives rather than at the testbench boundary. That relocation is the value: it fires at the moment of violation rather than when the corruption reaches an output, so the failure names the guilty module and cycle.

There are two families. **Immediate** assertions are procedural and evaluate when control reaches them: `assert (cond) pass_statement; else fail_statement;`. **Concurrent** assertions are temporal properties on a clock: `assert property (@(posedge clk) req |-> ##[1:3] ack);` — SVA, defined in IEEE 1800, whose operators `|->`, `##n`, `throughout` and `disable iff` make protocol checking astonishingly concise. Two relatives complete it: `assume` constrains the environment, `cover` records that a scenario happened. You cannot run the interesting half here, and the boundary is worth knowing exactly.

> **Icarus reality.** Ten constructs, four language levels, measured here. **Icarus Verilog 13.0 supports immediate `assert`, `assert … else`, `assume` and immediate `cover` from `-g2005-sv` upward, and supports no concurrent assertions, no `property` or `sequence` blocks, no deferred assertions and no covergroups, at any level.** At `-g2005`, `assert` is `error: Enable of unknown task ``assert''`. Nothing changes between `-g2005-sv`, `-g2009` and `-g2012` for any construct tested, so standardise on `-g2012`. A concurrent assertion with an implication gives `syntax error` then `error: Error in property_spec of concurrent assertion item.`; `property`/`endproperty` and `covergroup` give `syntax error` / `Invalid module item`; `assert final` and `assert #0` both give `sorry: Deferred assertions are not supported.`

The advertised `-gno-assertions` and `-gsupported-assertions` flags look like they might help. They are worse than useless: they enable nothing, and where the parser *can* read the syntax they **silence the diagnostic and discard the property**. A file containing `assert property (@(posedge clk) req);` with `req` low at every edge compiles cleanly under `-gno-assertions` and runs to completion reporting nothing:

```
$ iverilog -g2012 -gno-assertions -o a07b.vvp a07b.v ; echo "rc=$?"
rc=0
$ vvp a07b.vvp
ran to the end
```

A flag that turns a failing check into a silent pass is exactly what this guide exists to warn you about. Where the parser *cannot* read the syntax — anything with `|->` — the flag changes nothing.

### The pattern that does work

No concurrent assertions means clocked immediate assertions inside `always @(posedge clk)`. That covers every single-cycle invariant, and with a counter or flag simple multi-cycle properties too. `tb_assert.v` is the shape:

```verilog
    assert (^q !== 1'bx)
      else begin errs = errs + 1; $error("q is X"); end

    // An invariant from the SPECIFICATION - "a modulo-6 counter" - not from the
    // implementation. assert (q == q) would be a tautology that can never fire.
    assert (q <= 3'd5)
      else begin errs = errs + 1; $error("q=%0d exceeds 5", q); end
```

Both sit inside `always @(posedge clk) if (!rst) begin ... end`, which also counts the checks; the first is the X-check that catches uninitialised registers, incomplete `case` statements and inferred latches at the instant they happen. The rest of the block adds `assume (en === 1'b0 || en === 1'b1);` and `cover (q == 3'd5);` beside a hand-rolled counter. Three decisions are deliberate. The `if (!rst)` wrapper is a hand-rolled `disable iff`; without it every assertion fires during reset, when the design claims nothing. The `errs = errs + 1` beside every `$error` exists because **`$error` leaves the exit status at 0** — measured again this session, consistent with chapter 4's "Checking, and Making Failure Impossible to Miss" — so a run without `$fatal` reports success while assertions scroll past in red. And immediate `cover` produces nothing at all, because there is no database to write to, which is why the counter is there. (A violated `assume` behaves exactly like a violated `assert`.)

Rebuild `counter6` with `-DBREAK_WRAP` so it wraps at 8 instead of 6, and both kinds of check earn their keep at once. Abridged — the full run interleaves fifteen `FAIL` lines from the plain-`if` value-sequence check with four `ERROR` blocks from the assertion; here are the first six lines and the last four:

```
FAIL tb_assert: after 6 enabled cycles q=6, expected 0
ERROR: tb_assert.v:61: q=6 exceeds 5
       Time: 85000  Scope: tb_assert
FAIL tb_assert: after 7 enabled cycles q=7, expected 1
ERROR: tb_assert.v:61: q=7 exceeds 5
       Time: 95000  Scope: tb_assert
  27 clocked checks, q reached 5 3 times, 19 assertion failures
FAIL tb_assert: 19 assertion failure(s)
FATAL: tb_assert.v:152: 19 error(s)
       Time: 300000  Scope: tb_assert.stimulus
```

Look at what each kind of line carries. The assertion's `ERROR` brings **file, line, simulation time and scope**, none of which you wrote — that is the practical argument for `assert … else` where a plain `if` would do: chapter 4's failure-message discipline, handed to you. And the plain `if` is what *localises* the divergence — "after 6 enabled cycles q=6, expected 0" names the wrap itself, which no invariant can. They are colleagues, not rivals: the assertion says where to look, the sequence check says what went wrong.

### What makes an assertion worth writing

- **Inside the design, state invariants**: the normalised significand's leading bit is 1 unless the result is zero or subnormal, the aligner's shift amount is in range, a one-hot vector really is one-hot, every `case` has a complaining `default`. Wrap them in `` `ifndef SYNTHESIS `` so the synthesisable body stays clean. **In the testbench, state protocol and boundary facts**: no `x` on a valid output, a legal handshake, a result matching the reference model.
- **A good assertion comes from the specification, not the implementation.** `assert (sum == a + b)` beside `assign sum = a + b;` is a tautology that can never fire. It is local, so a failure names the guilty module; it fires early; it carries values; and it uses `!==`/`===` so `x` and `z` are caught rather than swallowed.
- **An assertion that can never fire is a comment.** `tb_assert.v` therefore ends by checking that its cover point `q == 5` was reached. Rebuild `counter6` as a modulo-*5* counter and every `assert` in the file still passes, because `q` is still never more than 5; what catches it is the reachability check and the value sequence, neither of which is an assertion.
- **The cheapest high-value assertion in this guide is the X-check**, `assert (^result !== 1'bx)` on every output every cycle — no SVA needed, and the listing above already carries it, aimed at chapter 3's "The Accidental Latch".

Two closing cautions. Assertions state invariants, not answers — the backwards `counter6` of "The Shape of a Suite You Can Trust" satisfied every one, which is why the value-sequence check sits beside them. And this is the weakest part of the open-source flow — SVA is one of the great ideas in hardware verification and you cannot practise it here, which is why `bad_sva.v` is an `xfail` target rather than a remembered fact. Past one or two multi-cycle properties the counter approach becomes painful; the answer then is a commercial simulator or Verilator, which supports a subset of SVA. Do not build a toy SVA library in Verilog — you will end up verifying the library.

## The Regression Loop

A regression suite is the set of tests you run to prove you have not broken anything. It runs because of a *change*, never a suspicion, and chapter 4's "Automating the Build" gave the mechanism: one command, an honest exit status, a `FAIL`-string gate.

**Speed is a correctness property of the suite.** An hour-long suite runs once a day and finds each bug tangled with twenty other changes; a three-second suite runs after every edit and finds it inside one diff. Measured:

| work | time |
|---|---|
| `iverilog -g2012 -Wall` on one testbench | 0.013 s |
| exhaustive 65,536-pair sweep, two designs and a reference | 0.91 s |
| 1,000,000 `shortreal` reference transactions | 3.47 s |
| `run_all.sh` — the whole book so far, 73 targets | 3.03 s |

About **288,000 transactions a second**, a real number to plan against: a million-vector campaign is a three-second test. Tier the suite only when it outgrows seconds — smoke, commit with coverage closure and the exhaustive minifloat, a nightly soak over many seeds. At this size "run everything, it takes three seconds" beats any test-selection cleverness, and premature selection machinery is its own bug farm.

Chapter 4's "Debugging Methodically" covers finding the bug. What this chapter adds is the step everyone skips between finding it and fixing it: **write a test that fails, before you touch the design.** It proves you understood the bug, proves the test can detect it, and becomes the permanent guard — mutation testing from the other direction. Then fix, confirm the new test and the whole regression, and **keep the test forever**, with a comment naming the bug.

The suite therefore only grows, because deleting a test deletes the evidence that a bug is gone. Legitimate removals: the feature went away, the test is a duplicate, the test was wrong. "It is slow" is not one — move it to a slower tier. "It has never failed" is emphatically not one; that is what a working guard looks like.

`git bisect run bash run_all.sh` binary-searches a thousand commits in ten runs, and its prerequisites are this chapter's arguments: deterministic, non-zero on failure, fast. Bisection is where a sloppy exit code finally bites. And **always print the seed**, on its own line, at the top of every run:

```
  SEED=1      <-- always echo it: this line is the reproducer
```

A failure report without the seed is not reproducible, and this is the one place a hardware regression can be as flaky as a software one. Pin `SEED=1` in the commit regression so bisection stays usable, and vary it in the nightly soak. Event-driven simulation is otherwise deterministic — same source, same command line, byte-identical output — so the classic flakiness sources are absent; what remains is uninitialised registers whose `x` resolves differently after an unrelated edit, and the blocking-assignment races chapter 3's "Simulation Artifacts That Will Cost You an Evening" dissects.

Then report in one line a human reads in two seconds: `PASS 214/214 tests, 1,000,000 vectors, 34/34 coverage bins, seed=1, 3.4 s`. An unread green run is the same as no run.

## Verifying Floating Point Specifically

Everything so far applies to any design. This is the part specifically about adding floating point numbers, and it is chapter 12's checklist. Chapters 6 to 8 explain *why* each row is what it is; the point here is that every row is **a separate piece of hardware**, not merely a separate sentence in the standard, which is what makes it a test list rather than a reading list.

| Group | Cases, with vectors | Why each is distinct hardware |
|---|---|---|
| **A** zeros | `(+0)+(+0)`; `(-0)+(-0)`; **`(+0)+(-0)` = `+0` in both orders**; `(+0)+x = x`. `00000000+00000000`, `80000000+80000000`, `00000000+80000000`, `00000000+3f800000` | zero is not a normalised significand, so logic that prepends the implicit `1.` breaks at `exp == 0`; and the signed-zero rule falls out of no datapath, so it must be hard-coded |
| **B** subnormals | one subnormal `00000001+3f800000`; **both** `00000001+00000001`; gradual underflow `00800000+80000001` → `007fffff`; subnormal → normal `007fffff+00000001` → `00800000` | the aligner must use effective exponent **−126**, not the encoded 0 — the commonest subnormal bug; with both subnormal there is no implicit 1 anywhere; the normaliser must *stop* at exponent 1; a fraction carry promotes exponent 0→1 with **no shift** |
| **C** NaN | `NaN+x` and `x+NaN`; signalling → **quiet**, `7fa00000+3f800000` → `7fe00000`; `NaN+inf` | a pure control override, so both orders matter; quieting is separate logic from propagation; NaN must beat infinity |
| **D** infinity | `inf+inf`, `inf+finite`, `inf+0`; **`inf+(-inf)` = NaN**, `7f800000+ff800000` → `7fc00000` | infinity shares the `exp==255` encoding with NaN, so the decoder must split on the mantissa; `inf+(-inf)` is the one place a finite datapath computes something that must be thrown away |
| **E** the sticky region | exponents ≥ 25 apart, `4b800000+33800000` | the small operand shifts past guard and round but must still set the **sticky bit**, which implementations lose by saturating the shift. **81.6 % of random normal pairs** |
| **F** cancellation | exact, `3f800000+bf800000` → `+0`; catastrophic, `40000001+c0000000` → `34800000` | a zero from cancellation is a different path from a zero *operand*, and at p ≈ 2 × 10^-10 must be directed; catastrophic cancellation is the only case driving the leading-zero counter at full range, and is ≈ **0.59 %** of random normal pairs — near-equal exponents (1.178 %) *times* opposite signs (one half) |
| **G** rounding | tie **down** `4b800000+3f800000`; tie **up** `4b800001+3f800000` → `4b800002`; guard and sticky, `4b7fffff+3f800000`; rounding carries out, `3fffffff+33800000` → `40000000` | one tie direction alone passes a design that always rounds up; guard/round/sticky/LSB are separate decisions; a rounding carry-out needs a second, rarely taken renormalise |
| **H** overflow and underflow | `7f7fffff+7f7fffff` → `7f800000`; rounding-induced overflow just below max normal; underflow to subnormal and to zero | arithmetic and rounding-induced overflow are different paths; rounding *up* a subnormal into the smallest normal is a third |
| **I** the shifter | same-signed with carry `3f800000+3f800000`; without carry `3f800000+3e800000`; opposite-signed, left shift of 0..24 | three shifter behaviours — right-1, none, left-N — each needing its own hit |

Twenty-eight of those vectors already run, in `tb_fpref.v`. Four cross-cutting notes. The table assumes **roundTiesToEven** throughout, the only rounding attribute this guide implements; the one row that moves under another attribute is A — `(+0)+(-0)` is `+0` under every attribute *except* roundTowardNegative, where it is `-0`, so a checklist that states the rule without the attribute is teaching a special case as a universal. **Exception flags are a specification decision chapter 12 must make in writing**: binary32 addition raises invalid (an sNaN operand, `inf+(-inf)`), overflow and inexact per IEEE 754-2019 Clause 7 — but, per a correction dated 2026-08-16 from chapter 7's review cycle, **not underflow**: a tiny sum of two binary32 values is always exact, so default underflow (tiny *and* inexact) can provably never fire for addition; chapter 7's "The Flags an Adder Can Actually Raise" carries the proof, and this note originally listed underflow among the raisable flags — and the moment the adder has flag outputs every row above grows a flag column — if chapter 12 ships without them, that exclusion belongs in the out-of-scope list, handled exactly like flush-to-zero. **Flush-to-zero is a different specification** — if chapter 12 implements it the reference model must too, or thousands of "failures" are a specification mismatch. And row I is the running example at full scale: a significand adder's carry out is exactly the sort of signal a plausible wrong expression computes correctly on every vector you thought of.

> **Seed for chapters 10 and 12.** Floating point addition is **not associative**: `(a+b)+(c+d)` and `((a+b)+c)+d` differ in general, so a four-input reference model must sum in *exactly* the hardware's order or vectors "fail" for no reason. Settle that before writing either. Four operands also create corner cases two cannot: an intermediate overflow that later cancels, an intermediate NaN from `inf + (-inf)` that must poison the result, and cancellation between *pairs*.

### Exhaustive testing, by making the problem smaller

You cannot enumerate 2^64, but you can enumerate a float with the *same structure* — sign, biased exponent, implicit leading one, `exp==0` subnormals, `exp==all-ones` infinities and NaNs — and fewer bits. **Structural bugs are width-independent**: a bug in subnormal handling, NaN priority, sticky reduction or tie-breaking shows up at 8 bits exactly as at 32. For 1 sign + E exponent + M mantissa bits there are 2^W values and 2^(2W) ordered pairs, W = 1+E+M:

| format | E | M | W | operand pairs | at this machine's measured Icarus throughput |
|---|---|---|---|---|---|
| E4M3 minifloat | 4 | 3 | 8 | **65,536** | about a second — the 8-bit integer sweep of the same size took 0.91 s |
| binary16 (half) | 5 | 10 | 16 | **4,294,967,296** | hours — a nightly job, not a commit test |
| **binary32** | 8 | 23 | 32 | **1.8 × 10^19** | no. Even at an optimistic 10^7 vectors a second it is 58,000 years |

What that buys is not "more coverage", it is *certainty*. E4M3's 256 patterns are 2 zeros, 14 subnormals, 224 normals, 2 infinities and 14 NaNs (an IEEE-*shaped* E4M3, with infinities; the OCP FP8 format of the same name has none, so its population differs). Over all 65,536 pairs, **10.6 % involve at least one subnormal** against 0.78 % for random binary32; **all twenty-five class crosses occur**, the rarest — zero against zero — exactly four times, guaranteed rather than hoped for; and `inf` against `inf` occurs four times, where random binary32 would need about **4.6 × 10^18** vectors to see one. Every tie, sticky case, cancellation, overflow and underflow occurs, because "every" is what exhaustive means, so the taxonomy above is covered by construction at that width.

Pin the binary16 row down, because it is the one you would schedule. The machine that first timed this chapter ran 65,536 full transactions in 0.91 s and a bare reference-model loop at about 288,000 a second, so four and a bit billion pairs is four to seventeen hours depending on what the testbench does per transaction — and half again longer on the slower container that re-verified this guide, which took 1.4 s for the same sweep. A nightly soak either way, not a pre-commit check. Knowing which *before* you write it is the point of doing the arithmetic.

So the plan this argument recommends: parameterise the adder on `EXP_W` and `MANT_W`, verify exhaustively at E4M3 in a second, run binary16 overnight, and only then instantiate at E8M23 and verify with corner cases, constrained random and coverage. The parameterisation is the trick, and good design practice anyway.

> **What chapter 12 actually did, recorded 2026-08-21.** It did *not* take this route. The shipped adder is binary32-specific — `grep` finds zero `parameter` declarations in `src/ch09` or `src/ch12` — because the design descends from chapter 8's algorithm module, whose widths are the 28-bit budget proved for binary32 and whose corner library, coverage bins and golden references are all binary32 artifacts. Parameterising after the fact would have re-opened every one of them. The cost of that decision is real and belongs here rather than in a footnote: **every format retarget in chapter 14 is a rewrite, not an instantiation**, and the reduced-width verification strategy this section argues for was never exercised on the guide's own design. Take the argument on its merits, not on the guide's example.

Its limits: reduced-width exhaustive testing does **not** catch width-dependent bugs — a shifter one bit too narrow at 24 bits but fine at 4, a carry chain that breaks above 16, a hard-coded `8'd127` right for binary32 and wrong for E4M3. It complements full-width random testing rather than replacing it.

One name for later. **Berkeley SoftFloat and TestFloat**, by John R. Hauser: SoftFloat is a conforming software implementation of IEEE 754 across 16- to 128-bit formats with all rounding modes and exception flags, and TestFloat tests an implementation by comparing it against SoftFloat. That a decades-maintained test-vector generator exists for *one arithmetic operation* is the most persuasive evidence available that floating point verification needs a methodology — and its architecture is this chapter's. It is a C toolchain, so wiring it to Icarus means generating vector files offline and loading them with `$readmemh`.

## Traps Beginners Fall Into

Each is a place to lose a week. As in chapters 3 and 4, no tool catches any of them: every entry in the third column is something you build yourself.

| Trap | What you see | Caught by | File |
|---|---|---|---|
| Code coverage read as correctness | 100 % line and toggle on a design wrong for 25 % of inputs | a functional coverage model | `tb_scoreboard.v` |
| A golden file generated by the design | the suite verifies today's bug is still there | nothing — mutation testing is blind here | — |
| A `shortreal` chain in double precision | a **correct** design reported wrong | nothing, no warning at all | `bad_srchain.v` |
| Comparing floats with a tolerance | a 1-ulp bug accepted at 1e-6 relative | `===` on the bits | `bad_tolerance.v` |
| Expecting `$error` to fail the build | red text, `make` reports success | `$fatal` plus the `FAIL` gate | ch. 4, `bad_severity.v` |
| Expecting `-gno-assertions` to help | the property is discarded, the run passes | nothing | `bad_sva.v` |
| Tests that pass because they never ran | a zero-bound loop, a task never called | a count-the-checks guard | `tb_scoreboard.v` |
| Declaring victory on a green run | — | this whole chapter | — |

The tolerance row deserves its argument in full, because chapter 12 will be tempted daily. `abs(got - exp) < eps` is wrong for verifying floating point hardware twice over. First, the bugs this guide exists to catch are *one unit in the last place* — a tie broken the wrong way, a lost sticky bit — and a relative eps of 1e-6 is about 8.4 ulps at binary32 precision, so it accepts every one of them: `bad_tolerance.v` measures a genuine 1-ulp bug passing at 1e-6 relative, and an absolute 1e-30 accepting a result 8,388,606 ulps wrong near zero. Second, there is no principled eps: anything tight enough to catch a last-place bug is zero, and at zero you are comparing values with extra steps. IEEE 754 addition is exactly specified — one correct bit pattern per rounding attribute — so compare bits with `===` and print them in hex. Tolerances are for numerical analysis, where the answer is an approximation; here it is a specification.

The last row is the chapter in one line. Green means nothing until you know the tests *can* fail, the stimulus reached the interesting states, the checker ran and the exit code is honest. Green is the beginning of the argument, not the end.

## Bridge to Chapter 6

You now have the argument that turns a green run into evidence: a reference model that is not the design, a suite split into parts you can change independently, stimulus chosen deliberately rather than by habit, a coverage model that fails the run when it has a hole, the assertions this toolchain will really execute, and a regression loop that keeps every bug you have found. What it lacks is the specification to verify *against*. Chapter 6 starts building it — binary number systems, two's complement, fixed point, and what a finite number of bits can and cannot represent: the ground chapter 7's IEEE 754 encoding stands on, and the reason this chapter's corner cases are the ones they are.
