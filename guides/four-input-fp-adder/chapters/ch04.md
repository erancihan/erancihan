## The Simulator Is Your Only Laboratory

You have no oscilloscope, no board, no logic analyser and no colleague who will tell you the answer. What you have is a program that pretends to be your circuit, and a second program you write that pretends to be the rest of the world. Everything you learn about the four-input floating point adder before it exists in silicon comes from running those two together and reading what comes out.

Taking that seriously changes how you work. A physicist with one instrument designs an experiment rather than waving a probe about: controlled input, predicted output, a written-down criterion for whether the prediction held. A **testbench** is that experiment in Verilog — the DUT is the specimen, the stimulus the controlled input, the check the criterion, the verdict one line saying PASS or FAIL.

Chapter 3 ended by pointing out that you have already written a dozen testbenches by accident. Now the testbench becomes the thing you are building — the half of your work that never ships, which is why it can do what the design cannot: wait, read files, compute in floating point, print, and stop the world. A **waveform viewer** turns a recorded simulation into a picture of every signal against time; it is the best debugging tool in digital design and the one used worst. The discipline fits in one sentence: **never open a waveform without a time to go to.** The testbench finds the bug and prints the timestamp; the waveform explains it.

Deciding *which* inputs to try, proving you have tried enough, building a reference model you can trust and measuring what your tests never reached is verification methodology: chapter 5. Mechanics first. Everything below was compiled with **Icarus Verilog 13.0** and run under `vvp` on this machine, and every listing is a file in `src/ch04/`.

## The Anatomy of a Testbench

A design has two halves under different rules. The **DUT** is synthesisable RTL, where every construct must map onto gates or flip-flops. The **testbench** drives it and watches it, and *nothing in a testbench needs to be synthesisable*: it is where the language stops pretending to be hardware and becomes an ordinary program. Its shape is always the same. Here is `tb_anatomy.v`, driving chapter 3's counter.

```verilog
`timescale 1ns/1ps
`default_nettype none

// The shape every testbench in this book has, read top to bottom:
// declarations, DUT, clock, dump control, watchdog, checker, stimulus, verdict.
module tb_anatomy;

  localparam real PERIOD = 10.0;          // ns - name the period, not the half

  // Chapter 2's rule still binds: reg for what the testbench drives.
  reg        clk = 1'b0;
  reg        rst_n;
  reg        en;
  wire [3:0] q;

  integer    errors = 0;
  integer    i;

  counter4 dut (.clk(clk), .rst_n(rst_n), .en(en), .q(q));

  // The initialiser on the declaration above is what makes this line work:
  // ~x is x, and an x clock never produces an edge.
  always #(PERIOD/2.0) clk = ~clk;

  // Waveform dump on request only:  vvp sim +dump=/tmp/anatomy.vcd
  // The filename lives inside the block, not at module scope, so a 2048-bit
  // string does not end up in the waveform of the design being debugged.
  initial begin : dumpctl
    reg [8*256-1:0] dumpfile;
    if ($value$plusargs("dump=%s", dumpfile)) begin
      $dumpfile(dumpfile);
      $dumpvars(0, tb_anatomy);
    end
  end

  // Watchdog: its own initial block, and it prints FAIL before killing the run.
  initial begin : watchdog
    #10000;
    $display("FAIL tb_anatomy: timeout at %0t, the test never finished", $time);
    $fatal(1, "timeout");
  end

  task check(input [3:0] got, input [3:0] want, input [255:0] what);
    begin
      if (got !== want) begin
        errors = errors + 1;
        $display("FAIL tb_anatomy: t=%0t %0s: q=%0d expected %0d",
                 $time, what, got, want);
      end else
        $display("  ok t=%0t %0s: q=%0d", $time, what, got);
    end
  endtask

  initial begin
    // Reset is asserted at time 0, before any edge exists to be confused by.
    rst_n = 1'b0;
    en    = 1'b0;
    repeat (3) @(posedge clk);            // hold it across several edges
    @(negedge clk) rst_n = 1'b1;          // release it on the far edge
    check(q, 4'd0, "out of reset");

    en = 1'b1;                            // stimulus changes on negedge only
    repeat (5) @(negedge clk);
    check(q, 4'd5, "five enabled cycles");

    en = 1'b0;
    repeat (3) @(negedge clk);
    check(q, 4'd5, "three disabled cycles");

    en = 1'b1;
    for (i = 0; i < 4; i = i + 1) @(negedge clk);
    check(q, 4'd9, "four more enabled cycles");

    if (errors == 0) $display("PASS tb_anatomy");
    else             $fatal(1, "%0d error(s)", errors);
    $finish;
  end

endmodule

`default_nettype wire
```

```
  ok t=30000 out of reset: q=0
  ok t=80000 five enabled cycles: q=5
  ok t=110000 three disabled cycles: q=5
  ok t=150000 four more enabled cycles: q=9
PASS tb_anatomy
tb_anatomy.v:76: $finish called at 150000 (1ps)
```

`module tb_anatomy;` has **no port list** — there is nothing above a testbench to connect to. Icarus picks the root automatically, and with *two* uninstantiated modules it does not complain — it exits 0 and elaborates both as roots, running them concurrently until whichever `$finish` fires first ends the lot. Compile `tb_vectors` and `tb_check` together and you get one `PASS` line where you expected two, and exit 0. "Automating the Build" names the root with `-s` instead. Declarations follow chapter 2's rule — **`reg` for what the testbench drives, `wire` for what it observes** — and getting that backwards is a compile error, one of the very few beginner mistakes here the tool does catch. The DUT instance uses **named port connections**, never positional ones, because a swapped pair produces a plausible failure you will blame on the design.

Then the two kinds of process. **`initial` runs once from time 0** — a *scenario*, read top to bottom like a script. **`always` restarts forever** — a *background process*: the clock, a monitor, a scoreboard. Multiple `initial` blocks start at time 0 and interleave, the idiom for separating concerns; this file has three, none of which knows about the others.

The end of the stimulus block is the **verdict**: zero errors prints `PASS`, anything else calls `$fatal`, the only severity task that changes the exit status. Then `$finish` ends the simulation. Leaving it out is how beginners break their terminal — a clock generator schedules an event every half period *forever*, so the queue is never empty and `vvp` never returns. A module with `always #5 clk = ~clk;` and no `$finish` had to be killed after four seconds:

```
started, and there is no $finish anywhere
EXIT=137
```

So the rule is **a testbench with a clock generator must call `$finish`** — plus the watchdog above, because the failure `$finish` does not cover is the test that never reaches it: a `@(posedge done)` on a signal that never arrives. The watchdog sits in its own `initial` block, prints `FAIL` with a reason, and calls `$fatal`, so a hang becomes a reported failure.

And it waits on **time**, not on clock edges. `repeat (n) @(posedge clk)` reads better and survives a change of period, which is how `tb_dump.v` used to be written — but it waits on the very signal whose absence is the commonest cause of a hang. Change that file's `reg clk = 1'b0;` to `reg clk;` and the edge-counted version never fired: killed at eight seconds with nothing on stdout. As an absolute `#delay` it prints `FAIL tb_dump: timeout at 280000, the test never finished` and exits 1. Only a watchdog that needs no edge survives the case a watchdog exists for.

One detail of that transcript recurs throughout the chapter: reset releases at 30 **nanoseconds** and the check prints `t=30000`, because with `` `timescale 1ns/1ps `` the **precision** is 1 ps and `%t` formats in precision units. Read the extra zeros, or set `$timeformat`.

## Clock and Reset Without Racing Your Own Design

A clock generator is two lines: `reg clk = 1'b0;` and `always #(PERIOD/2.0) clk = ~clk;`. What you must not do is leave the initial value out — `reg clk;` starts at `x`, `~x` is `x`, and the clock toggles `x` to `x` forever without an edge. Chapter 3's "Simulation Artifacts That Will Cost You an Evening" measures it: zero rising edges in twenty-six nanoseconds, and not one word from the simulator.

**Name the period, not the half period**, because `always #5 clk = ~clk;` is a 10 ns clock written as a 5. But dividing by two is where a timescale can betray you. `tb_period.v` compiles the identical generator twice, once under `` `timescale 1ns/1ps `` and once under `` `timescale 1ns/1ns ``:

```verilog
module clk_coarse (output reg clk);
  localparam real PERIOD = 5.0;
  initial clk = 1'b0;
  always #(PERIOD/2.0) clk = ~clk;      // #2.5 rounded to the 1 ns precision
endmodule
```

A third module measures each with `$realtime`:

```
  1ns/1ps: asked for 5.00 ns, measured 5.00 ns
  1ns/1ns: asked for 5.00 ns, measured 6.00 ns
PASS tb_period (precision decides what your period really is)
```

> **Trap.** A half period that does not land on the timescale **precision** is rounded, giving a clock of a different frequency with no diagnostic at all. Here a 5 ns request became a 6 ns clock — a twenty per cent frequency error — because `#2.5` rounded up to `#3`. The duty cycle stays at fifty per cent, which is why the symptom is easy to miss: the waveform looks perfect and only the time axis is wrong. Use `` `timescale 1ns/1ps `` everywhere and odd periods stop being a category of bug.

Now reset, which is a *sequence*, not a value. Chapter 3's "Reset Strategy" already chose synchronous and active-low, so what is left is when to assert and when to let go. Three rules, all visible in `tb_anatomy.v`:

```verilog
    rst_n = 1'b0;
    en    = 1'b0;
    repeat (3) @(posedge clk);            // hold it across several edges
    @(negedge clk) rst_n = 1'b1;          // release it on the far edge
```

**Assert at time 0**, before any clock edge exists — otherwise the first edge samples an `x` reset and the DUT starts from a state nobody chose. **Hold it across several edges** with `repeat (n) @(posedge clk)` rather than a hand-counted `#35`, which survives a change of period. **Release it on the opposite edge**, as far from a sampling instant as possible.

That last rule governs all stimulus, not just reset. **Drive the DUT's inputs on the opposite edge from the one it samples.** If the design has `always @(posedge clk)`, the testbench writes its inputs from `@(negedge clk)`. Every input is then stable across every sampling instant with half a period of margin either side, and the waveform becomes readable: signals change mid-cycle, not on the edge you are reading.

Break the rule and you have written the race chapter 3 dissects in "Simulation Artifacts That Will Cost You an Evening": three processes in one active region, an order IEEE 1364-2005 §11.4.2 leaves to the implementation and Icarus *alternates* between time steps, and a one-cycle pulse silently swallowed — correct design, broken testbench, no warning at all. If you must drive from the sampling edge, use `<=` rather than `=`, safe for exactly the reason a pipeline register is safe.

## Applying Stimulus

Stimulus reaches a DUT four ways. **Directed vectors** are the workhorse: inputs and expected output side by side. **Table-driven** stimulus lifts them into an array, **file-driven** stimulus out of the Verilog entirely, and **randomised** stimulus generates them — which in Icarus means something specific.

Start with delays, because two forms look alike and are not. Delays inside an `initial` block are **cumulative, not absolute**. From `tb_stimulus.v`:

```verilog
    // Delays inside an initial block are CUMULATIVE, not absolute.
    a = 8'h01;                 // t = 0
    #10;                       // t = 10
    a = 8'h0f;                 // still t = 10
    #10 a = 8'hff;             // "wait 10, then assign": t = 20
    a = #10 src;               // intra-assignment: src read now (20), assigned
                               // at t = 30, after src itself became 99 at t=25
    #10;                       // t = 40
```

The testbench logs every change of `a` and asserts all four: `t=0 a=01`, `t=10 a=0f`, `t=20 a=ff`, `t=30 a=20`. So `#10 a = ...;` means "wait ten units, then evaluate and assign", while `a = #10 ...;` is an **intra-assignment delay** whose right-hand side is evaluated *now* and assigned ten units later — confusing them applies the right values in the wrong order. The right-hand side is deliberately a *variable* that changes during the delay: with a literal, both forms log the same value and the file would be demonstrating a distinction its own checks could not detect. Swap the forms and `change 3` becomes `99`. One signal gets one driver: two blocks writing the same `reg` is legal, undiagnosed, and resolved by whichever ran last. `repeat (n) @(posedge clk);` counts edges; `wait (expr);` is **level**-sensitive, so an already-true expression does not block at all.

Reusable stimulus belongs in a **task**, because unlike a `function` a task may contain delays. `tb_stimulus.v` declares `task automatic drive(input [7:0] va, input [7:0] vb, input [7:0] expected, input expected_cout);`, and the `automatic` matters: without it a task's arguments and locals are **static and shared**, so two concurrent invocations corrupt each other. It costs nothing, and matters the day you fork a second stimulus thread.

Once you have more than a handful of vectors, put them in a file. `$readmemh` loads a memory array from hex text and has one behaviour that catches everybody exactly once: **it reads one memory word per whitespace-separated token**, and does not care about lines. A data file laid out in the columns a human wants —

```
01 02 03
0f 01 10
ff 01 00
80 80 00
```

— loaded into `reg [23:0] vec [0:3]` gives twelve tiny words, not four packed ones. `bad_readmem.v` measures the damage:

```
WARNING: bad_readmem.v:20: $readmemh(vectors_bad.hex): Too many words in the file for the requested range [0:3].
  vec[0] = 000001
  vec[1] = 000002
  vec[2] = 000003
  vec[3] = 00000f
PASS bad_readmem (one token per word, not one line per word)
```

The fix is to pack in the data file, one word per line, which is what `vectors.hex` does: `01020300`, `0f011000`, `ff010001` and five more, each 32 bits of `{a, b, expected_sum, expected_cout}`. Three more measured facts: `//` and `/* */` comments are accepted; an `@2` on its own line sets the load address; and — the dangerous one — **a missing file is not fatal**. A throwaway module, `s_rmf.v`, written for this measurement and not shipped, asks for a file that is not there:

```
ERROR: s_rmf.v:5: $readmemh: Unable to open nope.hex for reading.
m[0]=xx
```

That run exited **0**, carrying on with an untouched memory — and a testbench looping over its vectors will happily apply `x` to everything and report success. So it must **check the load at both ends**: `vec[0]` catches a file that did not load at all, `vec[N-1]` a file truncated to seven of eight words, whose last slot stays `x` — and `x !== x` is false, so an untouched slot passes in silence:

```verilog
    for (i = 0; i < N; i = i + 1) vec[i] = 32'hxxxxxxxx;

    // Relative to the working directory of vvp, not to this source file.
    $readmemh("vectors.hex", vec);

    // vec[0] catches a file that did not load; vec[N-1] catches a short one.
    if (^vec[0] === 1'bx || ^vec[N-1] === 1'bx) begin
      $display("FAIL tb_vectors: vectors.hex did not load %0d vectors", N);
      $fatal(1, "no vectors");
    end
```

That comment is the fourth fact. **`$readmemh` resolves relative paths against the working directory of `vvp`**, not the source file, so the moment a build script runs from a `build/` directory the vectors vanish — with the non-fatal error above, and a green run. "Automating the Build" picks its working directory with this in mind.

> **Seed for chapters 9 and 12.** File-driven vectors are how the adder gets tested at scale: a Python script using `struct` and `math` writes a few thousand packed lines, and the testbench reads them with `$readmemh` and never needs recompiling when the set changes. The load guard matters more there, because a silently short load in a 10,000-vector regression looks exactly like a clean pass. A file that outgrows its array is only a warning either way, so derive `N` from the generator.

Which leaves randomised stimulus, and one fact to state plainly first. `tb_random.v` asserts the exact values `$random` produces; three lines of its run, plus the verdict:

```
  $random           : 12153524 c0895e81 8484d609 b1f05663
  $random(seed=7)   : 80076200 466c4b8c 2d57715a 2e6dfb5c  seed is now -1368524349
  $urandom_range    : 77 19 3 50
PASS tb_random (the stream is fixed)
```

A testbench can only assert those numbers because they never change. **`$random` in Icarus is byte-identical across runs and across recompiles** — two runs of the same binary and one of a freshly compiled binary hashed the same. So a "random" test here is a **fixed pseudo-random vector set**: running it a hundred times explores exactly as much of the input space as running it once. Excellent for regression, because a failure stays reproducible forever; not what "random testing" means to a software engineer, and believing otherwise is how a design that has seen the same vectors four hundred times gets called well tested.

Three mechanical points go with it. `$random` returns a **signed** 32-bit value, so `a = $random % 256;` is negative about half the time; assign into a sized `reg` or use `$urandom_range`. The seeded form takes an **inout** — the seed must be a variable and is updated in place, `7` becoming `-1368524349` after four calls — and a literal is rejected by `vvp` at load time with `ERROR: $urandom's seed must be an integer/time variable or a register.` And determinism is **per stream**: one extra call anywhere shifts every later value.

> **Seed for chapter 5.** *Which* vectors to generate, how to make randomisation widen coverage rather than repeat itself, how to vary and print a seed so a failure stays reproducible, and how to know when you have enough — that is chapter 5, and the determinism measured here is why it needs a chapter rather than a paragraph.

## Checking, and Making Failure Impossible to Miss

A testbench that prints values for a human to read is a demo; one that compares them against an expected answer is an experiment. Four mechanisms turn one into the other: printing the right value, comparing it correctly, reporting the result, and making a build script notice.

**Print with the right task at the right time.** Verilog's three printing tasks run in different regions of the event queue, introduced in chapter 3's "How a Simulator Actually Runs Your Code". `tb_strobe.v` calls all three from the same rising edge, about the same flip-flop, stimulus on the far edge:

```verilog
  always @(posedge clk) begin
    $display("  $display t=%0t clk=%b d=%0d q=%0d", $time, clk, d, q);
    $strobe ("  $strobe  t=%0t clk=%b d=%0d q=%0d", $time, clk, d, q);
    active_q = q;
  end
```

The run in full, `$finish` trailer aside, so the verdict's count is checkable here:

```
  $monitor t=0 clk=0 d=0 q=x
  $display t=5000 clk=1 d=0 q=x
  $monitor t=5000 clk=1 d=0 q=0
  $strobe  t=5000 clk=1 d=0 q=0
  $monitor t=10000 clk=0 d=1 q=0
  $display t=15000 clk=1 d=1 q=0
  $monitor t=15000 clk=1 d=1 q=1
  $strobe  t=15000 clk=1 d=1 q=1
  $monitor t=20000 clk=0 d=2 q=1
  $display t=25000 clk=1 d=2 q=1
  $monitor t=25000 clk=1 d=2 q=2
  $strobe  t=25000 clk=1 d=2 q=2
  $monitor t=30000 clk=0 d=3 q=2
  $display t=35000 clk=1 d=3 q=2
  $monitor t=35000 clk=1 d=3 q=3
  $strobe  t=35000 clk=1 d=3 q=3
PASS tb_strobe (4 edges where $display saw the old q)
```

Four rising edges, four disagreements, the first `x` against `0`. Look at t=15000: `$display` reports `q=0` and `$strobe` reports `q=1`, in the same time step, about the same signal, and neither is lying. **`$display` runs in the active region**, before that step's non-blocking updates have landed, so at a rising edge it shows the *pre-edge* value of every flip-flop output. **`$strobe` runs in the monitor region**, after every value in the slot has settled, so it shows the *post-edge* value — the one a waveform viewer shows you. `$monitor` is in the same region and agrees with it exactly.

The rule follows: **at a clock edge, print with `$strobe`.** `$display` at a posedge reports last cycle's state, and you will chase an off-by-one-cycle bug that is not in your design. The testbench asserts this rather than illustrating it: it counts the disagreeing edges and requires exactly four, so a flip-flop written with `=` instead of `<=` — two disagreements — fails it too. It also pins the settled value against `d`, because a disagreement count says nothing about what the flop *computes*: an inverting flip-flop disagrees just as reliably, and until that check existed it passed every test in this chapter.

`$monitor` has one more property and nothing tells you about it: there is **exactly one monitor slot** per simulation. `bad_monitor.v` registers `$monitor("A: ...")` and then `$monitor("B: ...")`. Its run in full:

```
B: a=0
B: a=1
B: a=2
B: a=3
B: a=4
B: a=5
PASS bad_monitor (only the second $monitor ever printed)
```

Six `B:` lines, zero `A:` lines, no diagnostic: the first format string was discarded in silence. For several standing printouts use `$strobe` inside `always` blocks, which composes. `$monitor` does not.

**Format the value so you can read it.** Chapter 2 covered the specifiers; `tb_print.v` prints them all and *asserts* the misleading ones with `$sformat`, so the five lines below are checked, not eyeballed:

```
  %d   | 90|
  %0d  |90|
  partly unknown: %b |10x1|  %d | X|  %h |X|
  %t before $timeformat |1000|
  %t after  $timeformat |1.00 ns|
```

**`%0` means "no padding"** on every numeric specifier, while plain `%d` pads to the widest decimal the type can hold — which is what makes unformatted tables look broken. And **`%d` and `%h` collapse a partially unknown value to a bare `X`**: `4'b10x1` printed as `X` in both, `10x1` only in binary. When chasing an `x`, print binary; the *pattern* of surviving bits is the evidence, and hex throws it away.

**Compare with `!==`, never `!=`.** This is not a style preference: `!=` is the two-state comparison, so if either side contains an `x` it returns `x`, `if (x)` is false, and an all-`x` DUT output passes every test you have. `!==` is four-state and never returns `x`. (The exception is a `real`, which cannot hold an `x` and for which case equality is not defined at all — hence the plain `!=` in `tb_period.v`.) `tb_check.v` uses it, drives a correct adder and a deliberately broken one from the same vectors, and counts:

```
MISMATCH t=1000 a=01 b=02 got=ff want=03
MISMATCH t=3000 a=0f b=01 got=0e want=10
MISMATCH t=5000 a=ff b=01 got=fe want=00
ok       t=7000 a=80 b=80 got=00
PASS tb_check (3 of 4 vectors caught the broken adder)
```

Three of four vectors caught a module that subtracts instead of adding. The fourth did not, because in eight bits `0x80 - 0x80` and `0x80 + 0x80` are both zero. **A passing vector proves nothing on its own**: only that one input failed to distinguish your design from one wrong one.

> **Trap.** Those lines say `MISMATCH` rather than `FAIL` on purpose: this file is *supposed* to pass, and the regression runner treats `FAIL` anywhere in a run's output as a failure. The corollary of "every failure message must contain `FAIL`" is "**no passing message may contain it**" — a summary reading `0 FAILures` breaks the harness as thoroughly as a missing check does.

Which brings us to the mechanism people get wrong. **Make the failure detectable by a program.** Every severity task was run with its exit status captured:

| call | prints | exit status | continues? |
|---|---|---|---|
| `$info("...")` | `INFO: file:line: ...` + Time/Scope | **0** | yes |
| `$warning("...")` | `WARNING: ...` + Time/Scope | **0** | yes |
| `$error("...")` | `ERROR: ...` + Time/Scope | **0** | yes |
| `$fatal(1, "...")` | `FATAL: ...` + Time/Scope | **1** | no, immediately |
| `$finish` | `file:line: $finish called at 0 (1ps)` | **0** | no |
| `$finish(0)` | *(silent)* | **0** | no |
| `$stop` | `** VVP Stop(0) **`, then an interactive prompt | **0** | **yes** |

The headline is the third row. **`$error` does not change the exit status.** A testbench that reports every failure with `$error` and nothing else exits 0, and `make` reports success. `bad_severity.v` demonstrates that in this guide's own regression: it prints `ERROR: this is $error - loud, red, and worth exactly zero to a build script`, and the runner calls it **PASS**.

The last row is worse. **`$stop` is a breakpoint, not a stopper**: it exits 0 *and the simulation continues*. With standard input closed it prints `** Continue **` and runs to the end; in a terminal it drops into `vvp`'s prompt and hangs a CI job forever. `vvp -N` makes it behave as `$finish` and exit 1. (`$fatal`'s first argument is a *finish number*, not an exit code — 0, 1 and 2 all give exit status 1.)

So this project uses **two** independent mechanisms, and the second is not redundant. First, **exit status**: every testbench counts errors and ends in `$fatal(1, ...)` when the count is non-zero. Run `tb_vectors.v` with `+break`, which corrupts an expected value:

```
FAIL tb_vectors: t=5000 a=ff b=01 got=1_00 want=1_aa
FAIL tb_vectors: 1 of 8 vectors wrong
FATAL: tb_vectors.v:67: 1 error(s)
       Time: 16000  Scope: tb_vectors
```

That run exited **1**. Second, **the `FAIL` string**: the runner greps every run's output for it and treats a hit as a failure even when the process exited 0, because `$error` does not change the exit code and a testbench can be wrong in ways that never reach its own `$fatal`. The gate is `rc != 0 || grep -q FAIL log`, shown in a Makefile in "Automating the Build".

Both mechanisms report a failure. Neither shows your check would ever produce one, which is the question people skip. **A test you have never seen fail is not yet a test.** Settling it is cheap: copy the DUT somewhere scratch, break one thing, and confirm the run goes red. Keep the list of what you broke; that list, not the green run, is the evidence.

`tb_dump.v` is this chapter's cautionary example, and it took two goes. It printed `PASS tb_dump (latency 2, q=17)` against a `pipe2` rebuilt with a *single* flip-flop, because its only check ran after the stimulus had drained, and once the input stops changing every pipeline of latency two or less settles to the same value. Moving that check inside the stimulus loop *looked* complete and was not: sampling `q` once a cycle pins **what `q` holds** and never **when it changes**, so a `pipe2` rebuilt as one flip-flop on the *falling* edge was read half a cycle before it moved and printed the same `PASS` line. What closes it is a second check, watching every change of `q` and requiring `clk` to be high when it happens.

Thirteen rebuilt `pipe2`s were run against the finished file and twelve fail it: one flip-flop, three, four and none; both flops on the falling edge, the second alone on it, a single falling-edge flop, dual-edge flops; blocking `=` in both; the two flops fed in parallel rather than in series; a combinational `q = d - 1`; and three flops with the last on the falling edge. The thirteenth passes, and not because it cannot fail. Moving the *first* flop to the falling edge leaves `q`'s transitions bit-identical **under this file's stimulus**, which only ever drives `d` on the falling edge. Drive it two nanoseconds *after* the rising edge instead — same ports, `q` observed and nothing else — and the real design puts `a0` on `q` at t = 25 ns where the mutant puts it at 15 ns: latency two against one. A survivor is a gap in your stimulus long before it is an equivalent mutant, and this one is a half-cycle path: a bug you want caught.

The same exercise found `adder8`'s carry-out wired into three testbenches and read by none, so tying `cout` to `0` or `1` gave fourteen green targets out of fourteen. **An output that nothing reads is an output that nothing tests.** `tb_stimulus.v` now names the expected carry in every vector, with three vectors that exist only for it, and `tb_vectors.v` reads `cout` as well as `sum`. Of eight wrong carry functions, seven now die — including `~sum[7] & (a[7] | b[7])`, which only `ff+ff` distinguishes. The eighth, `cout = a[7] | b[7]`, still passes all fourteen targets, because every vector here happens to agree with it. That is what chapter 5 is for: it turns *choosing* what to break into a method. Breaking something is a habit you can start this afternoon.

## Dumping Waveforms: VCD, FST, and What Never Appears

Recording takes two calls in an `initial` block: `$dumpfile` names the output, `$dumpvars` selects the contents. Icarus appends an extension **only when the name has none**; a name that already carries one is used verbatim. Measured, one clean directory per case: `$dumpfile("tb")` writes `tb.vcd` by default and `tb.fst` under `-fst`, but `$dumpfile("tb.vcd")` under `-fst` writes **`tb.vcd`, containing FST**, and `$dumpfile("tb.fst")` with no dumper flag writes VCD text into `tb.fst`. Nothing warns you: the format comes from the `vvp` flag and the name is whatever you typed, so either always give an extension and keep it truthful, or never give one and let Icarus choose.

**`$dumpfile` writes relative to the working directory of `vvp`**, not to your source file, so a hard-coded name drops a build artifact wherever the run started — usually next to your source. Every testbench in `src/ch04/` therefore puts dumping behind the `+dump=` plusarg shown in `tb_anatomy.v` above. (Size that string generously: it is right-justified in a fixed-width vector, so a longer path loses its leading characters.)

`$dumpvars`'s first argument is a **depth**. Measured on `tb_dump.v` as it ships, which holds six scopes — `tb_dump`, the instances `u_pipe`, `u_a` and `u_b`, and the named blocks `dumpctl` and `watchdog`, because a named block is a scope too — by running `vvp sim.vvp +dump=/tmp/w.vcd` with `+depth=1`, `+depth=2`, `+sub` and nothing, then counting `$var` lines:

| invocation | vars | what appeared |
|---|---|---|
| `$dumpvars;` and `$dumpvars(0, tb_dump);` | 19 | **everything, all levels** |
| `$dumpvars(1, tb_dump);` | 6 | this scope only |
| `$dumpvars(2, tb_dump);` | 13 | `tb_dump` and one level below |
| `$dumpvars(0, tb_dump.u_pipe);` | 10 | that subtree, all of it |

So **`0` means unlimited**, `1` means this scope only, `n` means n levels, and no arguments gives every variable in every scope. Later arguments are scopes or individual signals, and may be mixed. Those are counts of one revision of one testbench: add a variable or a named block and they move, so re-run the command rather than trust the table.

What gets recorded is broader than you expect: `integer` and `real` variables are dumped, parameters are dumped (`localparam real PERIOD = 10.0` became `$var real 1 " PERIOD $end`), and named blocks and even **tasks** become scopes — dumping `tb_anatomy` produced `$scope begin watchdog $end` and `$scope task check $end`, the latter holding that task's arguments. None of that is what you want in a viewer: the practical reason to dump a subtree.

> **Trap.** **Icarus Verilog 13.0 does not dump memory arrays.** A `reg [7:0] mem [0:3]` appears in no VCD under any `$dumpvars` variant, in neither the testbench nor the DUT. Asking for it by name is not even a warning; `vvp` refuses to load the program at all: `ERROR: bad_dumparray.v:32: $dumpvars cannot dump a vpiMemory.`, exit 1. Individual **words** can be dumped one at a time and arrive as escaped identifiers (`$var reg 8 % \mem[0] [7:0] $end`), with a warning each:
>
> ```
> VCD warning: array word bad_dumparray.mem[0] will conflict with an escaped identifier.
> VCD warning: array word bad_dumparray.mem[1] will conflict with an escaped identifier.
> ```
>
> No flag changes this. To see memory contents, name each word — `$dumpvars(0, m[0], m[1], ...)`, which a `generate` loop can write for you — or print them with `$display`. `bad_dumparray.v` shows both halves: the data is there, the waveform is not.

> **Seed for chapter 12.** The adder's testbench will hold a vector memory and chapter 12's design may hold a register file. Both will simply be missing from the viewer, and the first instinct on "my register file is wrong" is to look there and conclude the tool is broken. It is not.

You can record part of a run: `$dumpoff` suspends recording and `$dumpon` resumes it, the answer when the interesting window is a thousand cycles in. `tb_dump.v` does it with `+window`. Note what `$dumpoff` writes — **every dumped signal is set to `x`** — so the viewer shows a visibly dead region, not a frozen one you might mistake for a stuck design.

Now the format: VCD is line-oriented text, and reading one is a real skill. The head of a file from `$dumpvars(0, tb_dump.u_pipe)`:

```
$date
	Mon Aug 10 01:44:04 2026
$end
$version
	Icarus Verilog
$end
$timescale
	1ps
$end
$scope module tb_dump $end
$scope module u_pipe $end
$var wire 1 ! clk $end
$var wire 8 " d [7:0] $end
$var wire 8 # q [7:0] $end
$var wire 8 $ mid [7:0] $end
$scope module u_a $end
$var wire 1 ! clk $end
$var wire 8 % d [7:0] $end
$var reg 8 & q [7:0] $end
$upscope $end
$scope module u_b $end
$var wire 1 ! clk $end
$var wire 8 ' d [7:0] $end
$var reg 8 ( q [7:0] $end
$upscope $end
$upscope $end
$upscope $end
$enddefinitions $end
$comment Show the parameter values. $end
$dumpall
$end
#0
$dumpvars
bx (
bx '
bx &
b0 %
bx $
bx #
b0 "
0!
$end
#5000
b0 $
b0 &
b0 '
1!
#10000
```

Everything you need is in there. The header's `$timescale` is the **precision**, not the unit — `1ps` here, which is why `#5` in the source appears as `#5000`. `$scope` and `$upscope` build the hierarchy tree that becomes the viewer's sidebar. `$var <type> <width> <id> <name> $end` declares a signal, `<id>` being a short printable-ASCII code; `clk` is `!` in all three scopes because it is one net seen from three places, so **one identifier can appear under several names**. After `$enddefinitions` come the value changes: `#<time>` opens a time step, then one line per changed signal — scalars as `<value><id>` with no space, vectors as `b<bits> <id>` with one, reals as `r<number> <id>`. Only changes are recorded.

Its problem is size, because it is text. Icarus can write **FST** instead — binary, block-compressed, incrementally written, from the GTKWave project — chosen at *run* time as an extended argument after the design file: `vvp sim.vvp -fst`, or `-fst-space` to repack on close, `-lxt2` for the older format, `-none` to suppress dumping. The same 100,000-cycle run four ways — `vvp sim.vvp +dump=/tmp/w.vcd +cycles=100000`, then again with `-lxt2`, `-fst` and `-fst-space` writing `/tmp/w.lxt2` and `/tmp/w.fst`:

| dumper | bytes | ratio |
|---|---|---|
| VCD (default) | 14 654 851 | 1.0× |
| `-lxt2` | 872 834 | 16.8× smaller |
| `-fst` | 218 067 | 67× smaller |
| `-fst-space` | 6 654 | 2202× smaller |

Use those exact names to reproduce them: the `+dump=` string is itself a dumped variable, so a longer path makes the file bigger.

Read those ratios with care: these signals are a counter and its delayed copies, about as compressible as data gets, and a design carrying random-looking values compresses far less. The honest summary is that **FST is smaller than VCD by one to three orders of magnitude for no effort**, and is written incrementally, so a killed simulation still leaves a usable trace. Control size in this order: dump a subtree, window it, switch to `-fst`.

**GTKWave is not dead, though.** Queried through the GitHub API today, `github.com/gtkwave/gtkwave` is not archived and not disabled, GPL-2.0, last commit **2026-04-18**, last push **2026-07-23**, latest tag **v3.3.116** — ahead of the 3.3.107 Homebrew froze at. What does belong there is **Surfer**, in homebrew-core proper — not a tap, not a cask: `surfer: stable 0.7.0 (bottled), HEAD`, from `Formula/s/surfer.rb`, EUPL-1.2. `brew install surfer`, then `surfer /tmp/w.vcd`. Written in Rust at Linköping University; its `--help` offers VCD, FST and GHW, its README a fourth, FTR. Prebuilt Linux and Windows binaries, a source build on all three platforms, and a browser build that uploads nothing. That is this guide's recommendation today.

> **Icarus reality.** There is **no scriptable waveform viewer in this environment.** Surfer's `server` subcommand looks like one and is not: "headless" there means serving a waveform file over the network to a Surfer *GUI client* elsewhere (`--port`, `--bind-address`, `--token`, `--file`). `--command-file` replays interactive commands into the GUI after load, and its own help calls that feature temporary. Surfer has no mode that renders an image or answers a question about a signal from a command line. So **every statement below about clicking, zooming, colours or menu layout is documentation, not measurement** — the same wall chapter 3 maintains between what was run here and what was read in a manual. A machine-checkable answer comes from the testbench, or from parsing the VCD in Python; the viewer is for the human.

Which is why the figure below is a **drawing**, not a screenshot: `tb_dump.v`'s two-stage pipeline as a viewer would show it, column-checked against the values the simulation produced.

```
cycle   0         1         2         3         4         5
clk     -----_____-----_____-----_____-----_____-----_____-----_____-----
d       <   ><   10   ><   11   ><   12   ><   13   ><   14   ><   15   >
mid     <        ><   10   ><   11   ><   12   ><   13   ><   14   >< 15>
q       <   x    ><        ><   10   ><   11   ><   12   ><   13   >< 14>
```

Read it and the pipeline explains itself. `d` changes mid-cycle, because the testbench drives on the far edge — that is what the opposite-edge rule buys you. `mid` changes on the rising edges, one cycle behind `d`; `q` one cycle behind `mid`, and only while `clk` is **high**, which in zero-delay RTL means only at a rising edge — the weaker property that `tb_dump.v`'s second check pins: give stage 2 a clock-to-Q delay of 4 ns and `q` moves mid-phase and still passes; 6 ns crosses the falling edge and fails. The `x` at the left of `q` is the flip-flops' unknown power-on state; it ends at t = 15 ns, where `q` takes the `00` that `d` held at time zero, and an `x` to the right of that would be a bug. The horizontal distance between a value on `d` and the same value on `q` is the **latency**: count the rising edges between the two and you get two.

> **Seed for chapter 11.** That is why a pipeline gets read in a waveform rather than a log. When the adder is pipelined the questions become "how many cycles from input to output", "does the `valid` bit arrive with its data", "did stage 3 stall while stage 2 kept going" — all questions about horizontal distance between rows, none easy to answer from printed text.

How to read one, as a procedure rather than a tour of a user interface. **Clock at the top**, because everything is read relative to its edges; then reset, then DUT inputs, outputs and internals in signal-flow order — and resist adding two hundred signals, because you will not read them. **Check the very beginning**, where only the *leftmost* `x` is the bug. For anything wider than four bits, **read the value column, not the wiggles**. "Debugging Methodically" has the rest.

Two other tools. **VaporView**, a VS Code extension, reads VCD, FST and GHW natively and makes a printed timestamp clickable. **WaveDrom** renders hand-written JSON timing diagrams to SVG: right for figures, wrong for debugging.

Finally, the workflow this chapter is selling. Your testbench prints `FAIL tb_vectors: t=5000 a=ff b=01 got=1_00 want=1_aa`; you open the trace, jump the cursor to **t = 5000**, and look only there. The message gives the *when*, the waveform the *why*.

## Debugging Methodically

Five habits, in the order to use them.

**Read the first divergence, not the last.** A failing run prints dozens of `FAIL` lines and almost every one after the first is a consequence of it. Fix the earliest failing time, re-run, and the tail usually vanishes. Inside a waveform the same holds: the leftmost wrong value is the bug, everything right of it is symptom. Mark the first edge where an output is wrong, then walk *backwards* until the inputs are right and the output is wrong. This habit saves more time than the other four together.

**Bisect, in time and structure.** Failure at cycle 900 and correctness at cycle 10 is a bracket — is the state you can name still right at 450? A `$strobe` of one internal signal per cycle into a log, plus `grep`, finds the first bad cycle in two or three runs, and because `$random` is deterministic the bisection is repeatable. Bisect structure the same way, at the boundaries between unpack, align, add, normalise, round and pack.

**Print the same expression from three places.** `$display` from a posedge is pre-NBA, `$strobe` from the same posedge post-NBA, `$display` from the negedge fully settled; disagreement among the three is a region problem, not a logic problem.

**Dump a golden reference alongside the DUT.** The strongest technique at this level, and barely more work than printing: compute the expected value in the testbench with whatever unsynthesisable Verilog you like, assign it to a `reg`, and dump it. The viewer then shows `dut_result` and `golden_result` on adjacent rows, and the cycle where they part is visible at a glance.

> **Seed for chapters 5, 9 and 12.** That is a *mechanic*, not a methodology; turning it into a scoreboard — something that tracks outstanding transactions, checks every one and reports coverage rather than one verdict — is chapter 5's job. Chapter 2 already found the route to a trustworthy reference: Icarus supports `shortreal` with `$shortrealtobits` and `$bitstoshortreal`, so a binary32 golden model can live inside the simulator, cross-checked against Python's `struct` where that reference is itself suspect.

**Know what all-`x` usually means**, and check in this order rather than reasoning: the clock never toggled; reset was never asserted, or asserted after the first edge; a `reg` is never assigned; a port is unconnected, which `-Wall`'s `portbind` class does catch. `+` poisons every bit of its result, so one unknown bit becomes a fully unknown value several stages downstream — **search upstream, never downstream** — while the bitwise operators and `?:` are per-bit, so the *pattern* of surviving bits identifies the bad one. Which is why you print with `%b`.

And when you have found it, **reduce to a minimal case**. Take the exact inputs from the `FAIL` line, write a tiny testbench applying only that vector, confirm it still fails — if it does not, the bug is state-dependent, itself information — then shrink the inputs field by field, because each simplification that preserves the failure removes a suspect. Keep the minimal case as a regression test.

## Automating the Build

A regression you have to remember how to run is one you will stop running. The target is a single command that builds everything, runs it, and returns a non-zero exit status if anything is wrong.

Four `iverilog` options beyond chapter 2's `-g2012 -Wall -o` earn their place. **`-s topmodule`** names the root, mandatory once more than one testbench is in play. **`-y dir`** makes `dir` a library: for every unresolved module, `iverilog` looks for `dir/<modulename>.v`, so a testbench pulls in its DUT without anyone listing the file. **`-D NAME`** defines a macro from the command line — how `bad_dumparray.v`'s whole-array request is switched on. And **`-t null`** elaborates and emits nothing, a real syntax gate: exit 0 and no output file on good source, `syntax error` / `I give up.` and exit **2** on a missing semicolon. At run time, **`vvp -N`** turns a stray `$stop` from "hang the job forever" into "fail the job".

Here is `src/ch04/Makefile` in full, the one that produced the transcripts below:

```make
# Chapter 4 regression. Artifacts go to $(BUILD), never next to the source.
#   make / make -k / make lint / make clean
#   make BUILD=/tmp/x        put the artifacts somewhere else
#   make PLUSARGS=+break     prove the failure gate actually fires
# Adding a test is adding a file: the list is discovered, not maintained.
# The pattern rule requires that file tb_foo.v contains module tb_foo.

IVERILOG ?= iverilog
VVP      ?= vvp
IVFLAGS  ?= -g2012 -Wall -y .
BUILD    ?= /tmp/ch04-build
PLUSARGS ?=

# -y . resolves the DUT at compile time, which make cannot see, so every .v is
# a prerequisite of every build. Coarse; iverilog -M writes exact depfiles.
SRCS := $(wildcard *.v)
DATA := $(wildcard *.hex)

# bad_adder8.v is a module, not a testbench: -y . pulls it in for tb_check.
TESTS := $(filter-out bad_adder8, \
           $(notdir $(basename $(wildcard tb_*.v) $(wildcard bad_*.v))))

all: test
test: $(addprefix run-,$(TESTS))

$(BUILD):
	@mkdir -p $(BUILD)

$(BUILD)/%.vvp: %.v $(SRCS) | $(BUILD)
	$(IVERILOG) $(IVFLAGS) -s $* -o $@ $<

# Compiling is cached, running is not: a result make calls up to date is a test
# that has quietly stopped running, and no PLUSARGS would reach it. FORCE keeps
# every run-% out of date. vvp runs in the source directory, because $readmemh
# resolves relative paths against the working directory; nothing is written
# there, since the log goes to $(BUILD) and dumping is behind a plusarg.
run-%: $(BUILD)/%.vvp $(DATA) FORCE
	@log=$(BUILD)/$*.log; \
	 $(VVP) $< $(PLUSARGS) > $$log 2>&1; \
	 rc=$$?; \
	 if [ $$rc -ne 0 ] || grep -qE '(^|[^A-Za-z])FAIL' $$log; then \
	   echo "FAIL $*  (rc=$$rc)"; sed 's/^/    /' $$log; exit 1; \
	 else echo "ok   $*"; fi

# Elaborate every testbench and emit nothing: a whole-suite syntax gate.
lint:
	@for t in $(TESTS); do \
	   $(IVERILOG) $(IVFLAGS) -t null -s $$t $$t.v || exit 1; \
	 done

clean:
	rm -rf $(BUILD)

FORCE:

.PHONY: all test lint clean FORCE
.PRECIOUS: $(BUILD)/%.vvp
```

Six decisions in there are load-bearing. **Tests are discovered, not listed**, so a test nobody remembered to list cannot quietly stop running. **`-s $*`** requires that `tb_foo.v` contains module `tb_foo`. **Every `.v` is a prerequisite of every compile**, because `make` cannot see the edge `-y .` creates — that is the whole reason the harness notices a broken DUT. (`$(DATA)` on the run rule is belt and braces: `FORCE` already makes every run out of date, and a data file never enters a compile at all.) **Compiles are cached and runs are not**: a `.log` treated as a build artifact is a test that stopped running the moment it ran once. **The failure gate uses both signals** — `rc != 0` catches `$fatal` and `vvp -N` on a `$stop`, `grep -q FAIL` catches a testbench that reported with `$error` and exited 0. And **`vvp` runs in the source directory**, because `$readmemh` resolves relative paths against the working directory; nothing lands in the tree, since dumping is behind a plusarg.

Run it and all fourteen tests go green in a couple of seconds. Two experiments prove the harness is worth having, both on a *warm* tree with no `make clean` first. First, `make -k PLUSARGS=+break` re-runs every test with a plusarg that makes `tb_vectors.v` assert a value it knows to be wrong:

```
ok   tb_strobe
FAIL tb_vectors  (rc=1)
    FAIL tb_vectors: t=5000 a=ff b=01 got=1_00 want=1_aa
    FAIL tb_vectors: 1 of 8 vectors wrong
    FATAL: tb_vectors.v:67: 1 error(s)
           Time: 16000  Scope: tb_vectors
make: *** [run-tb_vectors] Error 1
ok   bad_dumparray
```

`make -k` ran the rest, and the exit status was **2**. Second, change `adder8.v` from `a + b` to `a - b` and type `make`: every binary is out of date, `make` rebuilds the eight it reaches before the run stops at `FAIL tb_stimulus` with exit **2**, and `make -k` rebuilds all fourteen and catches `tb_vectors` too. Repeat both whenever the harness changes: a gate that has never fired is one you trust on faith, and an untested dependency edge is usually missing.

> **Trap.** GNU Make 3.81, which macOS still ships, compares timestamps to the whole second. Edit `adder8.v` inside the same second as the previous build and `make` misses the change entirely: fourteen green targets against a subtractor. Wait a second, or `touch` the file. `run_all.sh` cannot be fooled this way — it compiles into a fresh `mktemp -d` every run.

Plusargs make one compiled binary serve many runs, and `tb_plusargs.v` measures their two rules. `$test$plusargs("verbose")` returns presence as 1 or 0. `$value$plusargs("count=%d", n)` returns 1 on a match and **leaves the variable untouched on failure**, so assign the default *before* the call. Matching is **case-sensitive**.

> **Seed for chapters 9 and 12.** This Makefile, `targets.txt` and `run_all.sh` are the regression the adder will be developed against. By chapter 12 the same command builds every module, runs a corner-case suite and a several-thousand-vector sweep, and gates on both signals. Set it up now, while it is fourteen tiny tests.

The exit codes worth memorising: `iverilog` gives 0 on success and non-zero on any error — measured here, **2** for a syntax error, an unknown module type and a duplicate module, **1** for a bad port name or an unreadable file, and *either* for the same unknown identifier, which returns 2 from a continuous assignment and 1 from a procedural statement with a byte-identical diagnostic. So do not read a category out of the number. `vvp` gives 0 for a normal end or `$finish`, **1 for `$fatal`**, 1 for a runtime error such as `$dumpvars` on a memory, and 1 for `$stop` under `-N`. Not for `$error`, `$warning` or `$info` — the entire reason the `FAIL`-string convention exists.

## Traps Beginners Fall Into

Every trap below was demonstrated with running code above; this table is the index. The third column is the point: as in chapter 3, **for most of these the simulator says nothing at all.**

| Trap | What you see | Reported by Icarus? | File |
|---|---|---|---|
| No `$finish` with a free-running clock | terminal hangs, needs Ctrl-C | **No** — killed at 4 s, exit 137 | — |

## Bridge to Chapter 5

You can now build the instrument: a clock that runs, a sequenced reset, stimulus on the safe edge, checks that use `!==` and count what they find, a verdict a program can read, a trace for when that verdict is bad, and a Makefile that runs the lot. What none of it tells you is whether the experiment was any good. `tb_check.v` showed the shape of the problem — had its one accidentally-passing vector been your only test, you would have shipped a subtractor. Chapter 5 takes the question this chapter refused: **which inputs, how many, and how do you know when you have enough?** It builds a golden reference model, works out an IEEE 754 adder's corner cases, introduces assertions, and takes coverage seriously enough to answer "what did my tests never reach".
