static func moveToward(_ current: Vec3, _ target: Vec3, _ maxDelta: Float) -> Vec3 {
    let d = target - current
    let dist = simd_length(d)
    if dist <= maxDelta { return target }
    return current + d * (maxDelta / dist)
}

Same skeleton as the scalar version — abs(d) becomes simd_length(d), the sign step becomes a scale.

The trap, precisely

Obvious version:

return current + simd_normalize(d) * maxDelta   // ← NaN when d is zero

simd_normalize divides by length. Length 0 gives 0/0 = NaN in all three lanes.

But note the guard already saves you — if dist == 0 then dist <= maxDelta is true for any maxDelta >= 0, so you return early and never divide. The bug only bites if you write:

if dist < maxDelta { return target }    // strict — WRONG

Coincident points with maxDelta == 0 (paused, dt == 0, throttle at rest) give 0 < 0 = false, fall through, divide by zero. < vs <= is the whole difference. Scalar version has the same subtlety and gets it right.

Writing d * (maxDelta / dist) instead of simd_normalize(d) * maxDelta also drops a redundant division — normalize divides by dist, then you multiply by maxDelta. One reciprocal, three multiplies.

Why NaN specifically hurts here

NaN is sticky and silent. It lands in Transform.position, spreads through Math.trs into the model matrix, into InstanceData, onto the GPU. NaN fails every comparison including clip tests, so the object does not glitch — it disappears, permanently, with no error anywhere. You go looking in the renderer for a bug that is in the math.

Second trap, not in the prompt

Do not build it by applying the scalar version per component:

Vec3(moveToward(current.x, target.x, maxDelta),   // ← wrong
     moveToward(current.y, target.y, maxDelta),
     moveToward(current.z, target.z, maxDelta))

Compiles, never NaNs, still wrong. Each axis moves up to maxDelta independently, so a pure-diagonal move covers √3 · maxDelta — 73% too fast. This is the classic diagonal-speed bug, and it also curves the path: fast axes arrive first, then movement continues along the remainder. "In a straight line" in the challenge text is the requirement that rules this out.

Optional refinement

If you expect the early-out to dominate, skip the sqrt:

let dist2 = simd_length_squared(d)
if dist2 <= maxDelta * maxDelta { return target }
return current + d * (maxDelta / dist2.squareRoot())

Only worth it if most calls land within reach. Otherwise you compute the same sqrt one line later and gained nothing.

Where it pays off

The camera is the interesting one — a Vec3 moveToward gives constant-speed follow with a hard arrival, where the exp smoothing in that chapter gives exponential decay that never quite lands. Different feel: moveToward for a camera that keeps up rigidly then stops dead, exp for one that trails and settles. Try both, they are three lines apart.
