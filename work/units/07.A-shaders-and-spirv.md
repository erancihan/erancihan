## SPIR-V: shaders as bytecode, not text

Vulkan does **not** consume GLSL. It consumes **SPIR-V**, a portable binary
intermediate representation, and the translation happens in your build rather than
in the driver.

That is a real design decision with real consequences. Shader compilation is
decoupled from the vendor, so a shader that compiles on your machine parses
identically on everyone's — no more discovering that one vendor's GLSL front-end
accepts something the spec doesn't. Errors surface at **build** time with a file and
line number. And the driver's job shrinks to translating well-formed bytecode,
which is a large part of why Vulkan draw calls are cheap.

The cost is a build step, which chapter 01 already set up: every `.vert` and `.frag`
in `shaders/` becomes a `.spv` next to the binary. You get that for free from here
on — write a shader, build, and it is compiled.

## The lit pair: ship and enemies

Start with the pair that shows every idea. The vertex shader's job is to take a
corner of a mesh, place it in the world using its instance's matrix, and hand the
rasteriser a clip-space position.

**`shaders/lit.vert`** — new file:

```glsl
#version 450

layout(location = 0) in vec3 inPosition;
layout(location = 1) in vec3 inNormal;

struct InstanceData {
    mat4 model;
    vec4 color;
};
```

Those two `location` numbers are a contract. Chapter 07.B will describe the vertex
buffer to the pipeline with attribute descriptions numbered 0 and 1, at offsets 0
and 12 into a 24-byte `Vertex`. These `in` declarations are the other half. Get them
out of order and the GPU feeds normals into positions — which does not error,
because both are `vec3`.

`InstanceData` is declared here in GLSL and separately in C++ in
`RenderTypes.hpp`. Two declarations of the same 80 bytes, in two languages, that
nothing checks against each other. Chapter 03's `static_assert` guards the C++
side's size; the shader side you guard by keeping the two next to each other in
your head. This duplication is the most fragile seam in the project, and it is
inherent — there is no shared header between C++ and GLSL.

**`shaders/lit.vert`** — after the `InstanceData` struct:

```diff
 struct InstanceData {
     mat4 model;
     vec4 color;
 };
+
+layout(set = 0, binding = 0) uniform FrameUniforms {
+    mat4 viewProjection;
+    vec4 cameraPosition;
+    vec4 lightDirection;
+} frame;
+
+layout(set = 0, binding = 1, std430) readonly buffer Instances {
+    InstanceData instances[];
+};
```

`set = 0, binding = 0` and `set = 0, binding = 1` are the numbers chapter 06 put in
`VkDescriptorSetLayoutBinding`. Same numbers, same types — a uniform block at 0, a
storage block at 1 — or the pipeline is rejected at creation.

Two GLSL details worth naming. `readonly` on the buffer lets the compiler assume
nothing writes it, which matters for scheduling; and it also matches the
`VK_SHADER_STAGE_VERTEX_BIT`-only visibility we declared. `std430` is the layout
rule chapter 03 sized the struct against — the *only* difference from `std140` that
affects us is that std430 doesn't round array strides up to 16 bytes, which is why
an 80-byte element packs with no gap.

`instances[]` with no size is a **runtime array**, legal as the last member of a
storage block. Its length comes from the buffer we bound, which is how one shader
serves 1 instance or 4,096.

**`shaders/lit.vert`** — after the `Instances` block:

```diff
 layout(set = 0, binding = 1, std430) readonly buffer Instances {
     InstanceData instances[];
 };
+
+layout(location = 0) out vec3 vNormal;
+layout(location = 1) out vec4 vColor;
+
+void main() {
+    InstanceData inst = instances[gl_InstanceIndex];
+    vec4 world = inst.model * vec4(inPosition, 1.0);
+    gl_Position = frame.viewProjection * world;
+    vNormal = mat3(inst.model) * inNormal;
+    vColor = inst.color;
+}
```

Four lines, and three of them are the chapter-03 math made real.

**`gl_InstanceIndex`** is the whole instancing mechanism: one draw call runs this
shader `vertexCount × instanceCount` times, and this built-in tells each run which
copy it belongs to. Chapter 07.B explains why we index a storage buffer rather than
using per-instance vertex attributes.

**`frame.viewProjection * inst.model * vec4(inPosition, 1.0)`** is the MVP chain,
with P and V pre-multiplied on the CPU so the shader does two matrix multiplies
instead of three.

**`mat3(inst.model) * inNormal`** rotates the normal into world space. Taking the
upper-left 3×3 drops the translation, which is right — a normal is a direction, not
a place, and translating it is meaningless. (Strictly this is only correct for
uniform scale. Non-uniform scale needs the inverse transpose; all our scaling is
uniform except the bolt, which is unlit, so we skip it. That is a shortcut, and
this is it being labelled.)

### The fragment side

**`shaders/lit.frag`** — new file:

```glsl
#version 450

layout(location = 0) in vec3 vNormal;
layout(location = 1) in vec4 vColor;

layout(set = 0, binding = 0) uniform FrameUniforms {
    mat4 viewProjection;
    vec4 cameraPosition;
    vec4 lightDirection;
} frame;

layout(location = 0) out vec4 outColor;
```

The `in` locations here match the `out` locations in `lit.vert` — that is the third
numbering contract in this chapter, and the only one the *compiler* checks for you,
because both sides are GLSL.

The `FrameUniforms` block is declared again, identically. It has to be: the fragment
stage reads `lightDirection`, and each stage declares what it uses. This is also
why chapter 06 gave binding 0 both `VERTEX_BIT` and `FRAGMENT_BIT` while binding 1
got vertex only.

`layout(location = 0) out vec4 outColor` is attachment 0 of the render pass — the
colour image. The same index chapter 05.A used in `colorRef`.

**`shaders/lit.frag`** — after the `outColor` declaration:

```diff
 layout(location = 0) out vec4 outColor;
+
+void main() {
+    vec3 N = normalize(vNormal);
+    vec3 L = normalize(-frame.lightDirection.xyz);
+    float diffuse = max(dot(N, L), 0.0);
+    outColor = vec4(vColor.rgb * (0.25 + diffuse * 0.85), vColor.a);
+}
```

That is the entire lighting model: one dot product, exactly as chapter 03 promised.

`normalize(vNormal)` is not redundant. The rasteriser interpolates the normal across
the triangle, and interpolating two unit vectors gives you something shorter than
unit length in the middle. Skip it and faces get subtly darker toward their centres.

`-frame.lightDirection.xyz` flips the light's *travel* direction into the direction
*toward* the light, which is what the dot product wants. `max(…, 0.0)` clamps away
faces pointing away from the light, which would otherwise produce negative
brightness and, after the multiply, black holes where a surface should merely be
unlit.

`0.25` is ambient, so shadowed faces are dim rather than pure black; `0.85` is how
hard the sun hits. Those two numbers are the whole art direction. Try `0.0` and
`1.0` for a harsh, high-contrast look.

## The unlit pair: grid and bolts

Same vertex transform, no lighting. Used for the ground grid and the glowing bolts,
which want their colour delivered exactly as authored.

**`shaders/unlit.vert`** — new file:

```glsl
#version 450

layout(location = 0) in vec3 inPosition;

struct InstanceData {
    mat4 model;
    vec4 color;
};

layout(set = 0, binding = 0) uniform FrameUniforms {
    mat4 viewProjection;
    vec4 cameraPosition;
    vec4 lightDirection;
} frame;
```

Note what is **missing**: there is no `layout(location = 1) in vec3 inNormal`. This
shader has no use for a normal, so it doesn't declare one — and chapter 07.B gives
its pipelines a vertex layout with only one attribute to match. Declaring an
attribute the shader never reads is a validation *performance* warning, and one of
the few things in Vulkan that is wrong without being broken.

**`shaders/unlit.vert`** — after the `FrameUniforms` block:

```diff
     vec4 lightDirection;
 } frame;
+
+layout(set = 0, binding = 1, std430) readonly buffer Instances {
+    InstanceData instances[];
+};
+
+layout(location = 0) out vec4 vColor;
+
+void main() {
+    InstanceData inst = instances[gl_InstanceIndex];
+    gl_Position = frame.viewProjection * inst.model * vec4(inPosition, 1.0);
+    vColor = inst.color;
+}
```

**`shaders/unlit.frag`** — new file:

```glsl
#version 450

layout(location = 0) in vec4 vColor;
layout(location = 0) out vec4 outColor;

void main() {
    outColor = vColor;
}
```

Four lines. Worth keeping as a reference point: this is the smallest useful fragment
shader, and everything else is this plus arithmetic.

## The star pair: an infinite sky from three thousand points

The starfield is a few thousand points scattered in a cube. Fly far enough and you
would leave the cube, and space would go black.

The fix is a trick done entirely on the GPU, and it is the best argument in this
guide for moving a *rule* into a shader rather than looping on the CPU.

**`shaders/star.vert`** — new file:

```glsl
#version 450

layout(location = 0) in vec3 inPosition;
layout(location = 1) in vec3 inNormal;

layout(set = 0, binding = 0) uniform FrameUniforms {
    mat4 viewProjection;
    vec4 cameraPosition;
    vec4 lightDirection;
} frame;

layout(push_constant) uniform StarParams {
    float span;
} params;
```

There is the **push constant** chapter 06 described: no descriptor, no buffer, four
bytes written straight into the command buffer. `span` is the size of the tile.

`inNormal` is declared even though stars have no lighting. Chapter 08 stores each
star's brightness in `normal.x` — a spare channel on a vertex format we already had.
That is a small, deliberate hack, and the alternative (a second vertex format and a
second mesh path) would cost more than it teaches.

**`shaders/star.vert`** — after the push-constant block:

```diff
 layout(push_constant) uniform StarParams {
     float span;
 } params;
+
+layout(location = 0) out float vBrightness;
+
+void main() {
+    vec3 rel = inPosition - frame.cameraPosition.xyz;
+    rel = rel - round(rel / params.span) * params.span;
+    vec3 world = frame.cameraPosition.xyz + rel;
+
+    gl_Position = frame.viewProjection * vec4(world, 1.0);
+    gl_PointSize = 2.0;
+    vBrightness = inNormal.x;
+}
```

Those three lines in the middle are the trick. `rel` is the star's offset from the
camera. `round(rel / span) * span` is the nearest whole multiple of the tile size,
and subtracting it **folds the star into the single tile centred on the camera**.
Every star is always within half a tile of you, in every direction, forever. Fly a
million units and the sky is still full, at zero CPU cost, because the rule runs
per-vertex on hardware that was going to transform those vertices anyway.

**`gl_PointSize` is not optional here.** With point-list topology Vulkan has no
default size, and leaving it unwritten is undefined behaviour — you may get one
pixel, you may get nothing. And any value other than `1.0` additionally requires the
device-level **`largePoints`** feature, which is why chapter 02 enabled it in
`pEnabledFeatures`. If your stars come out as single pixels, that feature is the
thing to check.

**`shaders/star.frag`** — new file:

```glsl
#version 450

layout(location = 0) in float vBrightness;
layout(location = 0) out vec4 outColor;

void main() {
    float d = distance(gl_PointCoord, vec2(0.5));
    if (d > 0.5) discard;
    float falloff = smoothstep(0.5, 0.1, d);
    outColor = vec4(vec3(vBrightness) * falloff, 1.0);
}
```

A point is rasterised as a **square**, and `gl_PointCoord` gives each fragment its
position within that square, from `(0,0)` to `(1,1)`. Measuring distance from the
centre and discarding beyond 0.5 carves a circle out of it.

`smoothstep(0.5, 0.1, d)` then fades from the edge inward — note the arguments are
*reversed* (0.5 then 0.1), which is what makes it return 0 at the rim and 1 at the
core rather than the other way round. Without it you get hard-edged discs that
alias badly as they move; with it, soft dots.

`discard` is worth a word of caution: it forces the hardware to abandon early depth
testing for the whole draw, because a fragment's survival is no longer knowable
before running the shader. For three thousand two-pixel points that cost is
irrelevant. In a shader covering the screen it would not be.

## The HUD pair: 2D over everything

The HUD skips the whole MVP chain and gives positions **directly in clip space**.
Which means it also skips the projection matrix — and with it, the Y-flip.

**`shaders/hud.vert`** — new file:

```glsl
#version 450

layout(location = 0) in vec2 inPosition;
layout(location = 1) in vec4 inColor;

layout(location = 0) out vec4 vColor;

void main() {
    gl_Position = vec4(inPosition.x, -inPosition.y, 0.0, 1.0);
    vColor = inColor;
}
```

This is the only shader with a different vertex layout — `vec2` position and `vec4`
colour, matching `HUDVertex` rather than `Vertex`. Chapter 07.B gives it its own
attribute descriptions for exactly that reason.

**`-inPosition.y`** is chapter 03's rule 4 leaking back out. For 3D geometry we
hid Vulkan's downward Y inside `Math::perspective`; the HUD has no projection to
hide it in, so the flip happens here. The benefit is that chapter 13 can author
`(0, +0.9)` as "near the top" like a normal person. Forget this one character and
your HUD is mirrored top-to-bottom while the 3D world looks perfect — a genuinely
confusing pairing, precisely because the two use different paths to clip space.

`z = 0.0` puts every HUD vertex at the near plane, which is harmless because
chapter 07.B's HUD pipeline disables depth testing entirely.

**`shaders/hud.frag`** — new file:

```glsl
#version 450

layout(location = 0) in vec4 vColor;
layout(location = 0) out vec4 outColor;

void main() {
    outColor = vColor;
}
```

Identical to `unlit.frag`, and kept separate anyway. They will diverge the moment
you add textured text (chapter 13), and a shared shader that two pipelines depend on
is a worse problem than four duplicated lines.

Eight shaders in, eight `.spv` out. Confirm they landed where the renderer will look
for them:

```console
$ ls build/shaders/
hud.frag.spv  hud.vert.spv  lit.frag.spv  lit.vert.spv
star.frag.spv star.vert.spv unlit.frag.spv unlit.vert.spv
```

Running the program still gives you the same blue window — nothing loads these yet.

| Symptom | Likely cause |
|---|---|
| `'…' : syntax error` with a file and line | A real GLSL error. The line number is accurate; unlike a C++ template error, believe it. |
| No `compiling …` lines at all | CMake hasn't re-scanned `shaders/`. `CONFIGURE_DEPENDS` handles new files, but re-run `cmake -S . -B build` if it doesn't. |
| `'buffer' : storage qualifier requires …` | Missing `#version 450`, or a version below 430 — storage blocks don't exist before that. |
| `'gl_InstanceIndex' : undeclared identifier` | You wrote `gl_InstanceID`, which is the OpenGL spelling. Vulkan's is `gl_InstanceIndex`. |
| Only 6 or 7 files compiled | A shader is named `.glsl` or `.frag.txt`; the glob only matches `*.vert` and `*.frag`. |

**Try breaking it on purpose.** In `lit.vert`, swap the two `location` numbers so
position is 1 and normal is 0. Rebuild. **It compiles perfectly** — both are `vec3`,
and GLSL has no idea one of them is meant to be a position. Nothing will complain
until chapter 08, when your ship renders as an unrecognisable spike because the
GPU has been feeding normals through the model matrix. Put them back, and take the
lesson: **the vertex-attribute contract is checked by nobody.**

## Challenge

Give the lit shader a second, dimmer light from below — a cheap "bounce" fill that
stops the undersides of ships going flat.

Three things to get right. `FrameUniforms` is at 96 bytes and pinned there by a
`static_assert`; adding a `vec4` means updating the struct, the assert, *and* both
GLSL declarations of the block, and missing any one of the four gives you a silent
misread rather than an error. The second light must be summed *before* the ambient
term, not after, or you will double the ambient and wash the whole scene out. And
decide whether the fill light casts colour: a slightly blue bounce reads as
sky-light and costs nothing, but it will fight the cyan of the bolts and the HUD,
so pick a hue that loses that argument on purpose.
