>

## One immutable object, every decision frozen

A `VkPipeline` bundles the two programmable stages **and every fixed-function
decision the GPU makes around them** — vertex layout, topology, cull mode, depth
test, blend equation, the lot — into one object that is compiled once and never
changed.

That is a lot of ceremony for a triangle. What it buys is that the driver validates
and compiles the entire configuration up front, and then does **zero per-draw state
checking**. An OpenGL driver re-validates a pile of global state on every draw call
because any of it might have changed; a Vulkan driver knows it can't have.

Here is the full cast, and what each decides for us:

| State | What it decides | Ours |
|---|---|---|
| `VertexInputState` | Buffer stride + attribute layout | mesh (pos+normal), mesh (pos only), or HUD (vec2+vec4) |
| `InputAssemblyState` | How vertices group into primitives | triangles / lines / points |
| `ViewportState` | The viewport and scissor rectangles | **dynamic** — set at record time |
| `RasterizationState` | Fill mode, culling, winding, line width | fill, **cull none**, CCW |
| `MultisampleState` | MSAA sample count | 1 (off) |
| `DepthStencilState` | Test, write, compare op | three modes, below |
| `ColorBlendState` | How a fragment combines with the target | three modes, below |
| `DynamicState` | Which states are *not* baked | viewport + scissor |
| `PipelineLayout` | Descriptor set layouts + push-constant ranges | one, shared by all five |

Two of those carry real rendering decisions rather than boilerplate, so they get
enums:

**`Renderer.hpp`** — after `struct FrameSync`:

```diff
     VkFence inFlight = VK_NULL_HANDLE;

+
+enum class DepthMode { TestWrite, TestOnly, Off };
+enum class BlendMode { Opaque, Additive, Alpha };
+enum class VertexLayout { Mesh, MeshPositionOnly, Hud };
```

- **`TestWrite`** — solids. Test against the depth buffer *and* write to it, so near
  things hide far things with no sorting.
- **`TestOnly`** — glows. Test, so solids occlude them, but don't write, so a bolt
  never blocks a ship drawn afterwards.
- **`Off`** — the HUD. Ignore depth entirely, always draw on top.
- **`Opaque`** — replace the destination.
- **`Additive`** — `src + dst`. Nothing ever gets darker and two overlapping bright
  things get brighter than either. That is what light does, which is why it is how
  you draw glows, sparks, stars and neon on a dark background with no texture and no
  bloom pass.
- **`Alpha`** — standard transparency, for the HUD's translucent panels.

## Loading SPIR-V

**`Renderer.cpp`** — after the `<cstring>` include:

```diff
 #include "render/Renderer.hpp"
 
 #include <cstring>
+#include <fstream>
+#include <stdexcept>

+namespace {
+
+std::vector<char> readFile(const std::string& path) {
+    std::ifstream file(path, std::ios::ate | std::ios::binary);
+    if (!file) throw std::runtime_error("cannot open " + path +
+                                        " (are you running from the build directory?)");
+    size_t size = size_t(file.tellg());
+    std::vector<char> buffer(size);
+    file.seekg(0);
+    file.read(buffer.data(), std::streamsize(size));
+    return buffer;

```

`std::ios::ate` opens positioned at the *end*, so `tellg()` is the file size in one
call. `std::ios::binary` matters on Windows, where without it the runtime helpfully
translates byte pairs that happen to look like line endings and corrupts your
bytecode.

The error message names the working directory on purpose. "Cannot open
shaders/lit.vert.spv" from someone who ran `./build/SpaceFighter` instead of
`cd build && ./SpaceFighter` is the single most likely failure in this chapter.

## The pipeline factory

Five pipelines that differ in six ways is a function, not five copies.

**`Renderer.cpp`** — after `loadShader`:

```diff
     vkCheck(vkCreateShaderModule(ctx->device, &ci, nullptr, &module), "vkCreateShaderModule");
     return module;
 }
+
+VkPipeline Renderer::makePipeline(const char* vertPath, const char* fragPath,
+                                  VkPrimitiveTopology topology, DepthMode depthMode,
+                                  BlendMode blendMode, VertexLayout layout) {
+    VkShaderModule vert = loadShader(vertPath);
+    VkShaderModule frag = loadShader(fragPath);
+
+    VkPipelineShaderStageCreateInfo stages[2]{};
+    stages[0].sType = VK_STRUCTURE_TYPE_PIPELINE_SHADER_STAGE_CREATE_INFO;
+    stages[0].stage = VK_SHADER_STAGE_VERTEX_BIT;
+    stages[0].module = vert;
+    stages[0].pName = "main";
+    stages[1].sType = VK_STRUCTURE_TYPE_PIPELINE_SHADER_STAGE_CREATE_INFO;
+    stages[1].stage = VK_SHADER_STAGE_FRAGMENT_BIT;
+    stages[1].module = frag;
+    stages[1].pName = "main";
+}
```

`pName = "main"` is the entry point *within* the module. SPIR-V can hold several
entry points in one module, which is how engines ship shader permutations in a
single file; ours have one each.

### Vertex input: the layout contract

The GPU needs to know how to pull attributes out of a buffer: one **binding** (which
buffer, what stride) and some **attributes** (each field's location, format and
offset).

**`Renderer.cpp`**, in `makePipeline` — after the shader stages:

```diff
     stages[1].pName = "main";
+
+    VkVertexInputBindingDescription binding{};
+    VkVertexInputAttributeDescription attrs[2]{};
+    uint32_t attrCount = 2;
+    binding.binding = 0;
+    binding.inputRate = VK_VERTEX_INPUT_RATE_VERTEX;
+    if (layout == VertexLayout::Hud) {
+        binding.stride = sizeof(HUDVertex);
+        attrs[0] = {0, 0, VK_FORMAT_R32G32_SFLOAT, offsetof(HUDVertex, position)};
+        attrs[1] = {1, 0, VK_FORMAT_R32G32B32A32_SFLOAT, offsetof(HUDVertex, color)};
+    } else {
+        binding.stride = sizeof(Vertex);
+        attrs[0] = {0, 0, VK_FORMAT_R32G32B32_SFLOAT, offsetof(Vertex, position)};
+        attrs[1] = {1, 0, VK_FORMAT_R32G32B32_SFLOAT, offsetof(Vertex, normal)};
+    }
 }
```

Each attribute is `{location, binding, format, offset}`. The `location` is the
number in `layout(location = N) in` from chapter 07.A — the contract that nothing
checks. `offsetof` rather than a hand-counted byte offset is not fussiness: it is
what keeps this correct when someone reorders a member in `RenderTypes.hpp`.

`INPUT_RATE_VERTEX` means "advance once per vertex". The alternative,
`INPUT_RATE_INSTANCE`, is the other way to do instancing — and it is worth saying
why we don't. A `mat4` costs *four* attribute slots (Vulkan has no 4×4 attribute
format), the offsets get fiddly, and you are limited by
`maxVertexInputAttributes`. Reading a storage buffer with `gl_InstanceIndex`
instead keeps the vertex layout at two attributes, scales to any instance count,
and reads like plain array indexing in the shader.

**`Renderer.cpp`**, in `makePipeline` — after the layout branch:

```diff
         attrs[1] = {1, 0, VK_FORMAT_R32G32B32_SFLOAT, offsetof(Vertex, normal)};
     }
```

### Viewport, rasterization, multisampling

**`Renderer.cpp`**, in `makePipeline` — after the input assembly:

```diff
     ia.topology = topology;
+
+    VkPipelineViewportStateCreateInfo vp{};
+    vp.sType = VK_STRUCTURE_TYPE_PIPELINE_VIEWPORT_STATE_CREATE_INFO;
+    vp.viewportCount = 1;
+    vp.scissorCount = 1;   // contents are dynamic; only the counts are baked
+
+    VkPipelineRasterizationStateCreateInfo rs{};
+    rs.sType = VK_STRUCTURE_TYPE_PIPELINE_RASTERIZATION_STATE_CREATE_INFO;
+    rs.polygonMode = VK_POLYGON_MODE_FILL;
+    rs.cullMode = VK_CULL_MODE_NONE;   // our normals are self-correcting
+    rs.frontFace = VK_FRONT_FACE_COUNTER_CLOCKWISE;
+    rs.lineWidth = 1.0f;
+
+    VkPipelineMultisampleStateCreateInfo ms{};
+    ms.sType = VK_STRUCTURE_TYPE_PIPELINE_MULTISAMPLE_STATE_CREATE_INFO;
+    ms.rasterizationSamples = VK_SAMPLE_COUNT_1_BIT;
 }
```

The viewport state gives *counts* but no rectangles, because both are in the dynamic
list below. This is what makes a window resize free: chapter 05.A rebuilds the
swapchain and framebuffers, and not one of these five pipelines has to be
recompiled. Bake the viewport in instead and every resize is five pipeline builds.

`cullMode = NONE` is a decision chapter 08 earns: our mesh builder computes face
normals that always point outward, regardless of the order we listed the corners in,
so there is no reliable winding to cull by. Culling would be free performance if we
were careful about winding; we chose "never see a black face" instead, and this is
where that costs us.

`lineWidth = 1.0f` must be set even for triangle pipelines — it is read
unconditionally, and leaving it at zero is invalid usage.

### Depth and blend: the two that matter

The switch is incomplete, so this won't build yet. Fill in the glow:

**`Renderer.cpp`**, in `makePipeline` — after the `Opaque` case:

```diff
         case BlendMode::Opaque:
             cb.blendEnable = VK_FALSE;
             break;
+        case BlendMode::Additive:
+            cb.blendEnable = VK_TRUE;
+            cb.srcColorBlendFactor = VK_BLEND_FACTOR_SRC_ALPHA;
+            cb.dstColorBlendFactor = VK_BLEND_FACTOR_ONE;
+            cb.colorBlendOp = VK_BLEND_OP_ADD;
+            cb.srcAlphaBlendFactor = VK_BLEND_FACTOR_ONE;
+            cb.dstAlphaBlendFactor = VK_BLEND_FACTOR_ONE;
+            cb.alphaBlendOp = VK_BLEND_OP_ADD;
+            break;
     }
```

`dstColorBlendFactor = ONE` is what makes it additive: the destination is kept at
full strength and the source is added on top. Using `SRC_ALPHA` on the source side
rather than `ONE` lets a fragment fade its own contribution by writing a lower
alpha, which is how `star.frag`'s soft edge works without any transparency.

**`Renderer.cpp`**, in `makePipeline` — after the `Additive` case:

```diff

             break;

+            cb.blendEnable = VK_TRUE;
+            cb.srcColorBlendFactor = VK_BLEND_FACTOR_SRC_ALPHA;
+            cb.dstColorBlendFactor = VK_BLEND_FACTOR_ONE_MINUS_SRC_ALPHA;
```

`src·α + dst·(1−α)` — the classic "over" operator. The difference from additive is
one enum on one line, and it is the difference between a bolt that glows and a HUD

The modules are destroyed **immediately**. Creating the pipeline compiles their
bytecode into the driver's own form, and nothing refers back to the module
afterwards — keeping them alive is a common and harmless-looking leak.

That `VK_NULL_HANDLE` in the middle is the **pipeline cache** slot. Pass a real
`VkPipelineCache` and the driver can serialise compiled pipelines to disk and reload
them next launch, which is the difference between a half-second startup stall and
none once you have dozens of pipelines. Chapter 14.

pipeline cache mentioned above and **extended dynamic state**, which moves topology,

five explicit objects because they are readable.

```console
$ cmake --build build && cd build && ./SpaceFighter
[vulkan] using NVIDIA GeForce RTX 4070 (Vulkan 1.3)
[vulkan] Validation Performance Warning: [ WARNING-Shader-OutputNotConsumed ]
   vkCreateGraphicsPipelines(): pCreateInfos[0].pVertexInputState Vertex attribute
   at location 1 not consumed by vertex shader.
[vulkan] Validation Performance Warning: [ WARNING-Shader-OutputNotConsumed ]
   vkCreateGraphicsPipelines(): pCreateInfos[0].pVertexInputState Vertex attribute
   at location 1 not consumed by vertex shader.
[swapchain] 1280x720  format 50  3 images
```

The window is still blue and nothing is broken — these are *performance* warnings,
not errors. But there are exactly two of them, and there are exactly two pipelines
using `unlit.vert`: the grid and the bolts.

Chapter 07.A left `inNormal` out of `unlit.vert` because that shader has no use for
a normal. But `makePipeline` still declares two attributes for every mesh layout, so
those two pipelines promise the GPU a normal stream that nobody reads. The driver
sets up the fetch anyway, per vertex, forever.

This is what `VertexLayout::MeshPositionOnly` is for, and why the enum had three
values from the start:

**`Renderer.cpp`**, in `makePipeline` — in the vertex layout branch:

```diff
     } else {
         binding.stride = sizeof(Vertex);
         attrs[0] = {0, 0, VK_FORMAT_R32G32B32_SFLOAT, offsetof(Vertex, position)};
         attrs[1] = {1, 0, VK_FORMAT_R32G32B32_SFLOAT, offsetof(Vertex, normal)};
+        // unlit.vert reads only the position; declaring an attribute the shader
+        // never consumes is a validation performance warning.
+        if (layout == VertexLayout::MeshPositionOnly) attrCount = 1;
     }
```

The `stride` stays `sizeof(Vertex)` — the buffer really does contain 24-byte
vertices, we just skip fetching half of each. Only `attrCount` changes.

**`Renderer.cpp`**, in `createPipelines` — switch the two unlit pipelines:

```diff
     gridPipeline = makePipeline("shaders/unlit.vert.spv", "shaders/unlit.frag.spv",
                                 VK_PRIMITIVE_TOPOLOGY_LINE_LIST, DepthMode::TestWrite,
-                                BlendMode::Additive, VertexLayout::Mesh);
+                                BlendMode::Additive, VertexLayout::MeshPositionOnly);
     boltPipeline = makePipeline("shaders/unlit.vert.spv", "shaders/unlit.frag.spv",
                                 VK_PRIMITIVE_TOPOLOGY_TRIANGLE_LIST, DepthMode::TestOnly,
-                                BlendMode::Additive, VertexLayout::Mesh);
+                                BlendMode::Additive, VertexLayout::MeshPositionOnly);
```

Rebuild, and the warnings are gone.

That matters for more than tidiness. From here to the end of the guide, **a silent
run is the pass condition** for every checkpoint — and a channel that is always
printing two warnings you have learned to ignore is a channel that will not get your
attention on the day it prints a third.

Still the blue window — five compiled pipelines and nothing bound to draw with them

| Symptom | Likely cause |
|---|---|
| `cannot open shaders/lit.vert.spv (are you running from the build directory?)` | Exactly what it says. `cd build` first. |
| Two `OutputNotConsumed` warnings | The `MeshPositionOnly` fix above is missing from one or both unlit pipelines. |
| `vkCreateGraphicsPipelines … VUID-VkGraphicsPipelineCreateInfo-layout-07988` | The shader's `set`/`binding` numbers disagree with the descriptor set layout from chapter 06. |
| Validation complains about `lineWidth` | It is unset. It must be `1.0f` even on triangle pipelines. |
| `SPIR-V module not valid` | A stale `.spv`. Delete `build/shaders/` and rebuild. |
| Crash inside `vkCreateGraphicsPipelines` | A dangling pointer in the create-info: every `p…State` must point at a struct still alive at the call. |

**Try breaking it on purpose.** Delete the `cb.colorWriteMask = …` line and rebuild.
Everything still succeeds, validation stays silent, and the window is still blue —
so nothing tells you that all five pipelines now write **zero colour channels**.
Chapter 08 would come up completely black and you would spend an hour on the camera.
Put it back. Zero-initialised structs are a gift in Vulkan, right up to the handful
of fields where zero is a meaningful and useless value.

## Challenge

Add a wireframe mode: a sixth pipeline identical to `lit` but with
`polygonMode = VK_POLYGON_MODE_LINE`, toggled with a key.

Three things to get right. `POLYGON_MODE_LINE` requires the device feature
`fillModeNonSolid`, which chapter 02 did **not** enable — and an unenabled feature
is not an error at pipeline creation, it is undefined behaviour, so add it to
`pEnabledFeatures` and check `vkGetPhysicalDeviceFeatures` reports it first.
`makePipeline` has six parameters already and polygon mode would be a seventh;
consider whether the honest refactor is a small `PipelineDesc` struct rather than
another positional argument. And decide where the toggle lives: the renderer has no
input, so either it grows a setter or `FrameData` grows a field, and one of those
puts a rendering concern into the simulation's seam.
