## The swapchain: the ring of images you present

A **swapchain** is a small set of images the window system owns, that you draw into
and hand back to be shown. You create the whole ring up front and, each frame,
*acquire* the index of the next free one.

Everything in this chapter depends on the window's size, so it all lives together
in one class that can be torn down and rebuilt as a unit when the window resizes.

**`src/render/Swapchain.hpp`** — new file:

```cpp
#pragma once

#include "render/VulkanContext.hpp"

#include <vector>

constexpr VkFormat kDepthFormat = VK_FORMAT_D32_SFLOAT;
```

`D32_SFLOAT` is a 32-bit float depth buffer. Vulkan guarantees that *at least one*
of `D32_SFLOAT` and `X8_D24_UNORM_PACK32` is available as a depth attachment, and
in practice `D32_SFLOAT` is supported essentially everywhere. A shipping engine
queries `vkGetPhysicalDeviceFormatProperties` and picks; we hardcode it and say so.

**`Swapchain.hpp`** — after `kDepthFormat`:


Read the shape of the problem off those members. There are **N colour images** —
one per slot in the ring — but only **one depth image**, because only one frame is
being rasterised at a time and its depth values are dead the moment the frame ends.
Getting that backwards (a depth buffer per swapchain image) wastes memory; the
reverse mistake, sharing a colour image, would tear.

## Three choices the surface constrains

Creating the swapchain means making three decisions, each from a list the surface
gives you.

**`src/render/Swapchain.cpp`** — new file:

```cpp
#include "render/Swapchain.hpp"

#include <algorithm>
#include <array>
#include <cstdint>
#include <limits>

namespace {

VkSurfaceFormatKHR chooseFormat(const std::vector<VkSurfaceFormatKHR>& available) {
    for (const VkSurfaceFormatKHR& f : available)
        if (f.format == VK_FORMAT_B8G8R8A8_SRGB &&
            f.colorSpace == VK_COLOR_SPACE_SRGB_NONLINEAR_KHR)
            return f;
    return available[0];
}

} // namespace
```

**Format** is the pixel layout plus the colour space. `B8G8R8A8_SRGB` means the
hardware does the sRGB conversion for us on write — colours you compute in linear
space land correctly on a display that expects sRGB. The fallback to
`available[0]` is not laziness: the surface is required to advertise at least one
format, and any format beats refusing to run.

**`Swapchain.cpp`**, in the anonymous namespace — after `chooseFormat`:

```diff
     return available[0];
 }
+
+VkPresentModeKHR choosePresentMode(const std::vector<VkPresentModeKHR>&) {
+    return VK_PRESENT_MODE_FIFO_KHR;   // always supported; this is vsync
+}
 
 } // namespace
```

**Present mode** is the vsync policy, and Vulkan makes you name it:

- **`FIFO`** — a true queue, capped at the refresh rate. No tearing, and the only
  mode the spec *guarantees* exists. Our default.
- **`MAILBOX`** — like FIFO, but a newer frame replaces a waiting one, so latency
  drops without tearing. Great when the GPU outruns the display; not always
  supported.
- **`IMMEDIATE`** — no synchronization, may tear. Lowest latency.

The parameter is unnamed because we ignore the list. Upgrading to "prefer MAILBOX,
fall back to FIFO" is three lines, and chapter 09 explains why we don't: FIFO is
what paces our whole game loop.

**`Swapchain.cpp`**, in the anonymous namespace — after `choosePresentMode`:

```diff
     return VK_PRESENT_MODE_FIFO_KHR;   // always supported; this is vsync
 }
+
+VkExtent2D chooseExtent(const VkSurfaceCapabilitiesKHR& caps, GLFWwindow* window) {
+    if (caps.currentExtent.width != std::numeric_limits<uint32_t>::max())
+        return caps.currentExtent;
+
+    int w = 0, h = 0;
+    glfwGetFramebufferSize(window, &w, &h);
+    VkExtent2D actual{uint32_t(w), uint32_t(h)};
+    actual.width = std::clamp(actual.width, caps.minImageExtent.width, caps.maxImageExtent.width);
+    actual.height = std::clamp(actual.height, caps.minImageExtent.height, caps.maxImageExtent.height);
+    return actual;
+}
 
 } // namespace
```

**Extent** is the pixel size, and it has a genuinely odd protocol. Most window
systems tell you the size outright in `caps.currentExtent`. Some — notably some
Wayland compositors — instead set every field to `UINT32_MAX`, meaning "you decide,
within my limits." That sentinel is what the first `if` tests.

The call in the second branch is **`glfwGetFramebufferSize`, not
`glfwGetWindowSize`.** On a HiDPI display those differ by the scale factor, and
using window size gives you a swapchain at half resolution that the compositor then
stretches. Everything renders, nothing errors, and the whole game looks soft. Use
the framebuffer size everywhere sizes are in pixels — which, in Vulkan, is
everywhere.

The count-then-fill idiom from chapter 02, three times over. This is the "query,
don't assume" habit in its purest form.

Now the image count, which is the one number in this chapter worth arguing about:

**`Swapchain.cpp`**, in `createSwapchain` — after the present-mode query:

```diff
     vkGetPhysicalDeviceSurfacePresentModesKHR(ctx.physical, ctx.surface, &modeCount, modes.data());
+
+    VkSurfaceFormatKHR format = chooseFormat(formats);
+    colorFormat = format.format;
+    extent = chooseExtent(caps, window);
+
+    uint32_t imageCount = caps.minImageCount;
 }
```

`caps.minImageCount` is the smallest ring the surface will accept — typically 2.
That sounds right: one image being shown, one being drawn. Keep it for a moment.

Here is the problem. With exactly the minimum, *every* image is either on screen or
queued for presentation at the moment you ask for the next one, so
`vkAcquireNextImageKHR` has nothing free to hand you and blocks the CPU until the
display finishes with one. Your CPU stops — not because it has run out of work, but
because it has run out of *paper to write on*. One spare image decouples the two:

**`Swapchain.cpp`**, in `createSwapchain` — replace the image-count line:

```diff
     extent = chooseExtent(caps, window);
 
-    uint32_t imageCount = caps.minImageCount;
+    // One more than the minimum so we are never blocked waiting on the
+    // presenter for a free image.
+    uint32_t imageCount = caps.minImageCount + 1;
+    if (caps.maxImageCount > 0) imageCount = std::min(imageCount, caps.maxImageCount);
 }
```

`maxImageCount == 0` is Vulkan's way of saying "no limit", so the clamp has to be
guarded — clamping to zero would ask for a swapchain with no images at all. This
chapter's checkpoint prints the count, so you can see the effect of the `+ 1`
directly.

**`Swapchain.cpp`**, in `createSwapchain` — after the image count:

```diff
     if (caps.maxImageCount > 0) imageCount = std::min(imageCount, caps.maxImageCount);
+
+    VkSwapchainCreateInfoKHR ci{};
+    ci.sType = VK_STRUCTURE_TYPE_SWAPCHAIN_CREATE_INFO_KHR;
+    ci.surface = ctx.surface;
+    ci.minImageCount = imageCount;
+    ci.imageFormat = format.format;
+    ci.imageColorSpace = format.colorSpace;
+    ci.imageExtent = extent;
+    ci.imageArrayLayers = 1;
+    ci.imageUsage = VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT;
+    ci.preTransform = caps.currentTransform;
+    ci.compositeAlpha = VK_COMPOSITE_ALPHA_OPAQUE_BIT_KHR;
+    ci.presentMode = choosePresentMode(modes);
+    ci.clipped = VK_TRUE;
 }
```

Three of those deserve a word. `imageUsage = COLOR_ATTACHMENT_BIT` says we render
*into* these images; if you wanted to blit or copy into them instead you'd say so
here. `preTransform = caps.currentTransform` passes through whatever rotation the
surface already applies — it matters on phones and is a no-op on desktop.
`clipped = VK_TRUE` lets the driver skip fragments hidden by another window, which
is free performance as long as you never read the presented image back.

**`Swapchain.cpp`**, in `createSwapchain` — after `ci.clipped`:

```diff
     ci.clipped = VK_TRUE;
+
+    uint32_t indices[] = {*ctx.families.graphics, *ctx.families.present};
+    if (indices[0] != indices[1]) {
+        ci.imageSharingMode = VK_SHARING_MODE_CONCURRENT;
+        ci.queueFamilyIndexCount = 2;
+        ci.pQueueFamilyIndices = indices;
+    } else {
+        ci.imageSharingMode = VK_SHARING_MODE_EXCLUSIVE;
+    }
 }
```

This is where chapter 02's insistence on tracking *two* family indices pays off. If
graphics and present are different families, the images are touched by both, and
`EXCLUSIVE` would require explicit ownership transfers we have not written.
`CONCURRENT` gives up a little performance to make that correctness someone else's
problem. On the common single-family path we take `EXCLUSIVE` and lose nothing.

**`Swapchain.cpp`**, in `createSwapchain` — after the sharing-mode branch:

```diff

         ci.imageSharingMode = VK_SHARING_MODE_EXCLUSIVE;
     }
+

+
```

Note that `imageCount` is re-read from the driver. You asked for a number;
`minImageCount` is a *minimum*, and the driver may give you more. Trusting your own
request here — rather than the answer — is a classic source of an out-of-bounds
framebuffer index three chapters later.

## Image views: how a pass addresses an image

A `VkImage` is opaque memory. A **`VkImageView`** says how to interpret it: which
format, which mip levels, colour or depth. A framebuffer attaches views, never
images.

**`Swapchain.cpp`** — after `createSwapchain`:

```diff
     vkGetSwapchainImagesKHR(ctx.device, handle, &imageCount, images.data());
 }
+
+void Swapchain::createImageViews(VulkanContext& ctx) {
+    views.resize(images.size());
+    for (size_t i = 0; i < images.size(); i++) {
+        VkImageViewCreateInfo v{};
+        v.sType = VK_STRUCTURE_TYPE_IMAGE_VIEW_CREATE_INFO;
+        v.image = images[i];
+        v.viewType = VK_IMAGE_VIEW_TYPE_2D;
+        v.format = colorFormat;
+        v.subresourceRange = {VK_IMAGE_ASPECT_COLOR_BIT, 0, 1, 0, 1};
+        vkCheck(vkCreateImageView(ctx.device, &v, nullptr, &views[i]), "vkCreateImageView");
+    }
+}
```

That `subresourceRange` brace-initialiser is `{aspect, baseMipLevel, levelCount,
baseArrayLayer, layerCount}` — one aspect, one mip, one layer. Swapchain images
never have mips.

## The depth buffer — now our job

Chapter 02's `VmaAllocator` gets its first use. A depth image is device-local
memory the CPU never touches, which is the easiest allocation VMA will ever be
asked for.

**`Swapchain.cpp`** — after `createImageViews`:

```diff
         vkCheck(vkCreateImageView(ctx.device, &v, nullptr, &views[i]), "vkCreateImageView");
     }
 }
+
+void Swapchain::createDepthResources(VulkanContext& ctx) {
+    VkImageCreateInfo ii{};
+    ii.sType = VK_STRUCTURE_TYPE_IMAGE_CREATE_INFO;
+    ii.imageType = VK_IMAGE_TYPE_2D;
+    ii.format = kDepthFormat;
+    ii.extent = {extent.width, extent.height, 1};
+    ii.mipLevels = 1;
+    ii.arrayLayers = 1;
+    ii.samples = VK_SAMPLE_COUNT_1_BIT;
+    ii.tiling = VK_IMAGE_TILING_OPTIMAL;
+    ii.usage = VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT;
+    ii.initialLayout = VK_IMAGE_LAYOUT_UNDEFINED;
+}
```

`TILING_OPTIMAL` lets the driver store the image in whatever swizzled layout its
hardware likes; the alternative, `LINEAR`, is row-major and only useful when the
CPU needs to read it. `initialLayout = UNDEFINED` says "I don't care what's in it"
— which is true, because the render pass clears it every frame.

**`Swapchain.cpp`**, in `createDepthResources` — after the image create-info:

```diff
     ii.initialLayout = VK_IMAGE_LAYOUT_UNDEFINED;
+
+    VmaAllocationCreateInfo ai{};
+    ai.usage = VMA_MEMORY_USAGE_AUTO;
+    ai.flags = VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT;
+    vkCheck(vmaCreateImage(ctx.allocator, &ii, &ai, &depthImage, &depthAlloc, nullptr),
+            "vmaCreateImage");
+
+    VkImageViewCreateInfo v{};
+    v.sType = VK_STRUCTURE_TYPE_IMAGE_VIEW_CREATE_INFO;
+    v.image = depthImage;
+    v.viewType = VK_IMAGE_VIEW_TYPE_2D;
+    v.format = kDepthFormat;
+    v.subresourceRange = {VK_IMAGE_ASPECT_DEPTH_BIT, 0, 1, 0, 1};
+    vkCheck(vkCreateImageView(ctx.device, &v, nullptr, &depthView), "vkCreateImageView(depth)");
 }
```

`vmaCreateImage` creates the image, allocates memory for it, and binds the two —
the three-call raw dance in one line. `MEMORY_USAGE_AUTO` lets VMA infer
device-local from the usage flags. `DEDICATED_MEMORY_BIT` asks for its own
allocation rather than a slice of a shared block, which is the right call for a
full-screen render target: it's large, long-lived, and some drivers are faster with
attachments in dedicated memory.

The aspect is `DEPTH_BIT` here, where the colour views used `COLOR_BIT`. That one
enum is the difference between a view the depth attachment accepts and a validation
error.

## The render pass: declaring the shape of a render

A **render pass** is Vulkan's up-front description of a rendering operation: which
attachments it uses, what to do with them at the start and end, and the layouts
they pass through. You create it **once** and reuse it every frame.

**`Swapchain.cpp`** — after `createDepthResources`:

```diff
     vkCheck(vkCreateImageView(ctx.device, &v, nullptr, &depthView), "vkCreateImageView(depth)");
 }
+
+void Swapchain::createRenderPass(VulkanContext& ctx) {
+    VkAttachmentDescription color{};
+    color.format = colorFormat;
+    color.samples = VK_SAMPLE_COUNT_1_BIT;
+    color.loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR;
+    color.storeOp = VK_ATTACHMENT_STORE_OP_STORE;
+    color.stencilLoadOp = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
+    color.stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
+    color.initialLayout = VK_IMAGE_LAYOUT_UNDEFINED;
+    color.finalLayout = VK_IMAGE_LAYOUT_PRESENT_SRC_KHR;
+}
```

The `loadOp`/`storeOp` pair is a real performance decision dressed as boilerplate.
`CLEAR` then `STORE` means "wipe it, then keep what I draw" — right for the colour
image we're about to show. The alternative `LOAD` would preserve the previous
frame's contents, which costs bandwidth reading them back in.

`finalLayout = PRESENT_SRC_KHR` is Vulkan being explicit about something other APIs
hide: images have a *layout*, and the presentation engine requires a specific one.
Declaring it here means the render pass performs the transition for you at the end,
with no barrier to write yourself.

**`Swapchain.cpp`**, in `createRenderPass` — after the colour attachment:

```diff
     color.finalLayout = VK_IMAGE_LAYOUT_PRESENT_SRC_KHR;
+
+    VkAttachmentDescription depth{};
+    depth.format = kDepthFormat;
+    depth.samples = VK_SAMPLE_COUNT_1_BIT;
+    depth.loadOp = VK_ATTACHMENT_LOAD_OP_CLEAR;
+    depth.storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
+    depth.stencilLoadOp = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
+    depth.stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
+    depth.initialLayout = VK_IMAGE_LAYOUT_UNDEFINED;
+    depth.finalLayout = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL;
 }
```

Depth differs in exactly one meaningful way: `storeOp = DONT_CARE`. We clear it
each frame and never read it afterwards, so writing it back to memory at the end of
the pass would be pure waste. On a tiled mobile GPU that single enum is the
difference between a depth buffer that lives entirely in fast on-chip memory and
one that gets flushed to main memory every frame.

**`Swapchain.cpp`**, in `createRenderPass` — after the depth attachment:

```diff
     depth.finalLayout = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL;
+
+    VkAttachmentReference colorRef{0, VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL};
+    VkAttachmentReference depthRef{1, VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL};
+
+    VkSubpassDescription subpass{};
+    subpass.pipelineBindPoint = VK_PIPELINE_BIND_POINT_GRAPHICS;
+    subpass.colorAttachmentCount = 1;
+    subpass.pColorAttachments = &colorRef;
+    subpass.pDepthStencilAttachment = &depthRef;
 }
```

Those `0` and `1` are indices into the attachment array we're about to build, and
they are also the `location = 0` a fragment shader writes to. Three separate places
have to agree on that numbering — the attachment array, the reference, and the
shader — which is the sort of thing Vulkan asks of you constantly.

A **subpass** is one rendering step within a pass. Multi-subpass render passes let
a tiled GPU keep intermediate results on-chip between steps; we have one subpass
and never need more.

Now the piece that is pure synchronization:

**`Swapchain.cpp`**, in `createRenderPass` — after the subpass:

```diff
     subpass.pDepthStencilAttachment = &depthRef;
+
+    // Hold the pass at the point of first write until the image is acquired.
+    VkSubpassDependency dep{};
+    dep.srcSubpass = VK_SUBPASS_EXTERNAL;
+    dep.dstSubpass = 0;
+    dep.srcStageMask = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT
+                     | VK_PIPELINE_STAGE_EARLY_FRAGMENT_TESTS_BIT;
+    dep.srcAccessMask = 0;
+    dep.dstStageMask = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT
+                     | VK_PIPELINE_STAGE_EARLY_FRAGMENT_TESTS_BIT;
+    dep.dstAccessMask = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT
+                      | VK_ACCESS_DEPTH_STENCIL_ATTACHMENT_WRITE_BIT;
 }
```

`VK_SUBPASS_EXTERNAL` as the source means "everything before this pass". The
dependency says: the layout transition this pass performs on entry must not happen
until the colour-output and early-depth stages are reachable — which is exactly
when chapter 05.B's `imageAvailable` semaphore will be signalled. Without it, the
transition can begin before the image is actually free, and validation's
synchronization checks will say so.

The depth stage is in there because we clear depth too, and a clear is a write.
Leave `EARLY_FRAGMENT_TESTS` out and you have a correctly-synchronised colour
attachment next to an unsynchronised depth one.

**`Swapchain.cpp`**, in `createRenderPass` — after the dependency:

```diff
     dep.dstAccessMask = VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT
                       | VK_ACCESS_DEPTH_STENCIL_ATTACHMENT_WRITE_BIT;
+
+    std::array<VkAttachmentDescription, 2> attachments{color, depth};
+    VkRenderPassCreateInfo rp{};
+    rp.sType = VK_STRUCTURE_TYPE_RENDER_PASS_CREATE_INFO;
+    rp.attachmentCount = uint32_t(attachments.size());
+    rp.pAttachments = attachments.data();
+    rp.subpassCount = 1;
+    rp.pSubpasses = &subpass;
+    rp.dependencyCount = 1;
+    rp.pDependencies = &dep;
+
+    vkCheck(vkCreateRenderPass(ctx.device, &rp, nullptr, &renderPass), "vkCreateRenderPass");
 }
```

`{color, depth}` in that order is what makes `colorRef`'s index 0 and `depthRef`'s
index 1 correct. Swap the two and everything still compiles.

> **A note on dynamic rendering.** Since Vulkan 1.3 you can **skip render-pass and
> framebuffer objects entirely** and declare attachments inline at draw time with
> `vkCmdBeginRendering`. It's less boilerplate and the modern default for new
> engines. We use the classic path because it makes the attachment and layout model
> *explicit*, which is what you're here to learn, and because it's what most
> existing samples show. Chapter 14 points at it as the first refactor to try.

## Framebuffers: binding views to a pass

A **framebuffer** is the concrete set of views a render pass draws into — one per
swapchain image, each pairing that image's colour view with the shared depth view.

**`Swapchain.cpp`** — after `createRenderPass`:

```diff
     vkCheck(vkCreateRenderPass(ctx.device, &rp, nullptr, &renderPass), "vkCreateRenderPass");
 }
+
+void Swapchain::createFramebuffers(VulkanContext& ctx) {
+    framebuffers.resize(views.size());
+    for (size_t i = 0; i < views.size(); i++) {
+        VkImageView attachments[] = {views[i], depthView};
+
+        VkFramebufferCreateInfo fb{};
+        fb.sType = VK_STRUCTURE_TYPE_FRAMEBUFFER_CREATE_INFO;
+        fb.renderPass = renderPass;
+        fb.attachmentCount = 2;
+        fb.pAttachments = attachments;
+        fb.width = extent.width;
+        fb.height = extent.height;
+        fb.layers = 1;
+        vkCheck(vkCreateFramebuffer(ctx.device, &fb, nullptr, &framebuffers[i]),
+                "vkCreateFramebuffer");
+    }
+}
```

`depthView` appearing in every framebuffer is the one-depth-buffer decision made
concrete. The order of `attachments` must match the render pass's attachment array
— colour first, depth second — for the third time in this chapter.

So the addressing chain is **swapchain image → image view → framebuffer → render
pass**. Acquire an index each frame, and `framebuffers[index]` is where you draw.

A resize invalidates everything sized: the images, their views, the depth buffer

```diff
 }
+
+void Swapchain::destroySizeDependent(VulkanContext& ctx) {
+    for (VkFramebuffer f : framebuffers) vkDestroyFramebuffer(ctx.device, f, nullptr);
+    framebuffers.clear();
+
+    if (depthView) vkDestroyImageView(ctx.device, depthView, nullptr);
+    if (depthImage) vmaDestroyImage(ctx.allocator, depthImage, depthAlloc);
+    depthView = VK_NULL_HANDLE;
+    depthImage = VK_NULL_HANDLE;
+    depthAlloc = VK_NULL_HANDLE;
+
+    for (VkImageView v : views) vkDestroyImageView(ctx.device, v, nullptr);
+    views.clear();
+
+    if (handle) vkDestroySwapchainKHR(ctx.device, handle, nullptr);
+    handle = VK_NULL_HANDLE;
+}
```

Nulling the handles after destroying is not decoration. `destroySizeDependent` runs
on every resize *and* at shutdown, so a handle left dangling here is a
double-destroy the next time through. Note there is no loop destroying `images` —
the swapchain owns those, and destroying it releases them.

**`Swapchain.cpp`** — after `destroySizeDependent`:

```diff
     if (handle) vkDestroySwapchainKHR(ctx.device, handle, nullptr);
     handle = VK_NULL_HANDLE;
 }
+
+void Swapchain::recreate(VulkanContext& ctx, GLFWwindow* window) {
+    // A minimised window has a zero-sized framebuffer, which no swapchain can
+    // match. Idle here until it comes back.
+    int w = 0, h = 0;
+    glfwGetFramebufferSize(window, &w, &h);
+    while (w == 0 || h == 0) {
+        glfwGetFramebufferSize(window, &w, &h);
+        glfwWaitEvents();
+    }
+
+    vkDeviceWaitIdle(ctx.device);
+    destroySizeDependent(ctx);
+
+    createSwapchain(ctx, window);
+    createImageViews(ctx);
+    createDepthResources(ctx);
+    createFramebuffers(ctx);   // the render pass does not depend on the extent
+}
```

Two things here are easy to get wrong. The minimise loop uses **`glfwWaitEvents`**,
not `glfwPollEvents` — polling in a tight loop would spin a core at 100% for as long
as the window stays minimised. And `vkDeviceWaitIdle` before destroying is blunt but
correct: it blocks until the GPU has finished everything, so nothing we free is
still in use. A shipping engine recreates more surgically to avoid the stall; at our
scale a hitch on resize is invisible.

## Checkpoint

```console
$ cmake -S . -B build && cmake --build build
$ cd build && ./SpaceFighter
[vulkan] using NVIDIA GeForce RTX 4070 (Vulkan 1.3)
[swapchain] 1280x720  format 50  3 images
```

The window still shows garbage — we have created somewhere to draw and not drawn.
What matters is the second line and, again, the **absence of validation output** on
the way in or out. Format 50 is `VK_FORMAT_B8G8R8A8_SRGB`. The image count is your
surface's `minImageCount` plus our one spare — 3 and 4 are both common, and which
you get says nothing about whether you did this right.

| Symptom | Likely cause |
|---|---|
| `1 images` | `maxImageCount` clamped you to one. Legal but unusual — you will get no CPU/GPU overlap from the swapchain. |
| `format 0` (`UNDEFINED`) | `colorFormat` assigned before `chooseFormat` ran, or from the wrong variable. |
| Validation: `VkImageView … has not been destroyed` at exit | `swapchain.destroy(ctx)` is missing, or runs after `ctx.destroy()`. |
| `vkCreateFramebuffer failed with VkResult -13` | Attachment count or order disagrees with the render pass. `-13` is `ERROR_UNKNOWN`; the validation message above it will be specific. |
| `vmaCreateImage` fails | The depth format isn't supported for optimal-tiling depth attachments. Try `VK_FORMAT_D24_UNORM_S8_UINT`. |
| Extent is `4294967295x4294967295` | The `currentExtent` sentinel branch isn't being taken — check the comparison is against `UINT32_MAX`. |

**Try breaking it on purpose.** Swap the two entries in
`std::array<VkAttachmentDescription, 2> attachments{color, depth};` to
`{depth, color}` and re-run. It compiles, and validation immediately tells you the
framebuffer's attachment 0 has a format the render pass doesn't expect. Now change
`colorRef`/`depthRef` to `{1, …}`/`{0, …}` as well, so the indices agree again — and
the error goes away, because you have consistently renamed the attachments rather
than broken anything. That's worth sitting with: the numbering is arbitrary, but all
three places must agree. Put both back.

## Challenge

Add `MAILBOX` support: prefer it when the surface offers it, fall back to `FIFO`.

Three things to get right. `choosePresentMode` currently ignores its parameter —
you'll need the list it's already being handed. `MAILBOX` typically requires **at
least three images** to do anything useful, so the `+ 1` above may not be enough and
you should reconsider the image count alongside the mode rather than after it. And
decide how you'll know it worked: with vsync gone the frame rate is no longer pinned
to your refresh rate, so print the count and mode at startup — otherwise the only
symptom of "MAILBOX silently unsupported" is that nothing changes.
