Chapter 05.A built somewhere to draw. This chapter builds the *frame*: the fixed
sequence of acquire, record, submit, present, and the synchronization that keeps a
CPU and a GPU running in parallel without racing.

`Renderer` is the largest type in the project and it grows through chapter 08. It

## Commands are recorded, not executed

Nothing in Vulkan happens when you call it. `vkCmdBindPipeline`, `vkCmdDraw` and
friends **record** into a command buffer, and the buffer runs later, on the GPU,
when you submit it. That indirection is why the CPU can build frame *N+1* while the
GPU chews on frame *N* — and it is also why we need synchronization at all.

**`src/render/Renderer.hpp`** — new file:

```cpp
#pragma once

#include "render/Swapchain.hpp"
#include "render/VulkanContext.hpp"

#include <array>

constexpr int MAX_FRAMES_IN_FLIGHT = 2;
```

**`Renderer.hpp`** — after `MAX_FRAMES_IN_FLIGHT`:

```diff
 constexpr int MAX_FRAMES_IN_FLIGHT = 2;
+
+struct FrameSync {
+    VkSemaphore imageAvailable = VK_NULL_HANDLE;
+    VkSemaphore renderFinished = VK_NULL_HANDLE;
+    VkFence inFlight = VK_NULL_HANDLE;
+};
```

Those three objects are the whole subject of this chapter, so meet them now:

- **Semaphore** — orders work *between GPU queue operations*. "Don't start
  rendering until the image is acquired"; "don't present until rendering is done."
  Purely GPU-side; the CPU never waits on one and never learns its state.
- **Fence** — orders work *between the GPU and the CPU*. "CPU, block here until the
  GPU signals this." It is how the CPU knows a frame's resources are free to reuse.

Two semaphores and one fence, per frame in flight.

**`Renderer.hpp`** — after `FrameSync`:

```diff
     VkFence inFlight = VK_NULL_HANDLE;
 };

+    void init(VulkanContext& context, GLFWwindow* win, Swapchain& sc);
+    void destroy();
+    void drawFrame();
+    void onFramebufferResized() { framebufferResized = true; }
+};
```

**`Renderer.hpp`**, in `class Renderer` — after `onFramebufferResized`:

```diff
     void onFramebufferResized() { framebufferResized = true; }
```

`MAX_FRAMES_IN_FLIGHT`-sized array in this class, and it will pick up more arrays
in chapter 06.

## The pool and the buffers

A **command pool** allocates command buffers from one queue family. We take one
buffer per frame-in-flight, so that re-recording this frame's commands never
touches the buffer the GPU is still reading.

**`src/render/Renderer.cpp`** — new file:

```cpp
#include "render/Renderer.hpp"

void Renderer::init(VulkanContext& context, GLFWwindow* win, Swapchain& sc) {
    ctx = &context;
    window = win;
    swapchain = &sc;

    createCommandResources();
    createSyncObjects();
}
```

**`Renderer.cpp`** — after `Renderer::init`:

```diff
     createSyncObjects();
 }
+
+void Renderer::createCommandResources() {
+    VkCommandPoolCreateInfo pci{};
+    pci.sType = VK_STRUCTURE_TYPE_COMMAND_POOL_CREATE_INFO;
+    pci.flags = VK_COMMAND_POOL_CREATE_RESET_COMMAND_BUFFER_BIT;
+    pci.queueFamilyIndex = *ctx->families.graphics;
+    vkCheck(vkCreateCommandPool(ctx->device, &pci, nullptr, &commandPool), "vkCreateCommandPool");
+
+    VkCommandBufferAllocateInfo ai{};
+    ai.sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_ALLOCATE_INFO;
+    ai.commandPool = commandPool;
+    ai.level = VK_COMMAND_BUFFER_LEVEL_PRIMARY;
+    ai.commandBufferCount = MAX_FRAMES_IN_FLIGHT;
+    vkCheck(vkAllocateCommandBuffers(ctx->device, &ai, commandBuffers.data()),
+            "vkAllocateCommandBuffers");
+}
```

`RESET_COMMAND_BUFFER_BIT` lets us reset one buffer at a time with
`vkResetCommandBuffer`, which is what a re-recorded-every-frame buffer needs.
Without it you can only reset the entire pool at once. `LEVEL_PRIMARY` means a
buffer that can be submitted directly; secondary buffers exist for recording
subpass work in parallel across threads, which we don't do.

## Sync objects, and a deadlock worth having

Create the three objects per frame slot, the obvious way:

**`Renderer.cpp`** — after `createCommandResources`:

```diff
     vkCheck(vkAllocateCommandBuffers(ctx->device, &ai, commandBuffers.data()),
             "vkAllocateCommandBuffers");
 }
+
+void Renderer::createSyncObjects() {
+    VkSemaphoreCreateInfo sci{};
+    sci.sType = VK_STRUCTURE_TYPE_SEMAPHORE_CREATE_INFO;
+
+    VkFenceCreateInfo fci{};
+    fci.sType = VK_STRUCTURE_TYPE_FENCE_CREATE_INFO;
+
+    for (FrameSync& s : sync) {
+        vkCheck(vkCreateSemaphore(ctx->device, &sci, nullptr, &s.imageAvailable),
+                "vkCreateSemaphore");
+        vkCheck(vkCreateSemaphore(ctx->device, &sci, nullptr, &s.renderFinished),
+                "vkCreateSemaphore");
+        vkCheck(vkCreateFence(ctx->device, &fci, nullptr, &s.inFlight), "vkCreateFence");
+    }
+}
```

Keep that as it is for now. We'll come back to it in about thirty lines, when it
hangs.

## Recording a frame

Begin the buffer, begin the render pass with its clear values, end both. There are
no draws yet — that's chapters 07.B and 08 — but the clear alone is enough to prove
the whole machine works.

**`Renderer.cpp`** — after `createSyncObjects`:

```diff
         vkCheck(vkCreateFence(ctx->device, &fci, nullptr, &s.inFlight), "vkCreateFence");
     }
 }
+
+void Renderer::recordFrame(VkCommandBuffer cmd, uint32_t imageIndex) {
+    VkCommandBufferBeginInfo bi{};
+    bi.sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_BEGIN_INFO;
+    vkCheck(vkBeginCommandBuffer(cmd, &bi), "vkBeginCommandBuffer");
+
+    VkClearValue clears[2]{};
+    clears[0].color = {{0.02f, 0.02f, 0.06f, 1.0f}};
+    clears[1].depthStencil = {1.0f, 0};
+}
```

Two clear values, in the same order as the render pass's attachments — colour is 0,
depth is 1, for the fourth time. Depth clears to **1.0**, the far plane, because
chapter 07.B's depth test keeps fragments that are `LESS` than what's stored; clear
it to 0.0 instead and every fragment fails and you get an empty screen.

**`Renderer.cpp`**, in `recordFrame` — after the clear values:

```diff
     clears[1].depthStencil = {1.0f, 0};
+
+    VkRenderPassBeginInfo rp{};
+    rp.sType = VK_STRUCTURE_TYPE_RENDER_PASS_BEGIN_INFO;
+    rp.renderPass = swapchain->renderPass;
+    rp.framebuffer = swapchain->framebuffers[imageIndex];
+    rp.renderArea.offset = {0, 0};
+    rp.renderArea.extent = swapchain->extent;
+    rp.clearValueCount = 2;
+    rp.pClearValues = clears;
+    vkCmdBeginRenderPass(cmd, &rp, VK_SUBPASS_CONTENTS_INLINE);
+
+    vkCmdEndRenderPass(cmd);
+    vkCheck(vkEndCommandBuffer(cmd), "vkEndCommandBuffer");
 }
```

`framebuffers[imageIndex]` is the whole reason we acquire an index rather than an
image. `SUBPASS_CONTENTS_INLINE` says the commands are in this buffer, not in
secondary ones. Everything the rest of the guide draws goes between those last two
lines.

## The frame, in order

Here is the sequence the entire chapter exists for.

**`Renderer.cpp`** — after `recordFrame`:

```diff
     vkCmdEndRenderPass(cmd);
     vkCheck(vkEndCommandBuffer(cmd), "vkEndCommandBuffer");
 }
+
+void Renderer::drawFrame() {
+    FrameSync& s = sync[currentFrame];
+
+    // 1. Wait until this slot's previous GPU work is done.
+    vkWaitForFences(ctx->device, 1, &s.inFlight, VK_TRUE, UINT64_MAX);
+    vkResetFences(ctx->device, 1, &s.inFlight);
+}
```

**`Renderer.cpp`**, in `drawFrame` — after the fence reset:

```diff
     vkResetFences(ctx->device, 1, &s.inFlight);
+
+    // 2. Acquire an image; imageAvailable is signalled when it is ready.
+    uint32_t imageIndex = 0;
+    VkResult acquired = vkAcquireNextImageKHR(ctx->device, swapchain->handle, UINT64_MAX,
+                                              s.imageAvailable, VK_NULL_HANDLE, &imageIndex);
+
+    // 3. Record this frame's commands.
+    vkResetCommandBuffer(commandBuffers[currentFrame], 0);
+    recordFrame(commandBuffers[currentFrame], imageIndex);
 }
```

**`Renderer.cpp`**, in `drawFrame` — after `recordFrame`:

```diff
     recordFrame(commandBuffers[currentFrame], imageIndex);
+
+    // 4. Submit, ordered by the two semaphores and closed out by the fence.
+    VkPipelineStageFlags waitStage = VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT;
+    VkSubmitInfo submit{};
+    submit.sType = VK_STRUCTURE_TYPE_SUBMIT_INFO;
+    submit.waitSemaphoreCount = 1;
+    submit.pWaitSemaphores = &s.imageAvailable;
+    submit.pWaitDstStageMask = &waitStage;
+    submit.commandBufferCount = 1;
+    submit.pCommandBuffers = &commandBuffers[currentFrame];
+    submit.signalSemaphoreCount = 1;
+    submit.pSignalSemaphores = &s.renderFinished;
+    vkCheck(vkQueueSubmit(ctx->graphicsQueue, 1, &submit, s.inFlight), "vkQueueSubmit");
 }
```

`waitStage = COLOR_ATTACHMENT_OUTPUT` is a precise touch worth pausing on. The
submission does not wait for `imageAvailable` before *starting*; it waits only at
the moment it needs to **write colour**. Vertex work, and later all our matrix
multiplication, can run while the presentation engine is still finishing with the
image. Vulkan lets you order at that granularity, and this one enum is where you
say so.

**`Renderer.cpp`**, in `drawFrame` — after the submit:

```diff
     vkCheck(vkQueueSubmit(ctx->graphicsQueue, 1, &submit, s.inFlight), "vkQueueSubmit");
+
+    // 5. Present once rendering has signalled renderFinished.
+    VkPresentInfoKHR present{};
+    present.sType = VK_STRUCTURE_TYPE_PRESENT_INFO_KHR;
+    present.waitSemaphoreCount = 1;
+    present.pWaitSemaphores = &s.renderFinished;
+    present.swapchainCount = 1;
+    present.pSwapchains = &swapchain->handle;
+    present.pImageIndices = &imageIndex;
+
+    vkQueuePresentKHR(ctx->presentQueue, &present);
+
+    // 6. Move to the next slot.
+    currentFrame = (currentFrame + 1) % MAX_FRAMES_IN_FLIGHT;
 }
```

Trace the chain once and it clicks: **acquire → (imageAvailable) → render →
(renderFinished) → present.** Two semaphores, entirely GPU-side; the CPU is never
told when either fires. The fence is the only thing the CPU waits on, and it exists
to answer one question — *is this slot's command buffer free to re-record?*

> **Where you'd tighten this.** We key `renderFinished` by frame-in-flight, which
> is the clearest arrangement and the one most tutorials use. Strictly, the fence
> only proves the *submit* finished — the presentation engine may still be waiting
> on that semaphore when this slot cycles round, so its reuse is not formally
> guaranteed, and the newest validation layers have begun flagging exactly this.
> The fully-correct form keys the render-finished semaphore **per swapchain
> image**. It changes nothing about the shape above; chapter 14 lists it with the
> other production upgrades.

Finally, teardown:

**`Renderer.cpp`** — after `drawFrame`:

```diff
     currentFrame = (currentFrame + 1) % MAX_FRAMES_IN_FLIGHT;
 }
+
+void Renderer::destroy() {
+    vkDeviceWaitIdle(ctx->device);
+
+    for (FrameSync& s : sync) {
+        if (s.imageAvailable) vkDestroySemaphore(ctx->device, s.imageAvailable, nullptr);
+        if (s.renderFinished) vkDestroySemaphore(ctx->device, s.renderFinished, nullptr);
+        if (s.inFlight) vkDestroyFence(ctx->device, s.inFlight, nullptr);
+    }
+
+    if (commandPool) vkDestroyCommandPool(ctx->device, commandPool, nullptr);
+}
```

`vkDeviceWaitIdle` first, always. Destroying a fence the GPU is about to signal is
undefined behaviour, and the last frame is almost certainly still in flight when
the user closes the window.

```console
$ cmake -S . -B build && cmake --build build
$ cd build && ./SpaceFighter
[vulkan] using NVIDIA GeForce RTX 4070 (Vulkan 1.3)
[swapchain] 1280x720  format 50  3 images
```

…and then nothing. The window never appears, or appears blank and unresponsive.
No error, no validation message, no crash. **The program is hung**, and you have to
`Ctrl-C` it.

It is hung on line one of `drawFrame`. `vkWaitForFences` with `UINT64_MAX` blocks
until the fence is signalled, and the only thing that signals `inFlight` is the
`vkQueueSubmit` four steps *below* it. On the very first frame nothing has been
submitted yet, so nothing will ever signal it, so the wait never returns, so we
never reach the submit. Classic circular wait: the first frame is waiting for
itself.

There is a flag for exactly this. Fences can be **born signalled**:

**`Renderer.cpp`**, in `createSyncObjects` — after `fci.sType`:

```diff
     VkFenceCreateInfo fci{};
     fci.sType = VK_STRUCTURE_TYPE_FENCE_CREATE_INFO;
+    fci.flags = VK_FENCE_CREATE_SIGNALED_BIT;   // so the first wait returns immediately
```

Now the first wait on each slot returns immediately, `vkResetFences` clears it, and
every subsequent wait is satisfied by that slot's previous submission. Rebuild and
run: **a window filled with deep space blue.**

That colour is `{0.02f, 0.02f, 0.06f, 1.0f}` from `recordFrame`, and it is the
first pixel in this project you chose. Everything from chapter 06 on is drawn on
top of it.

## The second bug: correct, and half speed

The frame renders. It also has a subtler problem, and this one produces no symptom
you can see — only one you can measure.

Look again at steps 1 and 4. We wait on `inFlight`, and later we submit signalling
`inFlight`. With `MAX_FRAMES_IN_FLIGHT` at 2 those are *different slots* on
alternate frames, so the CPU is never waiting on the work it just queued. Prove to
yourself that this matters by breaking it:

In `Renderer.hpp`, temporarily change `MAX_FRAMES_IN_FLIGHT` from `2` to `1` and
rebuild. It still renders correctly — the picture is identical. But now there is
one slot, so step 1 waits on the fence for the frame *you just submitted*, and the
CPU sits idle until the GPU has completely finished before it starts recording
again. The two processors take turns instead of overlapping, and your frame time
becomes CPU time **plus** GPU time instead of the larger of the two.

With vsync on you may not see it at all, which is the trap: at 60 Hz a frame that
should take 4 ms and now takes 8 ms still hits 60 fps, and the cost is invisible
until the day your scene gets heavy enough that it isn't. **Set it back to 2.**

Two is the standard sweet spot: enough to keep both processors busy, not so many
that input latency piles up behind queued frames. Three is common for
triple-buffered presentation; beyond that you are mostly adding lag.

## Handling resize

One thing is still missing, and the checkpoint will find it. Resize the window and
the swapchain no longer matches the surface; `vkAcquireNextImageKHR` and
`vkQueuePresentKHR` say so by returning `VK_ERROR_OUT_OF_DATE_KHR`. Right now we
ignore both return values.

**`Renderer.cpp`**, in `drawFrame` — replace the fence wait and reset:

```diff
     // 1. Wait until this slot's previous GPU work is done.
     vkWaitForFences(ctx->device, 1, &s.inFlight, VK_TRUE, UINT64_MAX);
-    vkResetFences(ctx->device, 1, &s.inFlight);
 
     // 2. Acquire an image; imageAvailable is signalled when it is ready.
     uint32_t imageIndex = 0;
     VkResult acquired = vkAcquireNextImageKHR(ctx->device, swapchain->handle, UINT64_MAX,
                                               s.imageAvailable, VK_NULL_HANDLE, &imageIndex);
+    if (acquired == VK_ERROR_OUT_OF_DATE_KHR) {
+        swapchain->recreate(*ctx, window);
+        return;
+    }
+    if (acquired != VK_SUCCESS && acquired != VK_SUBOPTIMAL_KHR)
+        vkCheck(acquired, "vkAcquireNextImageKHR");
+
+    // Reset only once we know we will submit, or the fence never gets signalled.
+    vkResetFences(ctx->device, 1, &s.inFlight);
```

That move is the point of the edit, not a tidy-up. If you reset the fence and
*then* bail out of the frame on `OUT_OF_DATE`, you have left an unsignalled fence
behind with no submission coming to signal it — and the next time this slot comes
round, `vkWaitForFences` hangs forever. It is the same deadlock as before, except
it only happens when someone resizes the window, which is a far worse bug to own.
**Reset the fence at the last moment before which you are certain you will submit.**

The present side:

**`Renderer.cpp`**, in `drawFrame` — replace the present call:

```diff
     present.pImageIndices = &imageIndex;
 
-    vkQueuePresentKHR(ctx->presentQueue, &present);
+    VkResult presented = vkQueuePresentKHR(ctx->presentQueue, &present);
+    if (presented == VK_ERROR_OUT_OF_DATE_KHR || presented == VK_SUBOPTIMAL_KHR ||
+        framebufferResized) {
+        framebufferResized = false;
+        swapchain->recreate(*ctx, window);
+    } else if (presented != VK_SUCCESS) {
+        vkCheck(presented, "vkQueuePresentKHR");
+    }
```

`SUBOPTIMAL` means "this still works but no longer matches the surface well" — some
drivers report a resize that way instead of `OUT_OF_DATE`. We treat it as a resize
on present but not on acquire, because on acquire the image is valid and we would
rather draw this frame than drop it.

And `framebufferResized` is the belt to that pair of braces. Some window systems
resize without ever returning either code, so GLFW tells us directly:

## Checkpoint

```console
$ cmake --build build && cd build && ./SpaceFighter
[vulkan] using NVIDIA GeForce RTX 4070 (Vulkan 1.3)
[swapchain] 1280x720  format 50  3 images
```

A window filled with **deep space blue** — a very dark, slightly purple navy. It
should stay open and responsive, `Esc` should close it, and **nothing further
should be printed**.

Now stress the parts that are easy to get wrong:

- **Resize the window**, slowly, then quickly, then drag it between monitors. The
  blue should follow the window with no flicker and no validation output.
- **Minimise and restore it.** No output, no spin, no crash.
- **Close it while dragging.** Still clean.

| Symptom | Likely cause |
|---|---|
| Hangs immediately, no window | `VK_FENCE_CREATE_SIGNALED_BIT` is missing. |
| The image count isn't 3 | Perfectly normal — it's your surface's minimum plus one, and minimums of 2, 3 and 4 are all common. |
| Hangs the first time you resize | `vkResetFences` still runs before the `OUT_OF_DATE` early return. |
| Black window instead of blue | The clear value is being applied to the wrong attachment, or `loadOp` is `LOAD` rather than `CLEAR` (chapter 05.A). |
| `vkQueueSubmit … VkResult -4` | `-4` is `DEVICE_LOST` — usually a real GPU fault. Check for validation errors just above it. |
| Validation: "vkCmdBeginRenderPass: framebuffer 0x… was destroyed" | `recreate` ran while a frame was in flight. `vkDeviceWaitIdle` is missing from `Swapchain::recreate`. |
| Validation: semaphore "is being signaled but was never waited on" | The submit and present are using different `FrameSync` slots — check both read `s`, not `sync[0]`. |
| CPU pinned at 100% while minimised | The `w == 0` guard is missing, so the loop spins. |

**Try breaking it on purpose.** Change the clear colour to
`{{1.0f, 0.0f, 1.0f, 1.0f}}` and rebuild — magenta, instantly, which confirms you
are looking at *your* pixels and not at an uninitialised buffer that happens to be
dark. Then set `clears[1].depthStencil = {0.0f, 0}` and rebuild: nothing changes,
because nothing is being depth-tested yet. Make a note of that one — it is the bug
you will have in chapter 08 if the screen comes up empty. Put both back.

## Challenge

Measure the thing the `MAX_FRAMES_IN_FLIGHT = 1` experiment could only be reasoned
about. Add a frame-time counter: accumulate `glfwGetTime()` deltas in `main`, print
the average every second, and compare 1 against 2.

Three things to get right. Vsync will pin you to the refresh rate and hide the
whole effect, so you need `IMMEDIATE` present mode (chapter 05.A's
`choosePresentMode`) for the numbers to mean anything. An empty scene is far too
cheap to show a difference — you will need to come back to this after chapter 08,
when there is actually geometry. And decide what you are averaging: the wall-clock
delta between loop iterations includes the vsync wait, so with FIFO you would be
measuring your monitor, not your renderer.
